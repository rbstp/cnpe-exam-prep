Requests and limits look like Kubernetes 101 until you realize they show up everywhere: quotas count requests, OpenCost bills requests, LimitRanges inject them, Kyverno policies require them, HPAs divide by them, and our resources break drill corrupts them. Lock down these mechanics and four other sections immediately click into place.

Orientation

competency 1.1 + 1.2 · compute and scaling

Just two numbers per container control scheduling, cost, eviction order, CPU throttling, and whether your app survives a noisy neighbor. Let's trace exactly what each number does at every layer.

One sentence that ties it all together

A request is a reservation the scheduler uses for placement math; a limit is a hard ceiling the kernel enforces at runtime. Nothing reconciles the two after scheduling, which is how a node can burn 30% CPU while sitting 100% requested. Section 1.5 puts a dollar figure on that exact gap.

How requests and limits actually work

scheduler arithmetic · cgroup enforcement

What the scheduler does with requests

The scheduler adds up the requests of every non-terminated pod on a node and checks the sum against the node's allocatable resources (not total capacity; allocatable is capacity minus kube-reserved, system-reserved, and eviction thresholds). Live CPU and memory usage never enter the equation. If a node is sitting at 5% real CPU with 100% of its millicores requested, the scheduler treats it as completely full.

CPU is compressible: blow past your limit and the CFS scheduler simply pauses your container until the next 100ms window. Latency-sensitive services with tight CPU limits suffer mysterious periodic stalls that masquerade as network blips. Check container_cpu_cfs_throttled_periods_total to spot it fast. Memory is incompressible: you can't "slow down" RAM, so crossing the ceiling brings down the OOM killer immediately.

Check the right status field

On a one-shot pod (--restart=Never), an OOMKill appears in .status.containerStatuses[0].state.terminated.reason. On a crash-looping Deployment, the container has already bounced, so the proof lives in lastState.terminated.reason while state only shows waiting: CrashLoopBackOff. Looking at state alone and declaring "not an OOM" is an easy trap to avoid.

QoS classes: derive them, don't memorize them

Don't rely on rote recall: tweak the four numbers below and watch the QoS class, eviction rank, and runtime behavior update live:

When a node hits memory pressure, kubelet picks eviction victims in a clear order: pods exceeding their requests go first, ranked by Pod Priority (lowest first) and then by how far over their request they are. QoS class falls straight out of that rule: a BestEffort pod requested zero, so it's always over. Notice the practical takeaway: a high-priority Burstable pod outlives a low-priority BestEffort one, which is why PriorityClass shields platform agents from eviction as well as preemption. The kernel mirrors this ranking through oom_score_adj so node-level OOMs pick the same victim. And remember: CPU pressure never evicts pods, it only throttles them.

Three subtleties show up constantly in tasks. First, taints repel pods, while tolerations only allow placement; they never attract pods on their own. To truly dedicate a node pool, pair a taint with a matching nodeAffinity. Second, NoExecute evicts already-running pods that lack the toleration (with optional tolerationSeconds grace delay). Built right into this cluster

Our kind config stamps its workers into two zones via topology.kubernetes.io/zone so you can actually test spread constraints. Run kubectl get nodes -L topology.kubernetes.io/zone before writing your manifest, because targeting a label key no node carries silently fails open under ScheduleAnyway and locks everything Pending under DoNotSchedule.

One availability neighbor worth keeping top of mind: a PodDisruptionBudget limits voluntary disruptions (node drains, cluster upgrades) using minAvailable or maxUnavailable. It won't stop crashes or hardware failures. Watch out for minAvailable: 100%: it's the fastest way to hang a cluster upgrade forever, and spotting that stalled-drain symptom is an easy exam win.

The HPA formula behind every scaling surprise

desiredReplicas = ceil( currentReplicas × ( currentMetricValue / desiredMetricValue ) )

Keep two details in mind whenever an HPA seems stubborn: it ignores changes inside its tolerance band (10% by default), and it treats unready pods or pods with missing metrics specially. Also notice the denominator: with --cpu-percent=20 on containers requesting 25m CPU, the threshold is just 5m of actual CPU per pod. That's why tiny demo requests scale up under lightweight traffic: percentage targets are always relative to container requests, never node capacity.

By default, scale-up reacts fast while scale-down waits through a 300-second stabilization window to prevent flapping. You can tune both directions per HPA under spec.behavior using pod/percent policies and selectPolicy. Simply knowing that scale-down lag is deliberate saves you from chasing phantom bugs.

VPA update modes

  • Off: calculates recommendations without touching pods. The exam workhorse: gives you pure right-sizing data with zero disruption.
  • Initial: injects recommendations only when new pods are created.
  • Auto / Recreate: evicts and recreates pods to resize them (disruptive by design unless using in-place resize).

Modern Kubernetes clusters support resizing CPU and memory in place, softening that disruption trade-off. Don't probe for support with kubectl explain pod.spec.containers.resizePolicy, because that field has been in the schema since 1.27 regardless of whether the feature is enabled. Instead, check whether the pods/resize subresource exists via kubectl get --raw /api/v1 | grep -o 'pods/resize' (or test a patch directly).

Command reflex

Keep three commands in muscle memory: kubectl top pod --containers for live usage, kubectl describe node for the requests-vs-allocatable summary at the bottom (the best capacity snapshot in kubectl), and kubectl get vpa -o jsonpath='{.items[*].status.recommendation…}' for recommended targets.

Node scaling and disruption mechanics

Cluster Autoscaler vs Karpenter · PDB semantics · PriorityClass · kubelet reservations

Both Cluster Autoscaler and Karpenter react to the exact same trigger (Pending pods that can't fit on existing nodes), and both evaluate consolidation based on pod requests, never live usage. That's why right-sizing requests (1.5) has to come before expecting node-level savings.

Whenever a Karpenter node refuses to consolidate, check its events for Unconsolidatable, which spells out the exact blocker (like a PDB or missing cheaper replacement).

PodDisruptionBudget details

  • Specify either minAvailable or maxUnavailable (integer or percentage). Percentages read .spec.replicas from the owning controller, so bare unmanaged pods can't use percentage budgets.
  • PDBs only guard the Eviction API (node drains, autoscaler consolidation, descheduler). Hardware failures, OOMKills, and rolling updates bypass it (though they still eat into available headroom).
  • unhealthyPodEvictionPolicy (GA since 1.31): IfHealthyBudget (default) blocks evicting even broken pods until the budget is satisfied, which is how a crash-looping app stalls a drain; AlwaysAllow lets unhealthy pods get evicted cleanly and is Kubernetes' recommended setting for flaky workloads.
  • Scheduler preemption treats PDBs as best-effort: if no PDB-safe victim exists, it preempts anyway.

PriorityClass fields

  • Cluster-scoped; user values go up to 1000000000, while system-cluster-critical (2000000000) and system-node-critical (2000001000) are reserved for control plane and node agents.
  • At most one class can set globalDefault: true for pods that omit priorityClassName (otherwise priority defaults to 0); changing it doesn't alter already-running pods.
  • preemptionPolicy: Never lets a workload jump ahead in the scheduling queue without kicking off lower-priority pods, making it ideal for batch jobs. The default PreemptLowerPriority evicts victims.
  • A preempting pod records status.nominatedNodeName while victims shut down gracefully over their terminationGracePeriodSeconds.
  • Use a ResourceQuota with scopeSelector (scopeName: PriorityClass, operator: In, values: [high]) to stop tenants from abusing privileged priority lanes (section 1.4).

Where allocatable comes from

allocatable = capacity - kubeReserved - systemReserved - evictionHard. Kubelet subtracts kubeReserved (kubelet, runtime), systemReserved (sshd, kernel, journald), and evictionHard thresholds (defaults: memory.available: 100Mi, nodefs.available: 10%, nodefs.inodesFree: 5%, imagefs.available: 15%). By default enforceNodeAllocatable: [pods] only enforces pod cgroups; enforcing kube-reserved or system-reserved as well can hurt nodes if your estimates run tight. Always check Capacity vs. Allocatable in kubectl describe node before guessing why a pod won't schedule.

Node sizing rules of thumb

  • Nodes default to 110 pods max (maxPods). Because DaemonSets run on every node, lots of tiny nodes multiply DaemonSet overhead, whereas a few giant nodes widen single-node blast radius and make bin-packing chunky. Two to three zones with at least one spare node's headroom per zone is a solid sweet spot.
  • Bursty, request-heavy apps pack much more smoothly onto larger nodes; Guaranteed pods (requests == limits) pack tightest since nothing can share their slack.
  • Isolate spot or preemptible capacity in a tainted NodePool reserved for stateless, PDB-backed workloads, never single-writer databases.
How this gets tested

"A node has been cordoned for an hour and the drain still won't finish" is a textbook PDB puzzle. Run kubectl get pdb -A, find the budget showing ALLOWED DISRUPTIONS: 0, and choose the right fix: scale the Deployment up, loosen minAvailable, or switch to unhealthyPodEvictionPolicy: AlwaysAllow if the blocking pods are already unhealthy. Only delete the PDB outright if the prompt explicitly asks for it.

In-place resize and recent Kubernetes upgrades

version status stated precisely · Kubernetes 1.37 cluster

In-place pod resize

InPlacePodVerticalScaling reached GA in Kubernetes 1.35 (alpha 1.27, beta and default-on in 1.33), so on our 1.37 lab cluster the pods/resize subresource is ready to go. Here's how it works:

  • Patch via the subresource: kubectl patch pod x --subresource resize --patch '{...}' (or kubectl edit pod x --subresource resize). A regular patch against spec.containers[].resources gets rejected as immutable.
  • Configure per-container, per-resource resizePolicy: restartPolicy: NotRequired (default, resize live) or RestartContainer. Pods with restartPolicy: Never only allow NotRequired.
  • Track progress through pod conditions: PodResizePending with reason Infeasible (node can never fit it) or Deferred (waiting for space to free up), and PodResizeInProgress while kubelet applies it (with reason: Error if the runtime refuses). Check status.containerStatuses[].allocatedResources for what's actually granted and status.observedGeneration to confirm kubelet processed your latest change.
  • Constraints to remember: CPU and memory only; QoS class is locked at pod creation (Guaranteed must stay requests == limits, Burstable can't become Guaranteed, BestEffort can't gain requests); you can't remove a request once set; shrinking memory below live usage stays In Progress; non-restartable init containers, ephemeral containers, Windows pods, and static CPU-manager pods can't resize in place.
  • VPA caught up too: updateMode: InPlaceOrRecreate is GA in VPA 1.6, resizing live whenever kubelet permits and falling back to recreation only when necessary. That eliminates the old eviction penalty for latency-sensitive apps (though the HPA conflict on the same metric still applies).

Pod-level resources

spec.resources on the Pod object itself (beta and default-on since 1.34) defines a shared resource envelope across all containers in the pod, taking precedence for scheduling and QoS. In-place resizing of pod-level budgets hit beta in 1.36. Quotas and LimitRanges count it just like container requests, so always check your cluster version before reaching for it.

Optional topology spread fields

  • minDomains (with DoNotSchedule): treats fewer eligible domains than this minimum as skew, nudging the autoscaler to spin up another zone rather than crowding into two.
  • nodeAffinityPolicy and nodeTaintsPolicy (GA since 1.33): set Honor or Ignore to control whether excluded nodes count toward skew. By default Kubernetes honors affinity and ignores taints, which is why tainted spare nodes can skew your counts.
  • matchLabelKeys (typically pod-template-hash): spreads each ReplicaSet revision independently so rolling updates don't fight your spread rule.

HPA edge cases worth knowing

  • Global tolerance defaults to 10%; per-HPA spec.behavior.scaleUp.tolerance and scaleDown.tolerance hit GA in 1.37 (beta/off-by-default in 1.35–1.36). Verify with kubectl explain hpa.spec.behavior.scaleUp on older exam clusters before using them.
  • Unready pods and pods missing metrics are handled conservatively: assumed to be at 100% of target during scale-down and 0% during scale-up to dampen wild swings. CPU samples from pods ready for under 30s (--horizontal-pod-autoscaler-initial-readiness-delay) are ignored.
  • behavior.scaleDown.stabilizationWindowSeconds defaults to 300 (scale-up defaults to 0); combine policies via selectPolicy: Max (default), Min, or Disabled to freeze scaling in one direction.
  • ContainerResource metrics measure a single container rather than the pod sum, which is essential when heavy sidecars would otherwise distort scaling.
Reflex

Before resizing a live pod, run kubectl get pod x -o jsonpath='{.status.qosClass}'. Because QoS class can never change after creation, any resize that crosses a QoS boundary fails fast with a validation error naming the exact violation.

Self-check

answer before opening
A node shows 25% CPU usage and refuses to schedule a pod requesting 200m. Explain, in one sentence.

The scheduler checks pod requests against allocatable capacity, never live usage, so the node's CPU requests are already maxed out even though the running pods are mostly idle. Fix it by right-sizing inflated requests (or adding nodes).

Which pod does the kubelet evict first under memory pressure, and why?

BestEffort goes first because it declared no memory request at all. Next are Burstable pods exceeding their requests, ordered by how far over they are, with Guaranteed pods last. The kernel's oom_score_adj mirrors that exact ranking so node-level OOMs choose the same victim.

Your service has p99 latency spikes every few seconds; CPU usage sits at 60% of the limit. First metric you check?

Check rate(container_cpu_cfs_throttled_periods_total[5m]). A comfortable 60% average hides bursty per-period throttling: the container burns its 100ms CFS quota early and freezes until the next period starts.

Why can a VPA in Auto mode and an HPA on CPU not coexist on the same workload?

They fight in a feedback loop: HPA scales replicas off usage divided by requests while VPA keeps rewriting those requests underneath it. The clean fix is running HPA on CPU with VPA in Off (advisory) mode, or driving HPA from a custom/external metric while VPA manages CPU/memory.

A drain hangs forever on one node. What are the two usual causes?

Either a PodDisruptionBudget with zero allowed disruptions (like minAvailable equal to total replicas), or unmanaged bare pods with no controller that kubectl drain refuses to evict unless you pass --force.

Is in-place pod resize usable on a Kubernetes 1.37 cluster, and what does the request look like?

Yes: InPlacePodVerticalScaling hit GA in 1.35 (beta/default-on in 1.33). Patch through the resize subresource (kubectl patch pod x --subresource resize ...), since plain spec patches are rejected as immutable. Watch PodResizePending (Infeasible / Deferred) and PodResizeInProgress conditions, and remember QoS class can never change.

Karpenter refuses to consolidate a node you consider empty enough. Where is the reason, and name two things it could be.

Look for Unconsolidatable events on the node. Common blockers include a restrictive PDB, a pod carrying karpenter.sh/do-not-disrupt, no cheaper instance replacement available, or an exhausted NodePool disruption budget (Cluster Autoscaler has analogous blockers like safe-to-evict: "false", bare pods, and local storage).

A PDB has minAvailable 2 for a 2-replica Deployment whose pods are CrashLoopBackOff. Drain hangs. Fix without deleting the PDB?

Patch the PDB with unhealthyPodEvictionPolicy: AlwaysAllow. The default IfHealthyBudget refuses to evict even unhealthy pods while the budget isn't met, deadlocking the drain. Alternatively, scale the Deployment up temporarily, since deleting the PDB strips protection permanently.

What is allocatable, and which four kubelet settings subtract from capacity?

Allocatable is the slice of node capacity available for scheduling pods: total capacity minus kubeReserved, systemReserved, and evictionHard thresholds (defaults: memory.available 100Mi, nodefs.available 10%, nodefs.inodesFree 5%, imagefs.available 15%). enforceNodeAllocatable chooses which cgroups are enforced (default: pods).
