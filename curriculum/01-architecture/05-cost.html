Kubernetes cost management is an allocation problem, not a billing problem. Your cluster costs what it costs; the real question is which namespace, workload, or label owns which slice of the bill, calculated straight from requests, usage, and time out of the Prometheus metrics you already scrape.

Orientation

competency 1.2 · cost management for right-sizing and scaling

Section 1.2 gave you the measurement toolkit. Here we attach dollars to it and close the right-sizing loop: measure real usage, compare it against requests, adjust the numbers, and confirm nothing broke. That loop IS the competency; OpenCost is simply the lens.

The whole allocation formula in one line

For each container over a time window: cost = max(request, usage) × unit_price × hours, summed across CPU, memory, GPU, storage, and network, then rolled up by namespace, label, or controller. Everything in OpenCost is just a different slice of that formula. That's why an idle namespace can still top your cost chart: request won the max().

What actually drives spend, in priority order

requests · idle · sprawl
  1. Requests, not live usage. Schedulers and cost tools bill you for what you reserved. A Deployment requesting 4 CPU while burning 200m still locks up and costs 4 CPU. OpenCost expresses that ratio as efficiency, and closing the gap is right-sizing.
  2. Idle node capacity. You buy nodes whole, so unrequested space on a node is idle spend. OpenCost can either break idle out as its own __idle__ row or distribute it across tenants. Know both options: separating idle holds the platform team accountable for bin-packing, while sharing idle makes tenants feel the real cost of the cluster they share. Neither is wrong; they answer different organizational questions.
  3. Object sprawl. Cloud LoadBalancers, PVs, snapshots, forgotten namespaces, and orphaned PVCs rack up charges even with zero traffic. That's why team-a caps services.loadbalancers at 1.
  4. Node sizing and lifecycle. One layer above your pods: right-sized instance families, spot/preemptible pools, node consolidation (Karpenter), and scaling dev environments down to zero overnight. We can't demo cloud billing in kind, but always state the order clearly: right-size the pods first, then right-size the nodes.

FinOps vocabulary you'll see in scenarios

Showback shares cost visibility with teams; chargeback actually bills their budget. Allocation splits shared spend along a defensible key (namespace, label, owner). Efficiency is usage ÷ billed allocation. Unit economics ties infrastructure spend to a business unit (cost per tenant or per request). Whenever a prompt asks how to cut costs, start with allocation: you can't optimize spend you can't attribute.

FinOps breaks the cycle into Inform (allocate and surface costs), Optimize (right-size, commit, clean up), and Operate (bake budgets and alerts into daily ops). Map those onto Kubernetes layers and you have a rock-solid answer to any "reduce this cluster's spend" prompt:

How OpenCost works under the hood

metrics in, allocation out

OpenCost is a lightweight controller paired with a query API. It pulls pod and node inventory from the API server, joins it against Prometheus usage series (container_cpu_usage_seconds_total, container_memory_working_set_bytes, kube_pod_container_resource_requests, and node capacity), and multiplies by a price sheet (cloud billing rates in production, default on-prem rates in our lab). Don't worry about the lab's synthetic dollar amounts; the ratios and efficiency gaps are completely real.

kube-state-metrics ─┐
cadvisor / kubelet ─┼─▶ Prometheus ─▶ OpenCost ─▶ allocation API ─▶ kubectl cost / UI / Grafana
node inventory     ─┘                     ▲
                        price list (cloud rates or defaults)

Two things to keep in mind before running queries. First, OpenCost is only as accurate as its Prometheus scrapes: a broken scrape produces silent zero-dollar rows rather than a loud error, so debugging a missing namespace starts in Prometheus, not OpenCost. Second, pick an appropriate window: a 1-hour lookback over a brand-new workload tells you very little, so default to --window 1d for steadier numbers.

One flag to commit to memory

kubectl cost targets Kubecost by default. Pass --opencost so it switches to OpenCost's service name, port, and API path automatically. Leave it off and you'll get a connection error that makes OpenCost look down when you were just knocking on the wrong door.

The right-sizing loop (exam-ready version)

  1. Measure: pull actual usage from kubectl top, Prometheus, or VPA recommendations (1.2).
  2. Compare: stack requests against ~p95 usage per container; never hide outliers inside a namespace average.
  3. Adjust: update via kubectl set resources or Git manifests (size memory around peak plus headroom; set sensible CPU requests with generous or omitted CPU limits).
  4. Verify: confirm zero CPU throttling spikes, zero OOMKills, zero Pending pods, and a visibly higher efficiency score.

Step 4 is where candidates earn full credit. Slashing requests until pods throttle or OOM isn't optimization. Always include verification in your answer.

The allocation API and its parameters

/allocation · aggregate · window · idle · pricing sources · what kubectl cost sends

The OpenCost UI, Grafana panels, and kubectl cost all hit the exact same HTTP endpoint on port 9003 (the UI runs as a companion container on port 9090). Knowing the raw query parameters lets you pull answers with curl even when the CLI plugin isn't installed.

GET /allocation

ParameterValuesWhy it matters
windowtoday, yesterday, week, lastweek, month, 30m, 12h, 7d, RFC3339 pair, unix pairrequired; make sure the window covers the workload's lifetime; wider windows smooth out short spikes

Every returned row carries cpuCost, ramCost, gpuCost, pvCost, networkCost, loadBalancerCost, sharedCost, and totalCost, plus cpuEfficiency, ramEfficiency, and totalEfficiency (usage divided by billed max(request, usage), so anything over 1.0 means the container is under-requested). Under the hood, kubectl cost namespace --opencost expands to --service-port 9003 --service-name opencost --kubecost-namespace opencost --allocation-path /allocation/compute; subcommands like namespace, deployment, controller, label, pod, and node map straight to aggregate; and output defaults to a projected monthly rate unless you pass --historical for the window total.

Where pricing comes from

  • Cloud clusters: pulls on-demand list prices from the cloud provider's pricing API using each node's providerID, instance type, and region; spot nodes get spot pricing when labeled (such as Karpenter's karpenter.sh/capacity-type: spot). Real negotiated discounts and invoices come in only when you wire up a cloud billing export.
  • On-prem or kind: nodes without a cloud providerID fall back to the custom provider and default.json (CPU 0.031611/core-hour, RAM 0.004237/GB-hour, GPU 0.95/hour, storage 0.00005479452/GB-hour, spot CPU 0.006655, modeled on GCP us-central1). Override these via the custom pricing ConfigMap or Helm customPricing values whenever a prompt hands you custom rates; only the currency totals shift, never the relative ratios.

Spec definitions scenarios quote

  • Total cluster cost = cluster asset costs (nodes, PVs, attached disks, load balancers, network) + cluster overhead (control plane management fees).
  • Workload cost = max(request, usage) for compute (CPU, GPU, RAM), PVC capacity for storage, and bytes for network, computed per container and rolled up by your aggregation key.
  • Idle cost = asset cost minus workload cost (idle % = idle ÷ allocation costs). Show it on its own row or spread it evenly, proportionally to spend, or by custom metric.
  • Shared costs: platform namespaces like kube-system and monitoring, distributed using the same three options to turn basic showback into fair chargeback.
  • Pods stuck in ImagePullBackOff aren't billed even though they hold requests; Pending pods hold nothing.
Zero cost means a broken scrape

If a namespace with healthy running pods prints $0, OpenCost couldn't join its Prometheus metrics. Check PROMETHEUS_SERVER_ENDPOINT on the opencost Deployment, verify kube-state-metrics and cAdvisor targets are UP, and widen your query window. On sharded Prometheus setups, point OpenCost at the global query layer (Thanos Query or Mimir), never a single shard.

Self-check

answer before opening
A namespace runs almost no traffic and still tops the cost report. Give the two most likely explanations.

Either oversized requests (since you're billed on reservation, not actual traffic) or pricey attached objects like LoadBalancers, large PVs, or retained snapshots. Check efficiency first: rock-bottom efficiency points straight at requests, while high efficiency paired with high cost points at attached objects.

Why is container!="" in that PromQL query not optional?

cAdvisor emits per-container series alongside pod-level and node-level rollups with an empty container label (and often a pause container labeled container="POD"). Without {container!="",container!="POD"}, your sum double- or triple-counts the exact same CPU.

Should idle cost be spread across tenants or shown separately? Argue both.

Spread across tenants: teams feel the true cost of the cluster they share, discouraging resource hoarding. Shown separately: bin-packing and node choice belong to the platform team, so keeping an explicit __idle__ line drives consolidation. Mature orgs show both: per-tenant request spend plus a platform-owned idle row.

You cut a deployment's CPU request from 500m to 50m and latency degrades. What happened?

CPU requests set the cgroup weight, so under node contention your container suddenly gets a tiny slice of CPU time, and if you tightened the limit alongside it, CFS throttling kicks in hard. Right-sizing targets observed peak usage with headroom, not the flat average. Always validate changes with throttling metrics, not just the cost chart.

Give the four-step right-sizing loop in one breath.

Measure usage → compare against requests → adjust requests → confirm zero degradation (no throttling, OOMs, or Pending pods) and check the new efficiency score. That fourth step is what separates real engineering from blind cost-cutting.

Show cost per team when teams span several namespaces and pods carry a team label. Query?

Hit /allocation?window=7d&aggregate=label:team (or run kubectl cost label --opencost -l team). OpenCost aggregates on any label:<key> or annotation:<key>, and enforcing that label via Kyverno is what keeps your __unallocated__ bucket small.

What does shareIdle=true change in the numbers, and who should want it?

It removes the __idle__ row and redistributes that idle spend across all other rows proportionally to their cost, per resource. Use it when you want tenants to absorb the full cost of the shared cluster; keep includeIdle=true without sharing when the platform team owns bin-packing accountability.

Where do on-prem prices come from, and what is the CPU default?

Nodes without a cloud providerID fall back to the custom provider and OpenCost's default.json: CPU 0.031611/core-hour, RAM 0.004237/GB-hour, GPU 0.95/hour (modeled on GCP us-central1). Override them with a custom pricing ConfigMap or Helm values. Even with notional numbers, the ratios and efficiency scores stay completely valid.

A workload shows totalEfficiency 1.4. Is that good?

No: it means actual usage ran 40% above requests. It looks cheap on paper, but the pod is borrowing headroom from neighbors and sits first in line for OOM eviction under memory pressure. Bump requests closer to observed usage; efficiency near (but just under) 1.0 is the sweet spot.
