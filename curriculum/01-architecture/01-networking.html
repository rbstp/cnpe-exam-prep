Orientation

competency 1.1 · architecture best practices

Networking sits underneath everything else on the platform. A Crossplane XR that never turns Ready, an Argo CD app stuck Progressing, a Prometheus target that won't scrape, a canary that never sees traffic - half the time, the culprit is one mismatched Service selector, one missing DNS egress rule, or one unready endpoint.

What the exam actually asks

Nobody is going to ask you to write an essay on CNI plugins. You'll be asked to make traffic flow or block it cleanly, and prove it: expose an app, lock down a namespace, build a Gateway and HTTPRoute, or debug why a Service resolves in DNS and then refuses every connection. With a clear mental model, these are five-minute wins. Without one, they turn into twenty minutes of guesswork.

The four rules of the Kubernetes network model

  1. Every pod gets its own cluster-routable IP, with no NAT between pods.
  2. Pods on any node can reach pods on any other node without NAT.
  3. Node agents (kubelet, system daemons) can reach every pod on that node.
  4. A pod sees its own IP as the exact same address other pods use to reach it.

Your CNI plugin is whatever makes those four rules true - routing, an overlay, or an eBPF datapath. Everything layered on top (Services, DNS, NetworkPolicies, Gateways) assumes that foundation holds. If it doesn't, everything above behaves strangely, which is why "is this a CNI problem or a Service problem?" is always your first fork when debugging network failures.

Services and what actually makes them work

ClusterIP · NodePort · LoadBalancer · headless

ClusterIP is a virtual IP that exists only as translation rules on each node - no interface owns it, nothing listens on it, and you can't meaningfully ping it. NodePort exposes that Service on a high port (30000–32767 by default) across every node. LoadBalancer layers an external IP on top of NodePort (in our lab, cloud-provider-kind hands those out). Headless (clusterIP: None) skips the VIP completely and returns pod IPs straight from DNS, which StatefulSets rely on for stable peer discovery. ExternalName is just a DNS CNAME with zero proxying.

The real mental model

The Service itself doesn't route packets. The EndpointSlice behind it does, populated by whatever pods match the Service's selector. A Service with zero ready endpoints resolves cleanly in DNS and then refuses every connection - one of the exam's favorite troubleshooting setups. Check in this exact order every time: does the selector match the pod labels → are those pods Ready (readiness gates endpoint membership) → run kubectl get endpointslices -l kubernetes.io/service-name=<svc>.

Two nearby knobs control whether a pod receives traffic at all. A failing readinessProbe pulls the pod out of the EndpointSlice, which is how Kubernetes drains it gracefully. Setting publishNotReadyAddresses: true overrides that so clustered databases behind a headless Service can discover peers before they're ready to serve traffic. Finally, pairing terminationGracePeriodSeconds with a short preStop sleep closes the classic rollout race where a pod terminates before every node finishes removing its routing rules - connection resets during deployments almost always trace right here.

Traffic policies

  • externalTrafficPolicy: Cluster (default) SNATs traffic and may bounce it to another node, so your backend sees the node's IP instead of the client's. Switching to Local preserves the real client IP and routes only to pods on the receiving node, with one trade-off: nodes with no matching pod blackhole traffic, so you rely on external load balancer health checks to steer around them.
  • internalTrafficPolicy: Local brings the same behavior inside the cluster: route to node-local endpoints only. Handy for node-local caches and log shippers.
  • sessionAffinity: ClientIP is the only stickiness native Services support. Anything smarter belongs in a Gateway or service mesh.

Command reflex

Reach for kubectl get endpointslices -l kubernetes.io/service-name=X instead of describe svc. It breaks out per-address conditions (ready, serving, terminating) rather than flattening them into a plain IP list, so half-broken rollouts jump off the screen immediately.

The datapath: kube-proxy, eBPF, and why this lab uses Cilium

Cilium · Hubble · identities

Traditional kube-proxy watches Services and EndpointSlices and programs every node: iptables mode builds DNAT chains (simple, though lookup cost grows with rule count), while IPVS mode uses kernel load balancing with real scheduling algorithms. eBPF datapaths like Cilium and Calico can replace kube-proxy outright, performing translation at the socket or TC layer - sidestepping rule-table scaling limits and giving you deep flow visibility.

client pod
   │ connect 10.96.0.42:80          ← ClusterIP, exists only as a rule
   ▼
[ datapath ]  kube-proxy iptables/IPVS  or  eBPF (Cilium, this lab)
   │ DNAT → picks one endpoint from the EndpointSlice
   ▼
backend pod IP 10.244.2.17:8080
   │
   ▼ policy is evaluated on the pod identity, not the Service VIP

Don't miss that last line. An ipBlock rule targeting a ClusterIP never matches because DNAT has already rewritten the destination to a pod IP before policy runs. That one quirk explains a whole category of "why is my NetworkPolicy doing nothing?" bugs - and section 3.3 springs the exact same trap with CloudNativePG.

Our lab swaps out kindnet for Cilium (with kube-proxy still running alongside it) for one huge reason: kindnet ignores NetworkPolicies completely. Practicing on a CNI that accepts your policies and enforces nothing teaches terrible muscle memory. Cilium also compiles pod labels into numeric identities (so policy stays rock-solid even as pod IPs churn) and ships Hubble, which prints live packet flows along with their verdicts: forwarded or dropped, and why.

Cilium extras worth knowing by name

CiliumNetworkPolicy covers things standard Kubernetes NetworkPolicy can't express: toFQDNs (allow api.github.com by domain name, enforced via DNS), toEntities (kube-apiserver, world, host, remote-node), and L7 HTTP/DNS/Kafka rules. You won't be quizzed on obscure CRD fields, but "how do you allow egress specifically to the API server?" is a fair scenario, and here the clean answer is toEntities: [kube-apiserver].

DNS: the layer that fails quietly

CoreDNS · search domains · ndots

Cluster names follow <svc>.<ns>.svc.cluster.local, served by CoreDNS in kube-system behind a Service still named kube-dns for historical reasons. Every pod's /etc/resolv.conf gets a search list and ndots:5, meaning any hostname with fewer than five dots gets tried against every search domain first. Look up backend.default.svc.cluster.local (only four dots!) and the resolver fires off four or five queries before hitting the right one. Appending a trailing dot (backend.default.svc.cluster.local.) skips the search list completely - a cheap, instant win for DNS-heavy apps.

You can override all of this per pod with spec.dnsPolicy and dnsConfig: ClusterFirst (default), None with explicit nameservers, or Default (inherit the node's resolver). That comes up whenever a workload has to resolve an external private DNS zone.

The silent failure this lab drills on purpose

team-a allows DNS egress through one explicit NetworkPolicy rule (UDP/TCP 53 to kube-dns). The netpol break drill deletes just that rule. Every pod stays Running, every probe stays green, and nothing in the namespace can resolve a single hostname. kubectl get pods won't give you a clue. You catch it by forcing a lookup from inside (nslookup) and spotting Hubble's DROPPED verdicts on port 53. This exact break comes back in section 4.6.

NetworkPolicy semantics

additive allow-lists · both ends must open
  • Policies are namespaced and always select pods, never Services.
  • Until a policy selects a pod for a given direction, everything in that direction is allowed. The moment any policy selects it, that direction becomes isolated.
  • Rules are strictly additive allow-lists - there is no deny rule. You open traffic by adding rules and tighten it only by removing them. That asymmetry is why the DNS break drill is sneaky: a deleted rule leaves no trace that it was ever there.
  • Ingress and egress are evaluated independently. Cross-namespace traffic needs an egress allow on the caller and an ingress allow on the destination. Hitting that wall once in section 1.4 ("Cross-tenant traffic must die") locks it in so you never waste exam time rediscovering it.
  • Default-deny is just a policy with an empty podSelector, policyTypes: [Ingress, Egress], and zero allow rules.
  • Watch your YAML indentation inside rules: namespaceSelector and podSelector in the same list item mean AND (those specific pods in those namespaces); split into two list items (with an extra dash) they mean OR. This single typo is the #1 NetworkPolicy bug.
Exam angle

When a prompt says "team-a may only talk to team-b's web service and DNS," that usually means three objects, not one: default-deny in team-a, an egress allow in team-a (for both team-b and DNS), and an ingress allow in team-b. Verify like a grader: run one curl that returns 200 and a second curl to something forbidden that times out.

Ingress vs Gateway API

Gateway API is the modern answer

Classic Ingress jammed everything into one object with no clear ownership and relied on a jungle of controller-specific annotations. Gateway API splits that cleanly by team role - and those role boundaries are the whole design point:

KindOwned bySays
GatewayClassinfrastructure providerwhich controller implements Gateways of this class
Gatewayplatform teamlisteners: ports, protocols, TLS, and which routes can attach
HTTPRoute / GRPCRoute / TCPRouteapplication teammatch rules, filters, weighted backends
ReferenceGrantthe referenced namespaceexplicit permission for cross-namespace backend or Secret references

Like NetworkPolicy, route attachment takes two hands to clap: the route points at a Gateway with parentRefs, and the Gateway's listener declares allowedRoutes (same namespace, selected namespaces, or all). If the Gateway refuses the attachment, kubectl apply still succeeds - you only see the rejection in the route's status.

Always grade your own Gateway work by reading three status conditions: Accepted (the controller understood and attached it), Programmed (the data plane is actually configured), and ResolvedRefs (every backend Service and TLS Secret exists and is permitted). Reading those three beats guessing every single time.

Lab heads-up

Our main cluster installs the Standard-channel Gateway API CRDs so you can author manifests and validate schemas, but there's no controller programming a data plane on the main cluster. Your Gateway will sit unprogrammed there - don't confuse a clean apply with live routing. On the mesh cluster (make mesh), Istio actually implements Gateway API, giving you real Programmed: True status conditions with the exact same YAML.

One crucial neighbor Kubernetes doesn't ship out of the box: certificates. Every HTTPS listener points at a TLS Secret, and something has to mint and renew it. Usually that's cert-manager: an Issuer or ClusterIssuer (ACME, CA, or Vault) paired with a Certificate (or the cert-manager.io/cluster-issuer annotation right on the Gateway). We don't install cert-manager in this lab, but "how does that TLS cert get renewed?" is fair game in any architecture question, and a missing Secret is a classic cause of ResolvedRefs: False.

Gateway API also bridges straight into progressive delivery (section 2.5): weighted backendRefs on an HTTPRoute let controllers like Flagger shift live traffic by percentage instead of crude replica math.

Gateway API, field by field

listeners · matches · filters · weights · ReferenceGrant · status reasons

That role table gives you the architecture; an exam task hands you the exact fields. Our lab installs Gateway API v1.7 (October 2026), and everything below is Standard channel unless noted. Under the exam clock, kubectl explain gateway.spec.listeners --recursive and kubectl explain httproute.spec.rules --recursive give you the exact schema for whatever version sits in front of you.

Gateway listeners

  • name, port, protocol (HTTP, HTTPS, TLS, TCP, UDP) plus an optional hostname. Two listeners colliding on the same port, protocol, and hostname trigger Conflicted: True with reason HostnameConflict or ProtocolConflict.
  • tls.mode: Terminate (the Gateway decrypts TLS using tls.certificateRefs pointing to a kubernetes.io/tls Secret) or Passthrough (SNI-only routing, paired with TLSRoute). Pointing at a Secret in another namespace requires a ReferenceGrant in that Secret's namespace, or you'll hit ResolvedRefs: False with RefNotPermitted.
  • allowedRoutes.namespaces.from: Same (default), All, or Selector with a label selector; allowedRoutes.kinds narrows which route types can attach. This is the Gateway's half of the attachment handshake.
  • Gateway conditions: Accepted (reasons like ListenersNotValid or Pending), Programmed (AddressNotAssigned, NoResources), plus per-listener Accepted, ResolvedRefs, and Programmed. A Gateway referencing a class with no running controller sits at Accepted: Unknown indefinitely.

HTTPRoute rules

  • parentRefs attach to the Gateway; add sectionName (the listener name) or port to target one specific listener instead of all of them. Your route's hostnames must intersect the listener's hostname, otherwise you get Accepted: False (NoMatchingListenerHostname).
  • matches: items inside a single match entry are ANDed together (path AND headers AND queryParams AND method), while separate list entries are ORed. Path types are PathPrefix (default), Exact, and RegularExpression (implementation-specific). Omit matches entirely and it defaults to PathPrefix /, matching everything.
  • filters: RequestHeaderModifier, ResponseHeaderModifier, RequestRedirect, URLRewrite (mutually exclusive with redirect), RequestMirror, CORS (Standard since v1.5), and ExtensionRef for vendor CRDs. Filters replace almost every controller-specific Ingress annotation you used to memorize.
  • backendRefs: name, port, optional namespace (needs a ReferenceGrant), and weight (default 1). Weights are proportions of the sum: 90 and 10 split 90/10; 3 and 1 split 75/25. A rule with neither backendRefs nor a redirect returns HTTP 500, and a missing Service produces ResolvedRefs: False (BackendNotFound).
  • timeouts (Standard since v1.2): request bounds the entire exchange while backendRequest bounds a single attempt (and can't exceed request; 0s disables).
  • retry (Standard since v1.7): attempts (retries after the initial try; 0 disables), codes (unique status codes to retry), and backoff (base interval; curve and jitter are implementation-defined). Support is Extended, so verify your controller supports it before leaning on it.

The neighbors that arrived recently

  • ReferenceGrant is v1 since v1.5: from (group, kind, namespace of the referrer) and to (group, kind, optionally name) in the namespace being referenced. It is consent, never a route: it grants nothing by itself.
  • BackendTLSPolicy (Standard since v1.4) configures TLS from the Gateway to the backend pods: targetRefs a Service, validation.hostname as SNI, and either caCertificateRefs or wellKnownCACertificates: System. Same namespace as the Service, by design.
  • ListenerSet (Standard since v1.5) lets a team add listeners to a shared Gateway without editing it; the Gateway must opt in with spec.allowedListeners.namespaces.from (default None). Parent listeners win conflicts. It also lifts the 64-listener ceiling.
  • TLSRoute is v1 since v1.5, and TCPRoute and UDPRoute since v1.6 (their v1alpha2 is deprecated); GRPCRoute has been Standard since v1.1.

How this gets tested

"Expose service X on host Y through the existing Gateway in namespace infra" boils down to three checks: does the Gateway's listener allow routes from your namespace (allowedRoutes), does your route's hostname match the listener's, and do status.parents[].conditions report Accepted: True and ResolvedRefs: True? Pointing at a Service in another namespace adds a fourth piece: a ReferenceGrant in the backend's namespace, not yours.

On the pod side: dnsPolicy defaults to ClusterFirst, EXCEPT a hostNetwork: true pod silently falls back to the node's resolver unless you explicitly set ClusterFirstWithHostNet. Policy quirks across engines

  • Always match a namespace by name using the immutable kubernetes.io/metadata.name label inside namespaceSelector - never leave an empty {}, which matches every namespace in the cluster.
  • In Cilium, ipBlock rules don't match pod or node IPs by default (unless you change policyCIDRMatchMode); Cilium selects pods by labels and identities. That's a second reason, beyond DNAT, why CIDR-based rules look like they do nothing.
  • CiliumClusterwideNetworkPolicy is the cluster-scoped twin of CiliumNetworkPolicy for global baseline rules like "everyone can reach DNS and the API server." Cilium 1.20 also supports the upstream ClusterNetworkPolicy API with admin and baseline tiers that ordinary tenant NetworkPolicies can't override.

Cluster architecture callouts

  • HA control plane: at least three control plane nodes. Stacked etcd (colocated on control plane nodes, kubeadm's default) is simpler to operate; external etcd needs six hosts, but losing a node no longer knocks out both an API server and an etcd member at once. Either way, put a load balancer in front of the API servers - Kubernetes won't fail over the endpoint for you.
  • Availability zones: nodes carry topology.kubernetes.io/zone and region labels. Spread control planes across at least three zones, spread workloads with topologySpreadConstraints, and use WaitForFirstConsumer storage so volumes don't get provisioned in a zone your pod can't reach.
  • Scale ceilings worth keeping in your back pocket: 110 pods per node by default, 5,000 nodes, and 150,000 pods per cluster.
  • Multi-cluster delivery: run a hub Argo CD with cluster Secrets and an ApplicationSet clusters generator, or run one Flux instance per cluster watching clusters/<name> in a shared repo. Hub-and-spoke centralizes UI and credentials; agent-per-cluster keeps credentials local and rides out a hub outage cleanly. Section 2.2 digs into the objects.
The hostNetwork DNS trap

If a monitoring agent or CNI helper running with hostNetwork: true suddenly can't resolve cluster Services, it's almost always using dnsPolicy: ClusterFirst (which acts like Default on host-network pods). Flip it to ClusterFirstWithHostNet. This masquerades as a NetworkPolicy drop, and Hubble stays eerily quiet because the packet never even aimed at CoreDNS.

Self-check

answer out loud before opening
A Service resolves in DNS but every connection is refused. Name the three things you check, in order.

First, compare the Service selector against the actual pod labels. Second, check pod readiness (unready pods don't join the slice). Third, inspect the EndpointSlice directly. Addresses marked ready: false point to a failing readiness probe; an empty slice points to a selector mismatch or unscheduled pods.

Why does a NetworkPolicy ipBlock naming a Service's ClusterIP never work?

Because DNAT rewrites the ClusterIP to a backend pod IP before policy runs. NetworkPolicy operates on pod selectors and identities, not virtual IPs. To allow egress specifically to the API server in Cilium, use toEntities: [kube-apiserver].

Your backend needs the real client IP. What do you change, and what breaks?

Set externalTrafficPolicy: Local on the Service. The trade-off: nodes without a matching pod stop forwarding that traffic, so you now depend on your external load balancer's health checks to route around them, and traffic distribution becomes less even than with Cluster.

What is the difference between a headless Service and a ClusterIP Service with one endpoint?

A headless Service has no VIP and no datapath translation: DNS hands back pod IPs straight to the client. Even with a single endpoint, a normal ClusterIP Service still routes through the VIP rules, hiding the pod IP. StatefulSets need headless Services for stable per-pod hostnames like pod-0.svc….

Team-a can curl team-b's Service after you added an egress allow, but it still fails. What did you forget?

team-b's ingress policy. NetworkPolicies are independent allow-lists at both ends, so both sides have to open up. Also double-check DNS: once team-a restricts egress, resolving web.team-b.svc requires an explicit port-53 allow to kube-dns.

An HTTPRoute applies cleanly but nothing routes. Where do you look first?

Check status.parents[].conditions on the HTTPRoute. Accepted: False usually means the Gateway's allowedRoutes rejected attachment; ResolvedRefs: False means a backend Service or TLS Secret is missing (or lacks a cross-namespace ReferenceGrant). On the Gateway itself, Programmed: False means no data plane controller is running - which is always true on this lab's main cluster.

An HTTPRoute in team-a references a Service in team-b. Which object, in which namespace, and what does status say until it exists?

Create a ReferenceGrant in team-b (the target namespace) with from matching group gateway.networking.k8s.io, kind HTTPRoute, namespace team-a, and to matching kind Service. Until that grant exists, the route reports ResolvedRefs: False (reason RefNotPermitted) and returns HTTP 500 for that backend.

Two backendRefs carry weight 3 and weight 1. What split is that, and what happens if one backend Service is missing?

A 75/25 split - weights are shares of the total (3 + 1 = 4). If one Service is missing, the route reports ResolvedRefs: False (BackendNotFound), keeps forwarding traffic to the valid backend, and returns HTTP 500 for the broken backend's share - causing intermittent errors proportional to its weight.

A stub domain for corp.example must resolve via 10.0.0.53. Where does the change go and how long before it applies?

Add a second server block to the coredns ConfigMap in kube-system: corp.example:53 { errors; cache 30; forward . 10.0.0.53 }. The reload plugin picks it up within about two minutes with no pod restarts. Verify with nslookup from a pod, and check kubectl -n kube-system logs deploy/coredns for parse errors if it doesn't take.

Which kube-proxy mode is GA and newest, and what changes for NodePort when you switch to it?

nftables, GA since Kubernetes 1.33 (kernel 5.13+). NodePorts default to --nodeport-addresses primary, meaning they only answer on the node's primary IP (other interfaces and localhost stop responding), and kube-proxy stops opening firewall rules for the NodePort range. IPVS is deprecated as of 1.35; iptables remains the default.
