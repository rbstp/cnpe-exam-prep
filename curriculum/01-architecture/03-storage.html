Orientation

competency 1.1 · architecture best practices

Performance exams almost never ask you to install a CSI driver from scratch. Instead, they throw real operational puzzles at you: why is this claim stuck Pending, why did this pod lose its data, how do we make this workload survive a reschedule, how do we grow this volume? All four come straight down to four fields you should know cold.

Exam angle

The grader only sees live objects and their status. That's why almost every storage problem announces itself through one of three tells: a PVC stuck Pending, a PV stuck Released, or a pod stuck ContainerCreating with mount errors in its events. Map those three symptoms cleanly to their causes and you've got this competency locked down.

The model: three objects, one relationship

PV · PVC · StorageClass

A PersistentVolume represents a real slice of storage. A PersistentVolumeClaim is a user's request for it. A StorageClass is the blueprint for creating PVs on demand, with provisioner naming the controller that handles the work. Static provisioning (an admin pre-creating PVs) still exists, but dynamic provisioning is the default everywhere: the PVC asks for a class, the provisioner spins up a PV, and the two bind exclusively one-to-one.

pod ──mounts──▶ PVC ──binds 1:1──▶ PV ──backed by──▶ real disk / host path / cloud volume
                 │                  ▲
                 └── storageClassName ──▶ StorageClass ──▶ provisioner creates the PV
                                          (binding mode, reclaim policy, expansion, params)

Under the hood, CSI is the standard interface modern drivers implement, split into a controller side (provision, attach, snapshot) and a node side (mount/format). You won't write a CSI driver on the exam, but knowing that split tells you where to look when things break: "failed to provision" lives in controller logs, while "failed to mount" lives on the node.

The fields that decide exam tasks

FieldValuesWhat it changes
accessModesRWO · ROX · RWX · RWOPA PVC only binds to a PV that offers its requested mode. local-path only supports RWO, so an RWX claim sits Pending forever - spotting why immediately is the skill.
volumeBindingModeImmediate · WaitForFirstConsumerWaitForFirstConsumer holds the PVC in Pending until a pod actually mounts it, letting the scheduler pick the right zone first. Our standard class uses it, so you'll see a healthy Pending PVC right away.
persistentVolumeReclaimPolicyDelete · RetainDelete destroys the backing volume when the claim goes away; Retain keeps the data and leaves the PV Released so nothing can rebind to it until an admin clears spec.claimRef.
allowVolumeExpansiontrue · falseOnly classes with this set to true let you grow a PVC by bumping spec.resources.requests.storage. Shrinking is never supported anywhere.
volumeModeFilesystem · BlockBlock exposes a raw block device to the container. Mostly used by specialized databases.
Access modes are a capability match, not magic

Requesting RWX doesn't magically turn a local disk into a shared filesystem - it just asks for a PV whose backing storage already supports multi-node read-write mounts. Likewise, nothing stops two pods on the same node from trampling each other on an RWO volume. RWOP (ReadWriteOncePod) is the strict lock: strictly one pod at a time, enforced by both the scheduler and kubelet, so two database replicas can never corrupt the same volume.

Both protection finalizers look like bugs the first time you hit them, and both are saving you from yourself: pvc-protection blocks deleting a claim while a pod still mounts it, and pv-protection blocks deleting a bound PV. Never start by ripping off the finalizer - remove the pod first and let the controller clean up cleanly. Stripping finalizers blindly is the Kubernetes equivalent of yanking out a live hard drive.

StatefulSets: where storage semantics show up

volumeClaimTemplates stamps out a dedicated PVC for each replica, named <template>-<sts>-<ordinal>. Deleting the StatefulSet leaves those PVCs behind by default (unless you opt into persistentVolumeClaimRetentionPolicy), so scaling back up reconnects cleanly to the exact same data. That durability - paired with stable hostnames and ordered rollouts - is the whole point of using a StatefulSet over a Deployment.

This is also where GitOps hits its boundary: data. Deleting a namespace and letting Argo CD or Flux rebuild it brings back your YAML, not the bytes inside a PV. Three mechanisms cover disaster recovery: CSI snapshots for fast in-cluster point-in-time copies, a backup tool like Velero to ship cluster objects and volume backups off-cluster, and operator-native backups for databases. Knowing which of the three protects your state is the complete DR answer.

Snapshots mirror the exact same three-object pattern: VolumeSnapshotClass, VolumeSnapshot, and VolumeSnapshotContent. Since local-path doesn't support snapshots, this lab teaches the Kubernetes snapshot APIs conceptually and lets CloudNativePG show you real database backups.

What a platform engineer actually decides

classes as product

Section 3.1's "platform APIs as products" idea shows up right here: StorageClasses are a user-facing product menu. Each class hides durability, performance, and cost choices that app teams shouldn't have to reinvent.

  • Name classes by intent (fast-ssd, cheap-hdd, shared-rwx), not by today's underlying vendor driver.
  • Mark exactly one default class (storageclass.kubernetes.io/is-default-class) and price it deliberately, because every PVC that omits storageClassName buys it automatically. If two classes are marked default, the DefaultStorageClass admission plugin quietly picks the newest one - worse than an error, because behavior silently shifts the next time someone adds a class.
  • Default to WaitForFirstConsumer anywhere zones exist, so volumes aren't created in a zone your pod can't schedule into.
  • Use Delete for ephemeral tenant scratch space and Retain for anything whose loss would trigger a postmortem.
  • Cap tenant storage with quotas: requests.storage for the total cap, and <class>.storageclass.storage.k8s.io/requests.storage per class so teams don't default everything onto your most expensive NVMe tier (section 1.4).
Command reflex

Start every storage investigation with kubectl get sc: one table shows provisioner, reclaim policy, binding mode, and expansion support at a glance. Then run kubectl get pvc -A and hunt for anything that isn't Bound.

Backup and restore as objects: Velero

When an exam scenario reaches for a cluster backup tool, Velero is the standard name, built around four CRDs. A BackupStorageLocation points at your object store (bucket, prefix, provider plugin); a VolumeSnapshotLocation says where disk snapshots land; a Backup picks what to capture (includedNamespaces, includedResources, labelSelector, ttl defaulting to 30 days); and a Schedule wraps a Backup template in a cron expression, emitting backups named <schedule>-<timestamp>. Velero copies volume data either via CSI snapshots (moved/deleted once backed up) or via file-system backup (a node agent reading mounted files - works on any volume type, at the cost of crash-consistency). For application-consistent backups, use pre and post exec hooks (like flushing a database before snapshotting). A Restore replays the backup, optionally remapping namespaces with namespaceMapping: {abc: def}, and stamps restored resources with velero.io/restore-name. In a GitOps cluster, keep the boundary crisp: Git restores manifests, Velero (or your DB operator) restores PV data, and neither replaces the other.

Lifecycle features by version, and copying data

retention · expansion · snapshots · clones · ephemeral volumes · VolumeAttributesClass

Every item below maps to a concrete field on a PVC, StatefulSet, or StorageClass that a task can ask for, along with the Kubernetes version where it graduated. Our lab runs 1.37, so everything marked GA works out of the box.

StatefulSet PVC retention (GA since 1.32)

spec.persistentVolumeClaimRetentionPolicy gives you two switches, each set to Retain (default) or Delete: whenDeleted governs StatefulSet deletion, and whenScaled governs scale-down. Under the hood, Delete attaches an ownerReference to the PVC so garbage collection removes it once its pod terminates - whereas a pod recreated after a node failure keeps its claim untouched. The go-to production pairing is whenDeleted: Retain, whenScaled: Delete: accidental deletes keep your data safe, while intentional scale-downs don't leak orphaned disks.

Expansion and recovering from failed grows

  • Requires allowVolumeExpansion: true on the StorageClass plus CSI driver support. Always edit spec.resources.requests.storage on the PVC, never the PV (editing the PV tricks the controller into thinking the grow already finished).
  • The underlying block device expands first; the filesystem (ext3, ext4, xfs) expands only when a pod mounts the claim (online if the driver supports it). Until a pod mounts it, the PVC shows FileSystemResizePending - totally normal if no consumer is running.
  • You still can't shrink a bound volume, but you can cancel a failed expansion: thanks to RecoverVolumeExpansionFailure (GA since 1.34), you can lower the requested size back down to anything above status.capacity. Track live progress in status.allocatedResources and status.allocatedResourceStatuses (such as ControllerResizeInProgress or NodeResizePending).

Snapshots, clones, and populators

WantWriteNeeds

Two protections that look like hangs: a PVC with an in-flight snapshot can't be deleted until the snapshot reaches readyToUse, and a bound PV holds kubernetes.io/pv-protection. Let both clear on their own rather than stripping them.

Ephemeral volumes

  • Generic ephemeral volume (GA since 1.23): declare volumes[].ephemeral.volumeClaimTemplate right inside the Pod spec. Kubernetes creates a real PVC named <pod>-<volume> owned by the pod, so it vanishes when the pod does - yet while alive, it supports snapshots, clones, and expansion just like any normal PVC. Pair it with WaitForFirstConsumer classes so scheduling chooses the node first.
  • CSI ephemeral volume: inline volumes[].csi with no PVC object, used by drivers declaring the Ephemeral mode (like secrets-store drivers). Data dies with the pod and bypasses StorageClasses entirely.
  • emptyDir counts against ephemeral-storage requests and limits; add medium: Memory and it counts against container memory instead (and supports in-place resize on cgroup v2 nodes).

VolumeAttributesClass (GA since 1.34)

A StorageClass controls how a volume is provisioned; a VolumeAttributesClass (driverName plus performance parameters like IOPS and throughput) controls how it performs afterward. Better yet, pvc.spec.volumeAttributesClassName is mutable - upgrading a volume from silver to gold is a live edit instead of a data migration, and you can quota it per class (<vac>.volumeattributesclass.storage.k8s.io/...). Whenever a scenario asks how to change disk performance tiers without recreating the PVC, this is the answer.

Smaller versioned facts worth remembering

  • Retroactive default class (GA since 1.28): if you create a PVC with no storageClassName while no default exists, Kubernetes retroactively patches in the default as soon as one is annotated. Explicitly setting storageClassName: "" opts out and binds only to classless PVs.
  • ReadWriteOncePod (GA since 1.29, CSI-only): strictly enforced by scheduler and kubelet, unlike RWO/ROX/RWX which are matching hints.
  • HonorPVReclaimPolicy adds an external-provisioner.volume.kubernetes.io/finalizer so a Delete PV still cleans up its backend disk even if the PV is deleted before its PVC.
  • StatefulSet updateStrategy.rollingUpdate.maxUnavailable is beta since 1.35 (on by default in 1.35.0–1.35.3, off in 1.35.4–1.36, back on by default in 1.37), and Recreate is also feature-gated. Don't rely on either unless verified; default updates remain one pod at a time, highest ordinal first.
How this gets tested

"Grow the database volume to 20Gi" is graded against the PVC's status.capacity - editing the spec alone scores nothing. If the StorageClass lacks allowVolumeExpansion, admission rejects the edit immediately ("only dynamically provisioned pvc can be resized and the storageclass that provisions the pvc must support resize"). And if no pod mounts the claim, capacity stays frozen at the old size with FileSystemResizePending until a consumer actually runs.

Self-check

answer before opening
A PVC has been Pending for ten minutes and describe shows no events at all. Bug or not?

Not a bug if the StorageClass uses WaitForFirstConsumer and no pod mounts it yet: until a pod is scheduled, Kubernetes won't provision anything or emit events. It turns into a real bug only once a pod references the claim and it still sits Pending - at which point the events appear and tell you why.

A PV sits in Released and your new, identical PVC will not bind to it. Why, and what is the fix?

Retain leaves spec.claimRef pointing at the old claim, so Kubernetes treats the PV as still spoken for. Clear it with kubectl patch pv <name> -p '{"spec":{"claimRef":null}}' to flip it back to Available. The real engineering decision is whether you should wipe the leftover data before letting another workload mount it.

You delete a StatefulSet and its PVCs remain. Accident or design?

100% by design. Keeping PVCs alive ensures scaling back up reattaches the same data and prevents an accidental delete from wiping a database. When you want automatic cleanup, opt in via persistentVolumeClaimRetentionPolicy (whenDeleted and whenScaled).

Two pods on different nodes must share a directory. What do you need, and what will this lab do?

You need a StorageClass backed by an RWX-capable provisioner (NFS, CephFS, or a cloud file service). Because local-path only supports RWO, the claim sits Pending and its events explain why. Saying "the current provisioner can't do RWX, here's the class/driver swap required" is the exact right answer both in the lab and on the exam.

Which quota lines cap tenant storage, and why is per-class quota interesting?

requests.storage caps total volume size and persistentvolumeclaims caps the object count; <class>.storageclass.storage.k8s.io/requests.storage caps a single class. Per-class quotas let platform teams offer an expensive high-IOPS tier without letting every tenant quietly burn budget on it.

You want scale-down to reclaim volumes but deleting the StatefulSet by mistake to keep them. Which fields, and since when is this GA?

Set persistentVolumeClaimRetentionPolicy: { whenScaled: Delete, whenDeleted: Retain } (GA since Kubernetes 1.32). Under the hood, Delete adds an ownerReference to the condemned pod so garbage collection cleans up the PVC once the pod exits; node-failure replacements don't count as scale events and keep their claims.

An expansion to 500Gi failed because the backend has no capacity and the PVC keeps retrying. Can you back out?

Yes - RecoverVolumeExpansionFailure has been GA since 1.34. Just lower the PVC request back down to anything above status.capacity (you still can't shrink below current size) and watch status.allocatedResourceStatuses and events. Before 1.34, you had to manually flip to Retain, delete the PVC, clear claimRef, and recreate it.

Restore a database volume from last night's snapshot into a new PVC. What does the manifest look like and what must be true first?

Create a PVC with dataSource: { kind: VolumeSnapshot, name: <snap>, apiGroup: snapshot.storage.k8s.io } in the same namespace, using a StorageClass from the same CSI driver and a size at least as large as the snapshot's restore size. Make sure the VolumeSnapshot shows status.readyToUse: true first, or the PVC will hang in Pending.

How do you change a volume's IOPS tier without recreating it?

Use a VolumeAttributesClass (GA since 1.34). Define the class with your driver's performance parameters, then update the mutable spec.volumeAttributesClassName field on the PVC and let the external-resizer apply it. Regular StorageClass parameters, by contrast, are locked at creation time.
