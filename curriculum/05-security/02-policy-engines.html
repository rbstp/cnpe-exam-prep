Three consequences to carry
  1. Validating policies inspect the object after mutation, so an earlier mutation can satisfy a check the developer never wrote (that's the LimitRange trap waiting in exercise 1).
  2. Admission only runs at write time. Tightening a policy never touches objects already sitting in etcd, so you need an audit or reporting sweep to catch existing offenders.
  3. Every external webhook becomes an availability dependency of the API server, and failurePolicy decides which way you fail when it breaks.

Kyverno has two dialects, and starting in 1.20 only one accepts writes. The current generation is CEL-based: ValidatingPolicy, MutatingPolicy, GeneratingPolicy, ImageValidatingPolicy, and DeletingPolicy, controlled by spec.validationActions: [Audit|Deny|Warn]. It arrived in Kyverno 1.14/1.15 and is what this lab installs and exercises. The classic generation is ClusterPolicy/Policy: typed rules (validate, mutate, generate, verifyImages) with match/exclude blocks and a JMESPath-flavored pattern syntax, toggled with spec.validationFailureAction: Audit|Enforce.

Kyverno 1.20 still serves the classic API for read, list, and delete, but blocks creates and updates and no longer runs it. You'll still see classic manifests on older clusters and across most online examples, so know how to read both, and let kubectl api-resources | grep kyverno, kubectl explain, and the cluster's response to a write tell you which one you're facing. The lab's examples/kyverno/ pair uses the CEL dialect: require-resources.yaml checks that every container declares resource requests (starting in Audit mode; flip it to Deny to enforce), and add-tenant-label.yaml mutates a cost-centre label onto Deployments at admission.

Gatekeeper separates policy logic from policy instances on purpose: a ConstraintTemplate defines a parameterized Rego policy and generates a CRD, and each Constraint is an instance of that CRD binding the rule to specific resources and parameters. That split makes reusable libraries easy to share, which is why gatekeeper-library exists. In practice, whenever an exam prompt mentions "OPA", it means Rego inside Gatekeeper templates.

ValidatingAdmissionPolicy is Kubernetes-native: pure CEL, no extra controller to install, no webhook to keep healthy, paired with a Binding that sets scope and enforcement action. It's worth practicing at least once because both third-party engines increasingly compile down to it, and an exam task can hand it to you directly.

Audit → report → fix → enforce

Rolling out policy in stages beats "just apply it" every time on scenario questions: deploy in Audit mode first, inspect the reports to find every existing offender, fix or explicitly exempt them, and only then flip to Deny. Kyverno's PolicyReports and Gatekeeper's audit violations exist specifically for that middle step, mirroring PSS's warn/audit before enforce pattern in 5.3.

CEL-based policy fields

  • spec.matchConstraints (resourceRules[].apiGroups/apiVersions/operations/resources, plus namespaceSelector and objectSelector) and spec.matchConditions (CEL pre-filters) mirror Kubernetes' native VAP API directly. spec.variables define reusable CEL expressions once, and spec.validations[] hold expression alongside message or messageExpression.
  • spec.validationActions takes a list of Deny, Audit, or Warn (the lab patches ["Audit"] to ["Deny"]). spec.failurePolicy accepts Fail (default) or Ignore and governs evaluation errors and webhook timeouts.
  • spec.evaluation toggles admission.enabled and background.enabled independently (turning admission off makes a policy report-only), and mode: JSON lets the CLI evaluate the same policy against a Terraform plan or any arbitrary JSON payload.
  • spec.webhookConfiguration.timeoutSeconds defaults to 10 (range 1–30); Kyverno propagates it directly into the generated ValidatingWebhookConfiguration.
  • spec.autogen: setting podControllers.controllers: [deployments, statefulsets, ...] rewrites a Pod rule so it also validates pod templates at admission (the exact fix for "my policy only blocks bare pods, not Deployments"). Setting validatingAdmissionPolicy.enabled: true compiles the policy into a native VAP so the API server enforces it in-process. Keep in mind those two options are mutually exclusive: while pod-controller autogen is enabled, Kyverno skips VAP generation and logs why in the policy status.
  • Other CEL kinds: MutatingPolicy adds mutations[] with patchType: ApplyConfiguration (a server-side-apply partial object built in CEL) or JSONPatch, plus evaluation.mutateExisting.enabled to retrofit existing objects. GeneratingPolicy uses generate[].expression: generator.Apply(namespace, [objects]) or YAML template blocks, paired with evaluation.synchronize, generateExisting, and orphanDownstreamOnPolicyDelete. DeletingPolicy takes a cron schedule, conditions, and deletionPropagationPolicy.

Classic ClusterPolicy fields, still worth reading

Kyverno 1.20 won't execute these, but plenty of older clusters and reference docs still use them. Each rule pairs match.any[] / exclude.any[] (filtering by resources.kinds, namespaces, selector, and subjects) with one action: validate (pattern, anyPattern, deny.conditions, cel.expressions, podSecurity), mutate (patchStrategicMerge, patchesJson6902, targets for existing objects), generate (data or clone, synchronize), or verifyImages. Enforcement lives on each rule via validate.failureAction: Audit|Enforce (the older top-level spec.validationFailureAction, spec.webhookTimeoutSeconds, and spec.failurePolicy were deprecated in 1.13). Watch the default: it's Audit, so a copy-pasted sample policy won't block anything until you flip it. spec.background: true (default) drives background reports for existing objects, and pattern anchors work as follows: =(field) conditional, +(field) add if absent, X(field) negation, <(field) global, with wildcards "*" and "?*".

Exceptions, reports, CLI, and configuration

  • PolicyException (policies.kyverno.io/v1) pairs policyRefs[].name/kind with CEL matchConditions. It applies to both admission and background scans and shows up in reports as a skip naming the exception. Watch the controller flags: exceptions do nothing unless --enablePolicyException=true (Helm features.policyExceptions.enabled) is turned on. An optional --exceptionNamespace=<ns> (features.policyExceptions.namespace) confines where exceptions may live; without it, every exception prints a warning ("The exceptionNamespace flag is not set"). If an exemption task fails silently, check the enable flag first.
  • Reports. PolicyReport (namespaced) and ClusterPolicyReport (wgpolicyk8s.io/v1alpha2) are generated one per resource, carrying results[].result in pass|fail|warn|error|skip plus a summary. Both admission events and background scans feed them; --allowedResults=fail (1.17+) stores only failures to keep etcd lean. Note that enforced (Deny) rejections don't show up in PolicyReports because the rejected object never existed in etcd.
  • CLI. kyverno apply policy.yaml --resource pod.yaml (or --cluster) prints pass/fail per rule, and adding -o out/ dumps mutated manifests. kyverno test . executes a kyverno-test.yaml asserting expected results[].result per rule and resource, which is how you unit-test policies in CI. On 1.20, the CLI refuses to load classic policy kinds (failed to load file, quoting the webhook's removal message); 1.19 warns instead, failing if --warnings-as-errors is set.
  • Configuration. In the kyverno ConfigMap, resourceFilters ([Kind,namespace,name] triples, wildcards allowed) exclude resources from admission. excludeGroups defaults to system:serviceaccounts:kube-system,system:nodes and excludeUsernames to !system:kube-scheduler. Kyverno's own namespace is excluded by default, while kube-system isn't. The two critical webhooks are kyverno-resource-validating-webhook-cfg and kyverno-resource-mutating-webhook-cfg: if the admission controller dies and freezes cluster writes, deleting those webhook configs is the documented emergency break-glass (Kyverno recreates them on recovery), and --forceFailurePolicyIgnore switches every generated webhook to Ignore.

Gatekeeper and the native policies, field by field

constraints, mutation, audit, VAP and MAP, the decision table

Gatekeeper

  • ConstraintTemplate (templates.gatekeeper.sh/v1): spec.crd.spec.names.kind names the generated Constraint kind (like K8sRequiredLabels), spec.crd.spec.validation.openAPIV3Schema schemas its parameters, and spec.targets[].target: admission.k8s.gatekeeper.sh carries the logic. That logic is either rego with a violation[{"msg": msg, "details": {...}}] rule over input.review.object and input.parameters, or code[].engine: K8sNativeValidation with CEL validations (plus generateVAP: true to emit a native ValidatingAdmissionPolicy). If a template includes both engines, CEL takes precedence and Rego is ignored.
  • Constraint (constraints.gatekeeper.sh/v1beta1, using the template's generated kind): scope it with spec.match (kinds[].apiGroups/kinds, scope: Cluster|Namespaced|*, namespaces/excludedNamespaces supporting prefix globs like kube-*, labelSelector, namespaceSelector) and pass inputs via spec.parameters. Set spec.enforcementAction to deny (default), warn, dryrun, or scoped with scopedEnforcementActions[] picking an action per enforcement point (validation.gatekeeper.sh for the webhook, audit.gatekeeper.sh, gator.gatekeeper.sh for shift-left CI, and vap.k8s.io). The audit loop updates status.totalViolations and status.violations[] (capped at 20 by --constraint-violations-limit) every --audit-interval (60s).
  • Mutation (mutations.gatekeeper.sh/v1): four kinds handle different targets: Assign (any field under spec, like location: "spec.containers[name: *].imagePullPolicy" with parameters.assign.value and optional pathTests using MustExist/MustNotExist), AssignMetadata (labels and annotations only, optionally copying fromMetadata namespace or name), ModifySet (add or prune list items), and AssignImage (assignDomain, assignPath, assignTag). Everything except AssignMetadata requires applyTo with explicit groups, kinds, and versions (no globs). Mutations only run on CREATE and UPDATE when the mutating webhook is enabled (--operation=mutation-webhook).
  • Referential rules and expansion. Rego policies that inspect other cluster objects (data.inventory) need those kinds cached via a SyncSet (or Config.spec.sync.syncOnly). An ExpansionTemplate lets pod-level policies validate Deployments by expanding spec.template into a synthetic Pod at admission. For external lookups, a Provider (externaldata.gatekeeper.sh) points at an in-cluster service queried via external_data({"provider": ..., "keys": [...]}), which is how Ratify and the cosign provider handle image signature verification.
  • Operations. Gatekeeper installs with failurePolicy: Ignore by default (fail open). Flipping to Fail is a deliberate hardening step, typically paired with a tight timeoutSeconds and the admission.gatekeeper.sh/ignore namespace label for exemptions. In CI, gator test -f manifests/ -f policies/ checks manifests offline and exits 1 on violations, while gator verify runs a Suite of unit tests. Warnings show up in kubectl as Warning: [constraint-name] message.

Webhook mechanics every engine shares

Every ValidatingWebhookConfiguration and MutatingWebhookConfiguration is driven by the same core fields: rules[] (operations, groups, versions, resources, scope), clientConfig (a Service plus caBundle, or a URL), failurePolicy (API default is Fail; Gatekeeper ships Ignore, Kyverno ships Fail), timeoutSeconds (default 10, range 1–30), sideEffects (must be None or NoneOnDryRun to run during --dry-run=server), CEL matchConditions (GA in 1.30), and namespaceSelector / objectSelector. Mutating webhooks also support reinvocationPolicy: IfNeeded so an earlier mutator can re-run if a later one changes the object, and matchPolicy: Equivalent ensures a rule matching apps/v1 also catches apps/v1beta1. Remember the ordering guarantee: mutating webhooks always run before validating ones (in an order you don't control), and validating webhooks always see the mutated result.

How this gets tested

Kyverno and Gatekeeper show up in separate tasks, so the choice is usually made for you; the real test is writing the right fields in whichever dialect is named. In Kyverno, check validationActions or failureAction first, because copied samples default to audit. In Gatekeeper, check enforcementAction and make sure the Constraint's kinds actually match what you're testing. For either engine, verify the denial using both the apply error text and the report or violation count, and don't forget the tenant-namespace LimitRange trap from exercise 1.

Operating policy safely

failurePolicy, exemptions, and the blast radius
  • failurePolicy. Fail blocks writes whenever the webhook is unreachable: strong security, but capable of freezing the whole cluster if your policy pods crash. Ignore lets writes through unchecked: high availability, with a bypass window during outages. Neither is universally right; it's a deliberate risk trade-off you bound with tight timeoutSeconds and a well-scoped namespaceSelector.
  • Scope your webhooks. rules (resources and operations), namespaceSelector, and objectSelector define your interception surface. Exempting kube-system is standard practice, and it's also a governance decision: it means cluster admins have an unpoliced lane.
  • Latency. Every intercepted write pays a network round trip. Broad */* wildcard rules are how an overly eager policy engine turns into a cluster-wide API slowdown.
  • Order. Mutating webhooks run in an order you don't fully control and can fire more than once under reinvocation policies, so every mutation must be idempotent.
  • Where the message goes. Your denial message lands verbatim in the developer's kubectl apply error. Write messages a stranger can act on immediately: state what failed and how to fix it.

Gatekeeper can mutate objects on the way in, and which kind you pick decides whether it stomps on values a developer set intentionally. AssignMetadata only fills in a label when it's missing, whereas Assign needs a pathTests guard to avoid overwriting. Self-check

answer before opening
A "require requests" policy never fires in a tenant namespace. Why?

The namespace's LimitRange injects default requests during mutating admission, before validating webhooks execute, so the pod Kyverno sees already complies. Admission ordering (mutate first, then validate) explains this completely, and it applies to every defaulting mechanism.

failurePolicy: Fail versus Ignore: argue both, then say what bounds the risk.

Fail prevents unvalidated writes from sneaking past, at the cost of blocking cluster writes if the webhook goes down (a policy outage becomes a cluster outage). Ignore keeps deployments moving during an outage, at the cost of a policy bypass window. Bound the blast radius with a tight namespaceSelector, low timeoutSeconds, system-namespace exemptions, and enough controller replicas that the webhook isn't a single point of failure.

You tighten a policy to Deny. What happens to the workloads that already violate it?

Nothing right away, because admission only checks writes. Existing pods keep running until their next write (a rollout, scale event, or node eviction), and then fail unexpectedly, often at 3 a.m. That's why you follow Audit → report → fix → Enforce and clear the reports before flipping the dial.

Which engine would you pick to also create a default NetworkPolicy in every new namespace?

Kyverno. Resource generation is first-class there: a GeneratingPolicy (or a classic generate rule on older clusters) creates downstream objects and keeps them synced. Gatekeeper validates and mutates but doesn't generate, and ValidatingAdmissionPolicy only validates. Match the engine's capabilities to the requirement.

Why might a platform team prefer ValidatingAdmissionPolicy for a simple rule?

Zero extra controllers, zero webhooks, zero availability dependencies, and no version skew: the API server runs CEL right in-process. The trade-off is a narrower feature set (no generation, no built-in reports, and no mutation on older Kubernetes releases), making it ideal for crisp invariants rather than a full governance suite.

A Kyverno ValidatingPolicy denies bare pods but a Deployment with the same violating template is admitted. Field?

Set spec.autogen.podControllers.controllers to include deployments (along with statefulsets, daemonsets, jobs, and cronjobs as needed). Autogen rewrites your Pod rule to validate controller spec.template blocks directly. Without it, the Deployment gets admitted and its pods fail silently one layer down on the ReplicaSet (the same indirection as PSS). Remember that pod-controller autogen and autogen.validatingAdmissionPolicy are mutually exclusive.

Which Kyverno controller flag must be on before a PolicyException has any effect, and how does the report show an applied exception?

Only --enablePolicyException=true is mandatory. The companion flag, --exceptionNamespace=<namespace>, is optional: when set, only exceptions inside that namespace take effect; when omitted (as in this lab), exceptions work from any namespace while emitting a warning ("The exceptionNamespace flag is not set") on creation. When an exception matches, the PolicyReport logs the rule as skip with the exception's name in its result properties across both admission and background scans.

A Gatekeeper Constraint is applied, the violating object is still admitted, and status.totalViolations grows. Two likely settings?

Either the Constraint has spec.enforcementAction: dryrun (or warn), or the Gatekeeper webhook is running with failurePolicy: Ignore (its install default) while the webhook pod is unhealthy or timing out. In both cases, the audit loop still scans and bumps the violation count even though admission never blocks. Switch the Constraint to deny and inspect the webhook's failurePolicy and timeoutSeconds.

You write a ValidatingAdmissionPolicy with a misspelt field path. Is it rejected? Where do you find out, and what decides the runtime effect?

No, Kubernetes accepts it. CEL type errors show up afterward in status.typeChecking rather than as an apply error. At runtime, evaluating the bad field path throws an error, and failurePolicy decides what happens next: Fail blocks every matching write (per the binding's validationActions), while Ignore lets them slip through. Inspect status.typeChecking, then fix the path.
