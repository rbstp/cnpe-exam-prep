The chain, station by station

scan · sign · verify

Scanning belongs at two points, and the difference is the insight

In the pipeline (a Trivy step with --exit-code 1 --severity HIGH,CRITICAL), scanning acts as a gate: it stops a vulnerable image before it ever reaches the registry. In the cluster (Trivy Operator, section 5.4), scanning acts as surveillance: it catches brand-new CVEs disclosed after you shipped. Teams that only scan in CI are completely blind to every vulnerability published since their last deploy. Calling out both roles cleanly is a high-value exam answer.

Gate ergonomics matter just as much, because a noisy gate that breaks every build will get turned off. Filter to HIGH,CRITICAL and consider --ignore-unfixed (nobody can patch a CVE that has no fix yet). Track exceptions in an auditable ignore file with expiry dates instead of permanently lowering the bar, and make findings fail the step rather than warn: a warning in CI logs is a warning nobody reads.

Signing

cosign signs an image's digest and pushes that signature into the registry beside the image (classically as a sha256-<digest>.sig tag, or in newer versions as an OCI bundle). Signing the digest rather than the tag is what makes the trust real: tags can be moved anytime, whereas digests are content-addressed. Verifying :latest resolves it to a digest first, so someone who hijacks a tag still can't forge the signature.

Keyless mode is where modern supply chains are heading: an OIDC workload identity (like a CI job token) requests a short-lived cert from Fulcio, and both the signature and cert get written into Rekor, a public transparency log. Verifiers check the signer's identity and the log entry instead of juggling static keys you have to store and rotate. Know those three nouns cold. Meanwhile, key-pair mode works completely offline and is the best way to practice the mechanics hands-on.

Verification at admission is what makes signatures matter

Without enforcement at the door, signing is pure theater. A Kyverno image-verification policy holds your public key (or expected keyless identity), intercepts pod creation, resolves each image reference, verifies its signature, and rejects anything untrusted. Even better, it can mutate the pod's image reference into its pinned digest so the kubelet pulls the exact bytes you verified instead of whatever that mutable tag points to five minutes later. Gatekeeper handles this through external data providers (like Ratify), whereas Kyverno builds it right in.

SLSA, since the word appears everywhere

SLSA defines levels of build provenance rigor, scaling from "we have a repeatable build" up to isolated, hermetic, attested builds. For the exam, keep the three supply-chain documents razor-sharp: provenance attests to how an artifact was built, SBOMs list what's inside it, and signatures prove who vouches for it. Three documents, one trust story; because attestations are themselves signed statements, cosign handles all three.

cosign flags you'll actually type

  • Key-pair mode. Mint keys with cosign generate-key-pair (or use --kms awskms://..., gcpkms://, azurekms://, hashivault://, or k8s://ns/secret to keep private keys off disk). Sign with cosign sign --key cosign.key <image@sha256:...> and check with cosign verify --key cosign.pub <image>. A passing run prints Verified OK along with the claims lines (The cosign claims were validated, The signatures were verified against the specified public key) and the payload JSON; tags resolve to a digest first and verify against docker-manifest-digest.
  • Keyless mode. Run cosign sign <image> with an OIDC login or CI identity token (--identity-token, using GitHub Actions' id-token: write permission) to grab a short-lived Fulcio cert and log to Rekor. Verification always requires pinning who signed it: pass --certificate-identity <subject> --certificate-oidc-issuer <issuer URL> (or the -regexp variants for a workflow URL like https://github.com/org/repo/.github/workflows/build.yaml@refs/heads/main with issuer https://token.actions.githubusercontent.com). Leave off the identity flags and cosign refuses to run, which is exactly how it prevents "signed by any random stranger" mistakes.
  • Offline and private setups. Pass --insecure-ignore-tlog to skip Rekor checks when you signed with --tlog-upload=false, --offline when verifying a local bundle, --certificate-chain or --ca-roots for a private Fulcio, and --rekor-url for a private Rekor. Add custom annotations at sign time via -a key=value and require them with the same flag at verify time.
  • Attestations. Attach predicates via cosign attest --predicate file --type slsaprovenance1|spdxjson|cyclonedx|vuln|custom --key ... <image>, and verify with cosign verify-attestation --type <type> --key ... <image> (add --policy policy.cue or Rego to enforce rules on predicate content, like max severity or builder ID). Inspect everything attached to an image with cosign tree <image>, and fetch payloads with cosign download attestation.
  • Storage formats. Signatures sit next to the image in the registry either in the legacy tag format (sha256-<digest>.sig and .att) or as an OCI 1.1 referrer bundle (cosign v3's default). A verifier expecting one format reports no signatures found on an image signed in the other. The lab's --new-bundle-format=false flag is that exact format mismatch in action.

trivy gate flags

  • --severity HIGH,CRITICAL filters findings; --exit-code 1 actually fails the build (Trivy exits 0 by default even when it finds CVEs!); --ignore-unfixed expands to --ignore-status affected,will_not_fix,fix_deferred,end_of_life; --scanners vuln,secret,misconfig,license selects scanners (secret scanning runs by default on images and slows down big scans); and --pkg-types os,library narrows package types.
  • .trivyignore lists one CVE ID per line with optional expiry dates like exp:2026-12-31; .trivyignore.yaml (passed via --ignorefile) organizes vulnerabilities, misconfigurations, secrets, and licenses with statements; --ignore-policy policy.rego filters with OPA (package trivy, rule ignore); and --vex applies VEX documents. Expiry dates are what keep ignore lists auditable instead of permanent blind spots.
  • Pipeline outputs: --format json|sarif|cyclonedx|spdx-json|template --output file. Remember the subcommands too: trivy image --format cyclonedx emits an SBOM, trivy sbom rescans an SBOM later, trivy k8s scans a live cluster, and trivy config / trivy fs scan manifests and repos.

Hygiene that admission cannot give you

Pin base images by digest (FROM alpine@sha256:...) and let Dependabot or Renovate bump them; use distroless or Chainguard bases so scanners find fewer CVEs and attackers find no shell; use multi-stage builds so compilers never ship; lock down registries with immutable tags, pull-through caches, and allow-lists enforced by policy on image prefixes; and commit verified dependency lockfiles. On the repository side, OpenSSF Scorecard scores these habits under named checks: Pinned-Dependencies, Token-Permissions, Branch-Protection, Signed-Releases, SBOM, Dangerous-Workflow, Vulnerabilities, and Code-Review. Whenever an exam prompt asks for pipeline controls beyond image scanning, reach straight for this checklist.

SLSA v1.0 defines the Build track, with later versions adding Source and build-environment tracks on the same model. Provenance takes the form of an in-toto Statement with predicateType: https://slsa.dev/provenance/v1 carrying buildDefinition (buildType, externalParameters, resolvedDependencies) and runDetails (builder.id, metadata). Verifying provenance means checking three things: the signature is valid, builder.id matches a builder you trust, and the source repo in externalParameters matches what you expect.

Tekton Chains

Tekton Chains watches finished TaskRuns and PipelineRuns, then formats, signs, and publishes provenance automatically. All settings live in the chains-config ConfigMap inside tekton-chains:

  • artifacts.taskrun.format / artifacts.pipelinerun.format: choose in-toto (alias slsa/v1, emitting SLSA v0.2) or slsa/v2alpha3 / slsa/v2alpha4 (SLSA v1.0; v2alpha4 also reads type-hinted results from StepActions). New deployments should use slsa/v2alpha3 or newer.
  • artifacts.*.storage: comma-separated targets from tekton (stored as annotations on the run), oci (attestations beside the image), gcs, docdb, grafeas, or archivista. Setting artifacts.oci.storage: oci is what lets cosign verify-attestation find anything on the image.
  • artifacts.*.signer: x509 (a cosign.key inside the signing-secrets Secret, or keyless via signers.x509.fulcio.enabled: true), kms (signers.kms.kmsref), or none (unsigned provenance).
  • transparency.enabled: true uploads to Rekor (transparency.url), while manual uploads only runs annotated with chains.tekton.dev/transparency-upload: "true".
  • Type hinting is how Chains recognizes what your Task built: emit results named IMAGE_URL and IMAGE_DIGEST (or *_IMAGE_URL / *_IMAGE_DIGEST pairs, or an *ARTIFACT_OUTPUTS object with uri and digest). Here's the gotcha: if a Task pushes an image without emitting those results, Chains writes zero OCI attestations yet still stamps chains.tekton.dev/signed: "true" because it signed the run payload itself. Check that annotation first when "Chains didn't sign my image", then check controller logs for missing results or registry auth errors. Turn on artifacts.pipelinerun.enable-deep-inspection: "true" so PipelineRun-level provenance pulls in task-level results too.

Digest pinning closes the final TOCTOU gap: verify the digest, then run that exact digest. If a Deployment still says :v1 after admission, whoever can overwrite that tag still controls what runs.

How this gets tested

"Sign this image and block unsigned ones in the cluster" means cosign plus one of the three policies above, matching the in-cluster registry name pods use (plus the engine's insecure-registry flag if the lab registry is HTTP). "Generate provenance for this pipeline" means configuring Chains plus emitting IMAGE_URL/IMAGE_DIGEST results from the Task. "Fail the build on CRITICAL CVEs without breaking on unfixable ones" means --severity CRITICAL --exit-code 1 --ignore-unfixed paired with a dated ignore file. Graders verify the artifact itself (a valid signature, a downloadable attestation, a blocked pod), so always prove the end state.

Kyverno's current kind for image verification is ImageValidatingPolicy (run kubectl explain imagevalidatingpolicies.spec; this API has evolved, and checking live is part of the habit). Three practical details make or break the setup:

  1. Kyverno pulls signatures itself from inside the cluster, so both your pod images and policy globs must use the in-cluster registry hostname (kind-registry:5000, wired into CoreDNS and containerd), never localhost:5001 (inside the Kyverno pod, localhost is Kyverno itself).

  3. cosign v3 defaults to its new OCI bundle format, while Kyverno's verifier currently looks for the legacy .sig tag. Sign a second time in legacy format for Kyverno: cosign sign --key cosign.key --allow-http-registry -y --use-signing-config=false --new-bundle-format=false --tlog-upload=false localhost:5001/demo@$DIGEST. Because tags are mutable pointers, verifying a tag at admission and letting the kubelet pull that tag later creates a race window. Setting mutateDigest tells Kyverno to rewrite the pod spec straight to the verified digest, closing the gap inside the object itself. In an ImageValidatingPolicy, it lives under validationConfigurations and defaults to true (older docs show mutateDigest: true on a classic verifyImages rule, which Kyverno 1.20 refuses).

Self-check

answer before opening
Why scan in the pipeline and in the cluster?

The pipeline gate blocks known vulnerabilities before an image ever hits the registry, but it can't predict CVEs disclosed tomorrow. Continuous in-cluster scanning catches those new CVEs on images already running. CI-only leaves you blind to everything newer than your last deploy; cluster-only lets vulnerable images ship in the first place.

Why is signing by digest, not by tag, the point?

A digest uniquely identifies exact image bytes, whereas a tag is just a mutable label. Signing the digest binds the signature to those specific bytes so nobody moving the tag can forge it. Verification resolves any tag to its digest first, and a hardened admission policy rewrites the pod spec to that pinned digest so runtime can never drift from what was checked.

Signatures exist and someone still deployed an unsigned image. What was missing?

Admission-time verification. Without an enforcement point checking signatures at the door, signing is just decoration. Deploy an image-verification policy matching your registry glob in Deny mode, and double-check that its glob matches the exact in-cluster reference format pods actually use.

Kyverno reports "no signatures found" for an image you definitely signed. Three candidates?

Check three usual suspects: registry reachability and hostname (Kyverno resolves from inside the cluster, so localhost won't reach your registry), HTTP vs HTTPS scheme (plain HTTP requires the engine's insecure-registry flag), and signature format skew (a cosign v3 bundle where the verifier expects the legacy .sig tag). Also check Rekor transparency-log settings if you signed with --tlog-upload=false.

Distinguish SBOM, provenance and signature in one sentence each.

SBOM: what components and versions are inside the artifact. Provenance: how, where, and from what source it was built (a SLSA-style attestation). Signature: who cryptographically vouches for these exact bytes. Together they form one trust story, and both SBOMs and provenance are typically stored as signed attestations.

Keyless verification: which two flags are mandatory, and what does each pin?

--certificate-identity (or --certificate-identity-regexp) pins the SAN inside the Fulcio cert (a signer's email, or a CI workflow URI like https://github.com/org/repo/.github/workflows/build.yaml@refs/heads/main). --certificate-oidc-issuer pins the OIDC provider that authenticated them (like https://token.actions.githubusercontent.com). Without both, any Fulcio-issued cert from anywhere would pass, which is why cosign refuses to run without them.

Tekton Chains signs the TaskRun (annotation chains.tekton.dev/signed: "true") but cosign verify-attestation on the image finds nothing. Two configuration causes?

Either the Task didn't emit type-hinted results (IMAGE_URL and IMAGE_DIGEST, or *ARTIFACT_OUTPUTS) so Chains didn't know an OCI image was produced, or artifacts.taskrun.storage / artifacts.oci.storage omitted oci so provenance only went to the tekton backend (run annotations). Inspect the TaskRun's results, the chains-config ConfigMap, and the Chains controller logs.

What distinguishes SLSA Build L2 from L3, and which one does a signed provenance from a shared CI runner reach?

L2 requires a hosted build platform to generate and sign provenance using a platform-held key users can't touch. L3 goes further: builds must be isolated from each other and from user-controlled steps so a run can neither tamper with its own provenance nor access signing material. A shared runner where jobs can inspect each other's state or credentials tops out at L2; L3 requires ephemeral isolated builders with signing handled strictly outside the build step (like Tekton Chains signing from its own controller rather than inside the Task).

A Kyverno ImageValidatingPolicy fails on a private-registry image with an authentication error, although the pod's imagePullSecrets work. Why?

ImageValidatingPolicy doesn't read the pod's imagePullSecrets and ignores the global registry credential helper flag. You have to supply registry credentials explicitly on the policy itself via spec.credentials.secrets (Secrets in Kyverno's namespace) or credentials.providers for cloud ambient auth. Because Kyverno pulls signatures from its own pod, networking, TLS scheme (allowInsecureRegistry), and auth are all evaluated from Kyverno's side.
