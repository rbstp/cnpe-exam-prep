Orientation

competency 5.2 · RBAC and security controls

Every Forbidden error you'll ever hit (inside a workflow node, an operator log, a CI job, or an exam task) breaks down into the same four pieces: subject, verb, resource, and namespace. Learn to read that error line cleanly and half this domain answers itself.

Authorization in three sentences

A request arrives authenticated as a subject with a set of groups. Every RBAC rule is strictly an allow; there is no deny rule anywhere in Kubernetes RBAC. Your effective permissions are simply the union of every matching rule, and anything not matched is forbidden. That's why debugging RBAC is always "find the missing rule or missing binding", never "find what blocked me".

The RBAC model

roles · bindings · subjects · verbs

The asymmetry exams love

A RoleBinding can reference a ClusterRole, granting its rules inside that one namespace only. That's how you define a "developer" role once and bind it per tenant. A ClusterRoleBinding grants access everywhere and is almost always the wrong default. Whenever a task's final check says "and they must not have access in another namespace", that check is specifically hunting for a ClusterRoleBinding.

Four combinations of role and binding, and where each one grants access:

Subjects

Users and Groups are asserted by your authentication layer (client certificates, OIDC claims, proxy headers) rather than stored as API objects. That's why you can bind to dev-a even though no dev-a object exists in the cluster, and why --as=dev-a works out of the box for testing. ServiceAccounts are real objects, and they're how software gets identity: system:serviceaccount:<ns>:<name>, automatically placed in group system:serviceaccounts:<ns>. Every controller log yelling Forbidden traces back to a ServiceAccount missing a rule.

Modern ServiceAccount tokens are short-lived, audience-bound, and mounted as projected volumes instead of the old forever-Secrets. That same identity also underpins workload identity (section 5.5's SPIFFE IDs are built right from the SA name). Setting automountServiceAccountToken: false on pods that never talk to the API server is a cheap, meaningful hardening win.

Verbs and rules, the details that decide tasks

  • get, list, and watch are separate verbs. A dashboard listing pods needs list, and a controller needs watch too. Granting only get and wondering why kubectl get pods (plural) fails is a classic trap.
  • Subresources have their own resource strings: pods/exec, pods/log, pods/portforward, deployments/scale, */status. Allowing log reads while blocking exec is easy to express and makes a great tenant default.
  • resourceNames narrows a rule to specific named objects, which is how you allow editing a single ConfigMap. Keep in mind it can't restrict create or deletecollection, and a plain list or watch only succeeds if paired with a matching metadata.name field selector.
  • Wildcards (*) exist, and least privilege says to avoid them. escalate and bind are special verbs that let someone grant permissions they don't hold themselves; treat both as admin-only.
  • Aggregated ClusterRoles (aggregationRule with label selectors) let the built-in view, edit, and admin roles absorb new CRDs automatically. Label your ClusterRole rbac.authorization.k8s.io/aggregate-to-view: "true" and every viewer immediately gets read access to your new kind. That's the right platform-engineering move whenever you ship a CRD.
  • Built-in roles to know by heart: view (read-only, no Secrets), edit (read/write, no RBAC), admin (edit plus managing RBAC in that namespace), and cluster-admin (everything).

RBAC edges that decide tasks

special verbs, identity checks, tokens, OIDC groups

Verbs and rules people get wrong

  • Escalation prevention. You can only create or update a Role if you already hold every permission it grants, or hold the escalate verb on roles/clusterroles. Similarly, you can only create a binding if you hold those permissions or hold the bind verb on that role (optionally narrowed with resourceNames). Otherwise you get attempt to grant extra privileges. A tenant admin who "cannot bind the view role" needs bind on that one ClusterRole, not cluster-admin.
  • impersonate on users, groups, serviceaccounts (and userextras) powers kubectl --as and --as-group. Only cluster-admin holds it by default, so a tenant who wants to test their own SA with --as needs it granted explicitly.
  • kubectl auth whoami (the SelfSubjectReview API) prints the exact username, UID, groups, and extra attributes the API server sees after authentication. Reach for it first whenever an OIDC user or workload gets Forbidden and you aren't sure what identity actually arrived: prefixes, group names, and impersonation all show up right there.
  • nonResourceURLs (/metrics, /healthz, /logs/*) only work in ClusterRoles. A scraper hitting the API server's /metrics needs get on that URL, and wildcards act as suffix globs.
  • Default ClusterRoles. view reads most namespaced objects, excluding Secrets, Roles, and RoleBindings. edit adds writes, and less obviously, lets you read and write Secrets and launch pods as any ServiceAccount in the namespace, which makes it too broad for many developers. admin adds Role and RoleBinding management inside that namespace, and cluster-admin unlocks everything. All four aggregate labeled roles (rbac.authorization.k8s.io/aggregate-to-view|edit|admin). Meanwhile, system:authenticated inherits system:basic-user and system:discovery; if system:unauthenticated can read discovery, check for the system:public-info-viewer binding.
  • Auto-reconciliation. Built-in roles and bindings reset on API server restart unless annotated with rbac.authorization.kubernetes.io/autoupdate: "false". Any direct edit to view gets overwritten, which is why aggregation exists. Run kubectl auth reconcile -f rbac.yaml to apply RBAC manifests additively and see what changed.
  • kubectl create role shortcuts. Use --verb=get,list --resource=pods,pods/log, --resource=deployments.apps for group-qualified resources, --resource-name=x for named objects, and kubectl create clusterrole --aggregation-rule=.... Generating and inspecting the YAML beats writing it from scratch under exam pressure.

Identity mechanics

  • Tokens. Pods receive a projected token (serviceAccountToken with expirationSeconds and audience) that the kubelet refreshes via the TokenRequest API; it's bound to that pod and dies with it. Use kubectl create token <sa> --duration=1h to mint one for scripts, or add --bound-object-kind Pod --bound-object-name x to bind it to an object. Long-lived Secret tokens stopped being auto-created in 1.24 and get cleaned up when unused. If a task says "the CI system needs a token", reach for kubectl create token, and only create an explicit kubernetes.io/service-account-token Secret if a non-expiring token is genuinely required. Set automountServiceAccountToken: false on the pod or SA to drop the mount completely.
  • OIDC. Legacy flags are --oidc-issuer-url, --oidc-client-id, --oidc-username-claim (default sub), --oidc-username-prefix, --oidc-groups-claim, and --oidc-groups-prefix. The modern structured form is an AuthenticationConfiguration file passed via --authentication-config, supporting multiple issuers with jwt[].issuer.url/audiences, claimMappings.username.claim|prefix, claimMappings.groups.claim|prefix, and CEL claimValidationRules. Remember that groups arrive with their prefix attached (like oidc:platform-team), so binding to bare platform-team silently matches nobody; kubectl auth whoami reveals the exact string.
  • Built-in groups you get for free. system:serviceaccounts (every SA), system:serviceaccounts:<ns> (one namespace), system:masters (bypasses RBAC entirely, so never put a real user in it), and system:nodes.
How this gets tested

Expect three flavors: "user X can do Y in namespace Z and nothing else", "the CI ServiceAccount can submit workflows and read their status", and "why does user X still get Forbidden when a binding exists?" (usually prefixes, group names, a Role in the wrong namespace, or resourceNames paired with list). Close every one with kubectl auth can-i --as and, for real identities, kubectl auth whoami.

Secrets: the controls half

and the three GitOps answers

A stock Kubernetes Secret is just base64, not encryption. Anyone who can get secrets in that namespace has the plaintext, and so does anyone with etcd access unless you've turned on encryption at rest on the API server (EncryptionConfiguration, optionally backed by a KMS). That gives you three non-negotiable habits: never hand out get secrets lightly, prefer short-lived projected tokens over static credentials, and never let a plain Secret near git.

ApproachWhat git holdsWho can decryptGood for
Sealed SecretsCiphertext (a SealedSecret CR)Only the in-cluster controller's private keySelf-contained clusters with no external secret store
External Secrets (ESO)A reference (SecretStore + ExternalSecret)Whoever the backing store authorizesEnvironments where Vault or a cloud secret manager is already the source of truth
SOPSPartially encrypted YAMLHolders of the age, PGP, or KMS keyFlux-native repos where reviewable diffs matter

Be ready to state the core distinction crisply: Sealed Secrets stores encrypted data in git, whereas ESO stores only pointers in git while the external store holds truth and handles rotation outside your repo. Both keep plaintext out of version control, but only ESO gives you centralized rotation and audit trails.

ESO's object model, since it's the one you're most likely to meet

  • SecretStore (namespaced) or ClusterSecretStore (cluster-wide, referenced with kind: ClusterSecretStore) defines where secrets live and how to authenticate: a provider block (vault, aws, gcp, azure, kubernetes, or fake for practice) plus credentials, typically a ServiceAccount token or Secret ref.
  • ExternalSecret defines what to materialize: secretStoreRef, a refreshInterval, and either explicit data[] mappings (remote key → local key) or dataFrom to pull a whole path. Use target.name to name the generated Secret, target.creationPolicy to control ownership, and target.template to assemble structured outputs like config files or connection strings instead of raw key-value pairs.
  • Check the SecretSynced status condition: when syncing fails, the message usually points straight to the store, a missing key, or an auth error, in that order of likelihood.
  • PushSecret reverses the flow for the rarer case where the cluster itself is the source of truth.

What the exam tests here mirrors the rest of this domain: inspect the CRD, wire the two objects together, and verify the materialized Secret itself rather than stopping at a green apply.

Sealed Secrets' sharp edge

Every sealed value is encrypted for one specific controller and (by default) one specific namespace and name. Rebuild the cluster without restoring that controller's private key and every SealedSecret in git turns into unreadable noise, so back up the sealing key like production data.

Secrets: the fields and formats

encryption at rest, ESO, Sealed Secrets, SOPS, CSI

Encryption at rest

Pass an EncryptionConfiguration (apiserver.config.k8s.io/v1) via --encryption-provider-config listing resources[] (such as secrets, configmaps, CRDs like externalsecrets.external-secrets.io, or wildcards like *.*) and an ordered providers[] list. The first provider encrypts new writes while all listed providers can decrypt, which dictates the rotation sequence: place the new key first, restart the API server, rewrite every object (kubectl get secrets -A -o json | kubectl replace -f -), and only then drop the old key. Available providers are identity (plaintext; the default if unconfigured), aescbc, aesgcm (must rotate every 200k writes), secretbox, and kms with apiVersion: v2 talking to an external KMS plugin over a Unix socket (v1 is deprecated). Wildcards require 1.27+ and custom resources 1.26+. Reading raw etcd shows prefixes like k8s:enc:aescbc:v1:key1: once encryption is active.

External Secrets Operator, the decisive fields

apiVersion: external-secrets.io/v1
kind: ExternalSecret
metadata: { name: db, namespace: team-a }
spec:
  secretStoreRef: { name: vault, kind: ClusterSecretStore }
  refreshPolicy: Periodic            # CreatedOnce | Periodic (default) | OnChange
  refreshInterval: 1h                # 0 means create once, never update
  target:
    name: db-credentials
    creationPolicy: Owner            # Owner | Orphan | Merge | None
    deletionPolicy: Retain           # Retain | Delete | Merge
    template:
      engineVersion: v2
      data:
        DSN: "postgres://{{ .username }}:{{ .password }}@db:5432/app"
  data:
    - secretKey: username
      remoteRef: { key: team-a/db, property: username }
  dataFrom:
    - extract: { key: team-a/db }    # every property becomes a key
  • refreshPolicy: Periodic syncs every refreshInterval and on spec edits; OnChange syncs only when the ExternalSecret itself changes; CreatedOnce fetches once per object (recreating the ExternalSecret triggers a fresh pull, so pair it with target.immutable: true for credentials nothing should overwrite in place). Need an immediate refresh? Run kubectl annotate es x force-sync=$(date +%s).
  • creationPolicy: Owner (ESO owns the Secret and deletes it with the ExternalSecret), Orphan (leaves it behind), Merge (injects keys into an existing Secret you own), or None (never creates a Secret). deletionPolicy controls what happens to the Secret if the remote key disappears.
  • dataFrom.extract unpacks an entire JSON object into keys, dataFrom.find matches by path regex or tags, and rewrite renames keys. template (engine v2, Go templates with Sprig) builds full config files and DSNs, templateFrom pulls templates from a ConfigMap, and mergePolicy: Merge keeps raw keys alongside the templated ones.
  • Scoping: SecretStore is namespaced, while ClusterSecretStore can restrict which namespaces may use it via conditions[].namespaceSelector or namespaces. ClusterExternalSecret stamps one ExternalSecret across every namespace matching namespaceSelectors, and PushSecret pushes cluster Secrets back to an external store with updatePolicy: Replace|IfNotExists.
  • Status: check the Ready condition for reason SecretSynced or SecretSyncedError; errors typically name the store, missing key, or auth issue in that order. The store itself carries its own Ready condition (Valid reason) that trips first when credentials are bad.

The other three tools, in fields

  • Sealed Secrets. Scope controls where a ciphertext can be decrypted: strict (the default, binding both name and namespace so renaming triggers a decryption error), namespace-wide (annotation sealedsecrets.bitnami.com/namespace-wide: "true", allowing any name inside that namespace), or cluster-wide (any namespace). Useful CLI flags: kubeseal --scope, --fetch-cert for offline sealing, --merge-into to append one key, and --raw for a single value. The controller rotates its sealing key every 30 days while retaining older keys so existing ciphertexts keep working; back up the sealed-secrets-key* Secrets in kube-system. Annotating an existing Secret with sealedsecrets.bitnami.com/managed: "true" lets a SealedSecret adopt it, and .../patch: "true" merges instead of overwriting.
  • SOPS with Flux. Create a .sops.yaml with creation_rules (path_regex, age/pgp/kms recipients, and encrypted_regex: ^(data|stringData)$ so metadata stays cleartext) and run sops --encrypt --in-place secret.yaml. Point your Flux Kustomization at it via spec.decryption: { provider: sops, secretRef: { name: sops-age } }, where that Secret holds the age key file (age.agekey) or GPG private key. kustomize-controller decrypts in memory at apply time, while git diffs stay readable because only values are encrypted.
  • Secrets Store CSI driver. Pair a SecretProviderClass (providers: vault, azure, aws, gcp) with a pod volume using csi.driver: secrets-store.csi.k8s.io and volumeAttributes.secretProviderClass. Secrets mount directly as files and never touch etcd unless you add secretObjects to mirror them into a Kubernetes Secret (for env vars). Turn on rotation with --enable-secret-rotation and --rotation-poll-interval on the driver. Choose CSI when "the secret must never exist in etcd"; choose ESO when workloads already expect standard Kubernetes Secrets.
Trap

list and watch on Secrets return the actual secret values, not just their names. A "read-only" role with those verbs hands over every secret in the namespace. Kubernetes best practice is to grant get on named Secrets via resourceNames and reserve list/watch for controllers that genuinely need them. That single distinction is a rock-solid exam answer on its own.

Self-check

answer before opening
Define "developer" once and grant it in twelve namespaces. What objects, and how many?

One ClusterRole plus twelve RoleBindings (one per namespace, each pointing its roleRef at that ClusterRole). Never a ClusterRoleBinding: that would grant permissions cluster-wide and fail any "not in another namespace" check.

A user can get a pod by name but kubectl get pods fails. Why?

list is a separate verb from get, and a rule scoped with resourceNames can't satisfy an unfiltered list. Add list (and watch if anything streams updates), knowing that list exposes every object of that kind in the namespace.

How do you let a tenant read pod logs but never exec into a pod?

Grant get on pods/log and withhold create on pods/exec. Because Kubernetes treats subresources as distinct resource strings, you can separate them cleanly.

You ship a new CRD. How do existing view users get read access without editing the built-in role?

Create a ClusterRole granting read verbs on your new kind and label it rbac.authorization.k8s.io/aggregate-to-view: "true". Role aggregation folds it straight into the built-in view role automatically, which is the standard platform move when shipping a CRD.

Sealed Secrets versus ESO: which would you pick for a regulated environment with an existing vault, and why?

Pick ESO. Your vault remains the single source of truth with its own audit trail and rotation policies, and git only ever stores references rather than secret material (even encrypted). Sealed Secrets fits self-contained clusters without an external store, at the cost of managing and backing up the sealing keys yourself.

Is a Kubernetes Secret encrypted?

Not by default: base64 is just encoding. At rest in etcd, Secrets are only encrypted if the API server has an EncryptionConfiguration (optionally backed by a KMS); in transit, TLS protects them. In practice, strict RBAC over who can read Secrets does most of the day-to-day protection.

A namespace admin with the built-in admin role cannot create a RoleBinding to a custom ClusterRole that grants nodes read. Why, and what is the least-privilege fix?

Escalation prevention: you can only bind permissions you already hold, and admin doesn't include cluster-scoped nodes. The least-privilege fix is granting the bind verb on clusterroles scoped via resourceNames to that exact ClusterRole. Handing out node read access directly or granting cluster-admin would work, and would fail least privilege.

An OIDC user in group platform-team is bound via a ClusterRoleBinding to that group and still gets Forbidden. First command, likely cause?

Run kubectl auth whoami to see the exact groups the API server receives. With --oidc-groups-prefix (or claimMappings.groups.prefix in structured config), the group arrives prefixed, like oidc:platform-team, so bind to that exact string. The same check also catches username prefixes and mismatched groups claim names.

You rotate the aescbc key in EncryptionConfiguration. Order of operations, and what happens if you simply replace the key?

Add the new key first in providers[] while keeping the old key second, restart the API servers, rewrite every Secret so it re-encrypts under the new key (kubectl get secrets -A -o json | kubectl replace -f -), and finally remove the old key. If you simply swap the key out, every existing Secret becomes unreadable, failing loudly on get secrets rather than at API server startup.

ESO: a database password rotates in Vault every hour, the ExternalSecret has refreshInterval: 0, and pods keep failing to log in. Two fixes and their trade-offs?

refreshInterval: 0 means "create once and never refresh", so the Secret stays frozen on the original password. Option one: set a refreshInterval shorter than the rotation window (with Periodic policy) and ensure pods pick up updates (via file mounts or a restart trigger like Reloader, since env vars don't reload). Option two: if running pods shouldn't see credentials shift underneath them, keep CreatedOnce with immutable: true and roll deployments intentionally on rotation.
