Audit trails and compliance reporting are called out explicitly in the exam blueprint, yet almost nobody practices them because home labs rarely turn on API audit logging. This lab turns it on right when the cluster is built, so you can query real events.

Orientation

competency 5.3 · audit trails and policy compliance

Three artifacts, three concrete questions. The audit log answers "who did what to what, and did it work?". SBOMs answer "what's actually inside the thing we shipped?". Compliance reports answer "which controls are we failing right now?". Being able to produce and query all three on demand is the competency.

API server audit logs

policy · levels · stages · the event schema

Here's how the pipeline works: a policy file tells kube-apiserver what to record and at what detail level, and a backend (a log file on the control-plane node here, or a webhook to a SIEM in production) writes one JSON event per stage of every matching request.

LevelRecordsUse for
NoneNothingHigh-volume noise: leases, events, health endpoints
MetadataWho, what, when, verb, and response codeThe sensible catch-all (and Secrets, so values stay out of logs)
RequestMetadata + the request bodyWrites where you want the input without redundant response bloat
RequestResponseMetadata + both request and response bodiesHigh-value changes only (RBAC, policy); output grows fast

Stages mark where in the request lifecycle the event fires: RequestReceived, ResponseStarted (for long-running streams like watches), ResponseComplete, and Panic. Almost all analysis filters on ResponseComplete. Policy rules match top to bottom, first hit wins (just like Alertmanager routes), so a well-structured policy always reads in three bands: drop noise first, elevate sensitive kinds next, and catch everything else at Metadata. Open kind/audit-policy.yaml in this repo and you'll see that exact layout.

FieldAnswers

One operational failure the repo already documents

The API server starts with --audit-policy-file pointing at a mounted file. If that file is missing or malformed, the API server refuses to start at all. An audit config typo therefore looks like a completely dead cluster, making it one of the nastiest control-plane failure modes in this curriculum.

What audit is and is not

Audit logging only sees Kubernetes API requests. It won't see a shell spawned inside a container, lateral network traffic between pods, or anything bypassing the API server. Pair it with Falco-style runtime detection, network flow logs (Hubble), and image scanning to cover the other layers, and say so explicitly whenever a scenario asks for a "complete audit trail".

Audit policy and backends, field by field

rule fields, ordering, the flags, what a good policy records

Rule fields

An audit Policy (audit.k8s.io/v1) consists of rules[] plus an optional top-level omitStages. Each rule sets a level and filters by any mix of users, userGroups, verbs, resources[] (each taking group, resources like pods or pods/exec, and optional resourceNames), namespaces, and nonResourceURLs (/healthz*, /metrics, /version), along with per-rule omitStages and omitManagedFields. Because Kubernetes evaluates rules top to bottom and stops on the first match, order them cleanly: drop noise, protect sensitive bodies, raise RBAC/policy diffs, then catch everything else.

apiVersion: audit.k8s.io/v1
kind: Policy
omitStages: [RequestReceived]          # one event per request, not two
rules:
- level: None                          # noise first
  users: ["system:kube-proxy"]
  verbs: ["watch"]
  resources: [{ group: "", resources: ["endpoints", "services", "endpointslices"] }]
- level: None
  nonResourceURLs: ["/healthz*", "/readyz*", "/livez*", "/metrics", "/version"]
- level: None
  resources: [{ group: "coordination.k8s.io", resources: ["leases"] }]
- level: Metadata                      # never the body: it holds the values
  resources: [{ group: "", resources: ["secrets", "configmaps"] },
              { group: "authentication.k8s.io", resources: ["tokenreviews"] }]
- level: Metadata
  resources: [{ group: "", resources: ["pods/exec", "pods/attach", "pods/portforward"] }]
- level: RequestResponse               # who changed access and policy, with the diff
  resources: [{ group: "rbac.authorization.k8s.io" },
              { group: "kyverno.io" }, { group: "policies.kyverno.io" },
              { group: "constraints.gatekeeper.sh" }, { group: "admissionregistration.k8s.io" }]
- level: Metadata                      # everything else
  omitStages: [RequestReceived]
  • Why those levels. Setting Request or RequestResponse on Secrets dumps plaintext credentials straight into your log files; keeping them at Metadata still tells you who accessed which Secret and whether they succeeded. Logging pods/exec at Metadata answers "who shelled into production?". Putting RBAC and policy kinds at RequestResponse captures the full diff for permissions changes, while Request fits busy writes (like Deployment updates) where the response body adds noise.
  • Stages. RequestReceived fires before authorization, so it catches requests before they're rejected; most policies omit it and inspect ResponseComplete instead, since that event already includes responseStatus.code. ResponseStarted only applies to streaming requests (watch, exec, port-forward), and Panic is rare. All events from a single request share the same auditID.
  • Extra fields you'll grep for: level, stage, requestURI, impersonatedUser (populated whenever --as was used, while user records the real caller), requestObject / responseObject at higher levels, and requestReceivedTimestamp. Adding omitManagedFields: true strips the verbose managedFields noise from both bodies.

Backends and their flags

FlagBackendMeans

On static-pod control planes (kubeadm, kind), remember to mount both the policy file and the log directory as hostPath volumes on kube-apiserver; forgetting a mount triggers the dead-cluster failure above. On managed Kubernetes, you don't touch these flags at all: you consume the cloud provider's audit stream, so exam questions there pivot to "what do you query for?".

Annotations other controls leave in the audit event

  • authorization.k8s.io/decision and authorization.k8s.io/reason: RBAC's verdict and the exact rule that matched.
  • pod-security.kubernetes.io/audit-violations: findings recorded by a namespace's PSS audit label, per pod.
  • validation.policy.admission.k8s.io/validation_failure: failures from a ValidatingAdmissionPolicyBinding with validationActions: [Audit], alongside any custom keys from the policy's auditAnnotations.
  • mutation.webhook.admission.k8s.io/round_0_index_N and patch.webhook.admission.k8s.io/...: which mutating webhooks modified the object and what they patched (recorded at level Request or higher).
How this gets tested

Expect two task styles. Writing or fixing a policy: "log who reads Secrets without recording their values, and drop health checks" maps to a Metadata rule on secrets plus a None rule on nonResourceURLs, both placed above the catch-all. Querying the log: "which ServiceAccount deleted the Deployment?" becomes a jq filter over verb, objectRef.resource, objectRef.name, and user.username. Both get verified on real output, so always run the query after making your edit.

Supply-chain paper trail: Trivy Operator

The Trivy Operator rescans running workloads continuously and stores every finding as a Kubernetes CR. That's the core platform-engineering move: turning compliance from PDF attachments into queryable API objects so kubectl, RBAC, GitOps, and Grafana dashboards all work on compliance data out of the box.

SBOM vocabulary, because the words get tested

  • CycloneDX and SPDX are the two standard formats. Trivy outputs both, so picking one is a tooling compatibility question rather than a quality debate.
  • An SBOM lists components and versions; it isn't a vulnerability report on its own. You join it against a CVE feed, which is why an SBOM generated at build time stays valuable long after new CVEs drop.
  • The one-sentence pitch: when the next log4shell hits, you query your SBOMs for the affected package in seconds instead of rescanning the entire fleet.
  • Its neighbors: provenance/attestations (how the artifact was built; see section 5.6) and signatures (who vouches for these bytes). Three distinct documents forming one trust story.

Runtime detection, SBOM tooling, and compliance evidence

Falco, syft/grype/trivy, the Trivy Operator's report kinds, kube-bench, in-toto

Falco fills the gap the API audit leaves

The API server never sees a shell spawned inside a container, a file modified under /etc, or an unexpected outbound socket. Falco does. Its kernel driver (modern eBPF by default) watches syscalls, and its k8saudit plugin can ingest the API audit webhook stream too, letting one tool cover both runtime and control-plane events.

Every Falco rule defines rule, desc, condition (filtering fields like proc.name, container.image.repository, k8s.ns.name, and fd.sip), output (a format string), priority (EMERGENCY down to DEBUG), and tags, with macro and list blocks factoring out repeated logic. Rules ship in maturity tiers (stable bundled by default; incubating and sandbox opt-in) and should be tuned via override files rather than editing defaults. Alerts stream to stdout, files, gRPC, or HTTP, and Falcosidekick routes them to Slack, Loki, or Alertmanager. Keep the boundary clean: "alert on a shell in production or writes under /etc" is Falco; "who created that pod?" is the API audit log.

SBOM and scanner tooling, one line each

  • Formats. SPDX (ISO/IEC 5962, tag-value or JSON) and CycloneDX (OWASP, JSON or XML) both capture components, versions, licenses, and hashes: run trivy image --format cyclonedx|spdx-json or syft <image> -o cyclonedx-json. Any SBOM feeds straight back into a vulnerability scanner (trivy sbom sbom.json, grype sbom:sbom.json), which is why build-time SBOMs can be rescanned later without pulling the image again.
  • Attaching it to the image. cosign attest --predicate sbom.json --type cyclonedx <image@digest> stores the SBOM as a signed in-toto attestation right beside the image, ready for admission policies to verify (5.6).
  • VEX (Vulnerability Exploitability eXchange, in OpenVEX or CSAF) records a vendor's or platform team's statement that a CVE doesn't actually affect a shipped product. Passing trivy --vex <file> or --vex repo suppresses those findings with a written justification, giving you an auditable alternative to an ever-growing ignore file.

Every report carries trivy-operator.resource.kind, trivy-operator.resource.name, and trivy-operator.container.name labels, so -l trivy-operator.resource.name=payments filters cleanly without string-parsing report names. Because scans run as short-lived Kubernetes Jobs (in the operator's namespace or the workload's, per OPERATOR_SCAN_JOB_...), a strict NetworkPolicy or missing registry pull secret can silently block reports from ever showing up: a scan job is just a pod. Rescans trigger on a TTL (OPERATOR_VULNERABILITY_SCANNER_REPORT_TTL) and whenever an image digest changes.

Benchmarks and attestations

  • CIS Kubernetes Benchmark audits control-plane and node hardening (API server flags, kubelet settings, file permissions) and versions independently of Kubernetes. kube-bench runs it as a Job against specific targets (master, node, etcd, policies) and prints PASS/FAIL/WARN with control IDs (like 1.2.x for the API server). Use --benchmark to pin a CIS version or pick managed-cluster profiles (eks, gke, aks). The Trivy Operator's k8s-cis compliance report covers the same controls as native CRDs.
  • in-toto attestation is the standard wrapper everything shares: a DSSE envelope (payloadType: application/vnd.in-toto+json plus signatures) enclosing a Statement (_type: https://in-toto.io/Statement/v1, subject[] with name and digest.sha256, predicateType, and predicate). SLSA provenance, SBOMs, scan results, and VEX are all just predicate types inside that envelope. Whenever a task says "attestation", picture one of these signed envelopes attached to an image digest.
  • An end-to-end evidence pipeline: the build produces the image and SBOM; the scan gates on severity and emits a scan attestation; cosign signs the digest; SBOM and provenance attestations live in the registry next to the image; admission enforces signatures and attestations; and the Trivy Operator continuously rescans running workloads while compliance reports roll everything up. Every hop leaves a queryable artifact, which is what "generating audit trails" means for a software supply chain.
Trap

A ClusterComplianceReport is only as fresh as its spec.cron schedule and the underlying reports. After fixing a cluster issue, the rollup still shows yesterday's numbers until the next scheduled run. Always check status.updateTimestamp before quoting a pass count, and remember exam graders often verify the refreshed report rather than just your underlying fix.

Self-check

answer before opening
Which audit level would you set for Secrets, and which for Events? Why?

Secrets go at Metadata, never Request or RequestResponse, so you don't leak secret values straight into log files. Events go at None because they're noisy, high-volume, and low-value. Because rules are first-match-wins, put both near the top of your policy file.

Find every request a specific ServiceAccount was denied. What does the query look like?

Filter on .user.username == "system:serviceaccount:<ns>:<name>" paired with either .responseStatus.code == 403 or .annotations["authorization.k8s.io/decision"] == "forbid", then project out verb and objectRef. That's the audit-log twin of the RBAC debugging you practiced in 5.1.

An SBOM and a vulnerability report: what is the difference and why keep both?

An SBOM is a static inventory of components and versions; a vulnerability report is that inventory matched against a CVE database at one moment in time. Keep both because the inventory stays constant while new CVEs appear every day, which is why continuous rescanning via an operator beats scanning only at build time.

Why is "compliance as CRDs" a platform-engineering idea rather than a Trivy feature?

Because storing compliance findings as Kubernetes API objects makes them queryable with kubectl, governed by RBAC, watchable by controllers, graphable in Grafana, and reviewable in git. Static reports dumped into an object bucket can't integrate cleanly with anything else your platform already runs.

Your cluster's API server will not start after an audit change. First hypothesis?

The policy file at --audit-policy-file is missing, unreadable, or has invalid YAML (or its hostPath mount in the static pod manifest is broken). By design, kube-apiserver refuses to start rather than run silently unaudited, so a small audit mistake looks like a dead control plane.

Your audit policy puts the catch-all Metadata rule first and the Secrets rule after it. What is wrong, and what else should precede the catch-all?

First match wins, so putting the catch-all first makes every rule below it dead code. Here Secrets still land at Metadata by luck, but any None rule below the catch-all stops filtering noise, and any RequestResponse rule below it stops capturing RBAC diffs. Always order from top to bottom: None for health URLs, leases, and kube-proxy watches; Metadata for secrets, configmaps, tokenreviews, and pods/exec; RequestResponse for RBAC and policy groups; and the catch-all last.

Which layer catches each: a user reads a Secret; a process in a container starts /bin/sh; an image contains a package with a new CVE; a node's kubelet allows anonymous auth?

In order: the API audit log (Metadata rule on secrets), Falco syscall rules, the Trivy Operator's VulnerabilityReport on rescan (or a pipeline scan at build time), and kube-bench or the Trivy Operator's InfraAssessmentReport / CIS compliance report. Four distinct sensors telling one compliance story; naming which layer catches what is how you nail "design a complete audit trail".

What is the difference between an SBOM attestation and a VEX document, and why keep both?

The SBOM lists every component inside an artifact, while VEX states whether specific CVEs in those components actually affect the product (not affected, affected, fixed, or under investigation) along with a justification. Scanners match the SBOM against CVE feeds and then apply VEX to suppress non-applicable findings with a documented rationale, which is auditable in a way a bare .trivyignore entry isn't.
