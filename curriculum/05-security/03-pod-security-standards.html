Built-in admission control with nothing extra to install: three named profiles enforced by Kubernetes' Pod Security admission controller and driven entirely by namespace labels. It's less expressive than Kyverno or Gatekeeper, and that simplicity is the whole point.

Orientation

competency 5.4 · Pod Security Standards

Lock down what each profile requires and how the labels work, and PSS turns into the fastest points on the exam. PSS replaced PodSecurityPolicy (removed in 1.25), so if a scenario brings up PSP, the answer is straightforward: it's gone, use PSS for pod hardening and a policy engine for anything PSS can't express.

Profiles and modes

three profiles × three modes
ProfileBlocks / requiresUse for
privilegedNothing: completely unrestrictedSystem namespaces, CNIs, storage drivers
baselineBlocks known-dangerous settings: privileged containers, hostNetwork/hostPID/hostIPC, hostPath volumes, added capabilities outside a safe list, unconfined seccomp/AppArmor, host portsThe sane default for tenant namespaces
restrictedRequires active hardening: runAsNonRoot, allowPrivilegeEscalation: false, all capabilities dropped (ALL, with NET_BIND_SERVICE allowed back), seccompProfile: RuntimeDefault, no hostPath, restricted volume typesEvery workload you can make comply

The one-liner to remember: baseline stops you from being dangerous; restricted forces you to be safe.

You set the three modes independently on each namespace: enforce rejects pods at admission, audit writes violations into the audit log, and warn prints warnings back to the client. Here's the label grammar:

pod-security.kubernetes.io/enforce: baseline
pod-security.kubernetes.io/enforce-version: v1.31     # pin, or "latest"
pod-security.kubernetes.io/warn: restricted
pod-security.kubernetes.io/audit: restricted

Version pinning matters more than it looks: PSS profiles tighten across Kubernetes releases, so leaving a namespace on latest means a routine cluster upgrade can suddenly start blocking pods that deployed fine yesterday. Pinning trades that surprise for a deliberate migration.

The profiles at field level

Every PSS rejection explicitly names the violated controls (privileged, hostPath volumes, allowPrivilegeEscalation != false, unrestricted capabilities, runAsNonRoot != true, seccompProfile). Knowing which YAML field backs each control turns an error message into a ten-second fix.

  • Pod level vs container level. runAsNonRoot, runAsUser, seccompProfile, appArmorProfile, and seLinuxOptions can live on spec.securityContext and flow down to containers (which can still override them). By contrast, allowPrivilegeEscalation, capabilities, privileged, procMount, and readOnlyRootFilesystem exist only per container. When an error calls out "container x", check the container block; when it says "pod or container", pod-level fixes everything at once.
  • What restricted does not require. readOnlyRootFilesystem, resource limits, and a non-root fsGroup aren't part of PSS. If a task demands those, you're looking at a policy engine rule or a hardened manifest, not PSS.
  • Images built to run as root. Setting runAsNonRoot: true on an image whose default USER is root passes admission fine and then fails at container startup with container has runAsNonRoot and image will run as root (a CreateContainerConfigError). Fix it by setting runAsUser: 1000 (and usually runAsGroup), or switching to a non-root image.
  • Ephemeral containers count too. Running kubectl debug inside a restricted namespace fails unless you add --profile=restricted, because the injected debug container has to satisfy the same profile.
Reflex

When a pod gets rejected, split the error message on commas: each clause maps to one row above and tells you which container failed. Fix all of them in a single edit. PSS reports every violation at once, so your second apply should go through cleanly.

Two operational facts that decide troubleshooting tasks

and one preview command
  1. PSS enforces on pods. A Deployment with a violating pod template gets created with zero errors, and then silently fails to spawn pods. The actual rejection lives on the ReplicaSet, one level below where you looked first (same indirection as ResourceQuota in 1.4). Spotting that pattern immediately is worth more than memorizing any single profile rule.
  2. Enforcement only fires at admission. Tightening a namespace label never evicts pods that are already running; they keep going until their next write or rollout. That's why Kubernetes gives you a built-in preview command:
kubectl label --dry-run=server --overwrite ns <ns> pod-security.kubernetes.io/enforce=restricted

What a compliant pod looks like

securityContext:                 # pod level
  runAsNonRoot: true
  runAsUser: 1000
  seccompProfile: { type: RuntimeDefault }
containers:
  - name: app
    securityContext:             # container level
      allowPrivilegeEscalation: false
      readOnlyRootFilesystem: true          # not required by restricted, but good practice
      capabilities: { drop: ["ALL"] }

The demo app's manifest (examples/demo-app/base/deployment.yaml) gives you a live working example of a restricted-compliant pod. Read its securityContext blocks closely, since writing this exact stanza from memory is fair game on the exam. Notice the split: runAsNonRoot and seccompProfile fit naturally at pod level, while capabilities and allowPrivilegeEscalation belong on each container.

PSS versus a policy engine

PSS is built-in, zero-ops, and laser-focused on pod hardening. A policy engine is installable, flexible, and handles everything else (allowed registries, required labels, ownership, cross-object rules) at the cost of running a webhook. The mature answer to "which one?" is both: use PSS as the always-on baseline floor and a policy engine for organization-specific rules (or for namespaces where you need fine-grained exceptions PSS can't express).

Cluster-wide defaults, exemptions, and newer knobs

AdmissionConfiguration, workload resources, user namespaces, AppArmor

Defaults and exemptions live on the API server

Namespace labels handle the per-namespace layer. For cluster-wide defaults and exemptions, configure the PodSecurity admission plugin and pass it to kube-apiserver via --admission-control-config-file:

apiVersion: apiserver.config.k8s.io/v1
kind: AdmissionConfiguration
plugins:
- name: PodSecurity
  configuration:
    apiVersion: pod-security.admission.config.k8s.io/v1
    kind: PodSecurityConfiguration
    defaults:                       # applied to namespaces with no label for that mode
      enforce: baseline
      enforce-version: latest
      audit: restricted
      audit-version: latest
      warn: restricted
      warn-version: latest
    exemptions:
      usernames: []                 # authenticated or impersonated users
      runtimeClasses: [kata]        # pods with this runtimeClassName
      namespaces: [kube-system]     # whole namespaces
  • A namespace label always overrides the cluster default for that mode; defaults only fill in what a namespace didn't specify. So "every new namespace must enforce at least baseline" is solved with this config file (or, on a managed control plane where you can't touch API server flags, with a policy engine that stamps labels onto new namespaces).
  • Exempt requests bypass all three modes. Exempting a username only exempts objects that user creates directly, not pods a controller creates for them. That's why Kubernetes explicitly warns against exempting controller ServiceAccounts like the ReplicaSet controller: doing so would accidentally exempt everyone who can create a Deployment.
  • Watch pod_security_evaluations_total and pod_security_exemptions_total on the API server to track how often each mode triggers; a spike in decision="deny" right after a label change is your immediate rollout signal.

Workload resources and updates

warn and audit evaluate Deployments, StatefulSets, Jobs, and other pod-template controllers directly, so the person running kubectl apply sees the warning right away. enforce only evaluates the resulting pods, which is why violating Deployments fail one level down on the ReplicaSet. Pod updates that only touch metadata (other than seccomp or AppArmor annotations), activeDeadlineSeconds, or tolerations skip re-evaluation. Anything that spawns a new pod, including a Deployment rollout, runs through full admission, which is when a newly tightened label first hits an existing app. Use kubectl label --dry-run=server to preview a namespace tightening, and kubectl apply --dry-run=server on a workload to preview its warnings before creating anything.

Newer knobs that change what "compliant" means

  • User namespaces (GA in 1.36). Setting spec.hostUsers: false maps container UIDs to unprivileged host UIDs, so UID 0 inside the container isn't root on the host node. It requires a Linux 6.3+ kernel with idmap mount support across every filesystem the pod uses (including tmpfs), containerd 2.0+ or CRI-O, and runc 1.2+ or crun 1.9+. It's Linux-only and doesn't apply to hostPath or host namespaces. PSS still evaluates the pod normally; user namespaces add defense in depth underneath it.
  • AppArmor (GA in 1.30). Configure it via securityContext.appArmorProfile: { type: RuntimeDefault | Localhost | Unconfined, localhostProfile: name }. The old container.apparmor.security.beta.kubernetes.io/<container> annotation is deprecated and gets rejected if it conflicts with the field. Baseline checks this field directly.
  • Seccomp. RuntimeDefault uses your container runtime's default profile, while Localhost reads localhostProfile relative to the kubelet's /var/lib/kubelet/seccomp/ directory on each node. Passing --seccomp-default (or seccompDefault: true in KubeletConfiguration) applies RuntimeDefault fleet-wide to pods that omit seccomp, though keep in mind PSS inspects the pod spec at admission rather than the kubelet's runtime default, so restricted still insists the field is written in the spec.
  • PodSecurityPolicy was removed back in 1.25. If a task hands you a policy/v1beta1 PodSecurityPolicy manifest, treat it as a trap and answer with PSS labels plus a policy engine.
How this gets tested

"Make namespace X enforce restricted without breaking existing workloads" means: preview with --dry-run=server, fix the fields the warnings call out (usually allowPrivilegeEscalation, capabilities.drop, runAsNonRoot, and seccompProfile), and then apply the label with a pinned enforce-version. "Allow one system workload that needs hostPath in an otherwise restricted cluster" means an exemption by namespace or a dedicated privileged namespace, never a per-pod exception, because PSS doesn't have those.

On a cluster that does support it, cat /proc/self/uid_map inside the pod maps container UID 0 to a high unprivileged host UID instead of 0, which is the verification check to keep in mind.

Self-check

answer before opening
Name the three profiles in one clause each.

Privileged: completely unrestricted. Baseline: blocks known privilege escalations (privileged containers, host namespaces, hostPath, unsafe capabilities). Restricted: actively requires non-root, allowPrivilegeEscalation: false, all capabilities dropped, and RuntimeDefault (or Localhost) seccomp.

A Deployment is created and no pods appear. Where is the PSS error?

On the ReplicaSet. Because PSS enforces at the pod level, the Deployment succeeds and the ReplicaSet controller logs the rejection one level down. Check kubectl describe rs -l … or namespace events.

You want to know who breaks if you tighten a namespace. Command?

kubectl label --dry-run=server --overwrite ns <ns> pod-security.kubernetes.io/enforce=restricted. The API server evaluates every running pod against the proposed label and prints a warning for each offender without modifying anything.

Why pin enforce-version?

Because PSS profiles gain stricter checks across Kubernetes releases. Leaving it on latest means a routine cluster upgrade can start rejecting pods that deployed cleanly before. Pinning turns that into a scheduled migration instead of a surprise outage.

PSS or Kyverno for "images must come from our registry"?

Kyverno (or Gatekeeper). PSS only covers the fixed pod-hardening profile and knows nothing about image registries. Treat PSS as the always-on floor and run a policy engine alongside it for organization-specific rules.

A pod passes restricted admission and then sits in CreateContainerConfigError with container has runAsNonRoot and image will run as root. What happened?

Setting runAsNonRoot: true satisfied PSS at admission, but the container image's default user is root, so the kubelet refused to launch it. Set runAsUser (and runAsGroup) to a non-zero UID, or switch to an image built with a non-root USER. Remember: PSS checks the pod spec; the kubelet checks the image.

How do you make every namespace without labels enforce baseline and warn on restricted, cluster-wide, and what does a namespace label do to that default?

Configure an AdmissionConfiguration containing a PodSecurityConfiguration whose defaults set enforce: baseline and warn: restricted (with versions), and pass it to kube-apiserver via --admission-control-config-file. Any namespace label overrides the default for that mode only. On a managed cluster where you can't touch API server flags, use a policy engine to stamp those labels onto namespaces as they're created.

Restricted rejects a container for seccompProfile, yet the kubelet runs with seccompDefault: true. Why is that not enough?

PSS inspects the pod spec at admission, whereas the kubelet default only takes effect later at container creation and is invisible to admission control. Restricted requires seccompProfile.type to be explicitly set to RuntimeDefault or Localhost in the spec (at pod level or on every container). The kubelet flag is still worth enabling to cover pods in non-restricted namespaces.
