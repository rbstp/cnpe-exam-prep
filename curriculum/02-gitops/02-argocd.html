Argo CD is the tool most likely to be sitting in front of you on exam day, and the Application resource is its entire API: source, destination, and syncPolicy. Everything in the web UI is just a view over that object, and everything that breaks shows up in its status.

The Application spec

source · destination · syncPolicy
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: demo-staging
  namespace: argocd                      # apps live in the controller's namespace
spec:
  project: default                       # AppProject = the guardrails (see below)
  source:
    repoURL: http://gitea.lab:3000/lab/platform.git
    targetRevision: HEAD                 # branch, tag, or commit SHA
    path: demo-app/overlays/staging      # or chart: + helm: for a chart source
  destination:
    server: https://kubernetes.default.svc   # or name: in-cluster
    namespace: team-a
  syncPolicy:
    automated: { prune: true, selfHeal: true }
    syncOptions:
      - CreateNamespace=true
    retry:
      limit: 3
      backoff: { duration: 5s, factor: 2, maxDuration: 3m }

For targetRevision, setting HEAD or a branch means "follow whatever moves there", while a tag or commit SHA means immutable. Pinning production apps to a SHA and promoting by bumping it is a clean, auditable pattern.

The two status axes

AxisValuesAnswers
SyncSynced · OutOfSync · UnknownDoes live state match git?
HealthHealthy · Progressing · Degraded · Missing · Suspended · UnknownAre the running resources actually okay?
Synced and Degraded isn't a contradiction

Git told the cluster to run a broken image, and the cluster faithfully ran it broken. Sync is green because there's zero diff between git and live; health is red because the Deployment can't roll out. Clicking Sync again won't fix a thing - you need a git commit. Learn to spot this state on sight; section 2.6 opens with it.

Every combination tells a different story, and each has one clear first move:

Health is computed per resource kind using built-in checks (a Deployment is Healthy when its available replicas match desired, a LoadBalancer Service waits for an external IP, and so on). Custom kinds rely on custom Lua health checks, which is how Argo CD knows how to report on CRDs like Argo Rollouts. When a custom resource stays stuck in Progressing forever, either it has no health check registered or its status conditions never settle.

syncPolicy, decided before you need it

  • Manual: flags OutOfSync and waits. Right for production environments where a human needs to approve the rollout.
  • automated: syncs automatically whenever git moves.
  • automated.selfHeal: true: continuously reverts live cluster drift back to git.
  • automated.prune: true: deletes live resources whose manifests disappear from git. Watch this one carefully: leave it off and renaming a resource orphans the old copy forever; turn it on and deleting a file deletes production.

Ordering: waves and hooks

CRDs before CRs, migrations before rollout

A sync runs in phases, and within the Sync phase it walks through numbered waves. Lower numbers run first (default is 0), so adding argocd.argoproj.io/sync-wave: "-1" puts a resource ahead of the pack. Argo CD waits for every resource in a wave to report Healthy before moving to the next one.

PreSync  ──▶  Sync (wave -1 → 0 → 1 → …)  ──▶  PostSync  ──▶  SyncFail (only on failure)
   │                      │                       │
   │                      │                       └─ smoke-test Job
   │                      └─ CRDs, then CRs, then apps
   └─ db migration Job

Hooks are plain manifests carrying argocd.argoproj.io/hook: PreSync|Sync|PostSync|SyncFail|PostDelete|Skip, usually paired with hook-delete-policy (HookSucceeded, BeforeHookCreation, or HookFailed) so completed Jobs don't pile up. The classic pairing is a database migration Job in PreSync and a smoke test in PostSync.

The "no matches for kind" fix has two forms

If you own both the CRD and the CR, put the CRD in wave -1. If the CRD comes from somewhere you don't control, annotate the CR with SkipDryRunOnMissingResource=true so Argo CD's pre-apply dry run stops choking on it.

Scale patterns and guardrails

AppProject · app-of-apps · ApplicationSet

AppProject

An AppProject draws the security fence around a group of Applications: which sourceRepos they can pull from, which destinations (cluster + namespace pairs) they can target, which cluster-scoped and namespaced kinds are allowed or blocked, plus per-project RBAC roles and sync windows (time ranges when syncing is permitted or denied). In a multi-tenant platform, this is how teams self-serve deployments without being able to sneak a ClusterRoleBinding into kube-system. If a task says "team X may only deploy to namespace Y from repo Z", the answer is an AppProject, not a Kubernetes Role.

app-of-apps vs ApplicationSet

  • app-of-apps: one root Application whose manifests are other Applications. Simple, explicit, and easy to review because you write each child yourself. It shines when bootstrapping a cluster's platform layer in a strict wave order.
  • ApplicationSet: a template paired with generators that stamp out Applications automatically. Generators to know on sight: list, clusters, git (directories or files in a repo), scmProvider (every matching repo in an org), pullRequest (ephemeral preview environments), and matrix/merge to combine them. Setting goTemplate: true switches templating to Go templates with Sprig functions.

On the exam, the testable skill is reading a generator block and predicting exactly which Applications will be created. In this lab, examples/argocd-appset.yaml stamps out one app per overlay directory in git, and the Backstage golden path (section 3.6) uses an SCM generator watching the Gitea services org.

Where does the workload actually land?

An ApplicationSet template sets destination.namespace on each generated app, but an explicit namespace: inside a manifest or kustomization always wins. That's why the lab's overlays land in team-a and team-b regardless of what the template's destination says.

Other clusters

destination.server: https://kubernetes.default.svc (or name: in-cluster) targets the local cluster. Any remote cluster has to be registered first: argocd cluster add <context> creates a ServiceAccount over there and saves its credentials in a Secret in argocd labeled argocd.argoproj.io/secret-type: cluster. That Secret is the exact object an ApplicationSet's clusters generator iterates over, so multi-cluster fan-out and "deploy to the second cluster" are really the same mechanism. Run argocd cluster list to see what's registered, and check the AppProject's destinations to see who's allowed to target it.

Diffing quirks

ignoreDifferences (using group/kind with jsonPointers or a jq path) keeps a mutating webhook or an HPA-managed replica count from causing permanent drift. argocd.argoproj.io/compare-options: IgnoreExtraneous hides extra resources Argo didn't create. Both exist because "stuck OutOfSync forever on a field nobody edits" is one of the most common day-2 headaches.

Argo CD 3.x defaults and the vocabulary of status

what changed in 3.0 to 3.5 · conditions · operation phases · deletion · refresh

Defaults that differ from what older tutorials assume

  • Annotation tracking is now the default (application.resourceTrackingMethod: annotation). Resources get argocd.argoproj.io/tracking-id: <app>:<group>/<kind>:<ns>/<name> instead of the old app.kubernetes.io/instance label (use annotation+label if another tool still expects the label). Because the annotation names the exact object, copied resources like HNC copies stop showing up as false drift.
  • Fine-grained RBAC: update and delete on applications no longer cover an Application's child resources - those require update/* and delete/* (or a scoped rule like update/apps/Deployment/ns/name). logs, get is also a first-class permission now; without it, the UI logs tab renders blank.
  • Default resource.exclusions keep high-churn kinds out of the cache: Endpoints, EndpointSlice, Lease, the SubjectAccessReview family, CertificateSigningRequest, Kyverno reports, cert-manager CertificateRequest, and Cilium identities and endpoints. If a question asks why Argo CD "can't see" a Lease, this is why.
  • Status ignored in diffs across all resource kinds (previously CRDs only), so controllers writing to .status never trigger false OutOfSync states.
  • Minor-release milestones: 3.1 added oci:// sources and CLI plugins; 3.2 loosened OCI layer rules and unified UI deletion; 3.3 requires server-side apply to install the ApplicationSet CRD (it outgrew the client-side annotation size limit); 3.4 updated the cluster version format and Teams notifications; and 3.5 (August 2026) promoted the Source Hydrator and impersonation to beta while adding internal mTLS, git commit signature verification, ApplicationSets in any namespace, and Helm 4 support.

When you see an InvalidSpecError saying "application repo X is not permitted in project Y" or "destination namespace Z is not permitted", that's the AppProject pushing back. Fix the project's sourceRepos or destinations, not the Application.

Deletion and refresh mechanics

  • Cascade deletion is controlled by the finalizer resources-finalizer.argocd.argoproj.io (foreground) or resources-finalizer.argocd.argoproj.io/background. argocd app delete X adds it, whereas --cascade=false strips it so workloads stay running (the "unmanage without deleting" move). With kubectl, patch the finalizer in or out before deleting. PreDelete and PostDelete hooks run only on Application deletion and stall it with a DeletionError if they fail.
  • Refresh without the CLI: annotate the Application with argocd.argoproj.io/refresh: normal or hard, and the controller strips the annotation once it runs. Adding argocd.argoproj.io/skip-reconcile: "true" freezes an Application completely (alpha; status stops updating).
  • Hooks and waves: hook cleanup defaults to BeforeHookCreation if no hook-delete-policy is set. Don't put ttlSecondsAfterFinished on hook Jobs, or Kubernetes may garbage-collect a Job Argo CD is still waiting on. Pruning walks waves in reverse order, with a 2 s pause between waves (ARGOCD_SYNC_WAVE_DELAY).
Reflex

Run argocd app get X, then kubectl -n argocd get app X -o jsonpath='{.status.conditions}'. The first gives you sync and health; the second gives you the exact condition type, which points straight at the broken object: InvalidSpecError → AppProject or spec, ComparisonError → repo-server or credentials, SyncError → API server rejection.

ApplicationSet behavior, RBAC and notifications

generator specifics · policies · progressive syncs · policy.csv · subscriptions · sync windows

Generators: what each one yields

  • list: literal elements. The simplest fan-out and the one to reach for when a task hands you three clusters by name.
  • clusters: one parameter set per registered cluster Secret (name, server, and Secret labels under metadata.labels.*), filterable with selector. Note that the local cluster only shows up if you've explicitly registered it.
  • git directories: path: apps/* emits path.path, path.basename, path.basenameNormalized, and path.segments. Entries with exclude: true drop directories, and dot-directories are skipped. git files turns every matching JSON or YAML file into a parameter set populated with its keys.
  • matrix: cartesian product of exactly two generators. The second generator can reference parameters from the first, and combination generators only nest one level deep.
  • merge: starts with a base generator and overrides matching entries from later generators on mergeKeys, following the same nesting limit.
  • scmProvider (repos in an org) and pullRequest (open PRs matching labels, branchMatch, or titleMatch): Applications come and go automatically with repos or PRs, powering ephemeral preview environments. requeueAfterSeconds sets the poll interval; webhooks make it immediate.
  • plugin (RPC to a custom service), clusterDecisionResource (a placement CR), and oci (directories or files inside an OCI artifact).

For templates, pair goTemplate: true with goTemplateOptions: ["missingkey=error"] so typos fail loudly instead of silently rendering an empty string, and use normalize or slugify to keep generated names DNS-safe. Watch out for collisions: two generated Applications with the same name silently collapse into one.

Controlling what the controller may do

  • spec.syncPolicy.applicationsSync controls lifecycle rights: sync (default: create, update, delete), create-only, create-update, or create-delete. The controller's global --policy flag overrides this unless policy override is enabled.
  • spec.syncPolicy.preserveResourcesOnDeletion: true keeps live workloads alive when the ApplicationSet is deleted. To preserve the child Applications themselves, you also need the finalizer on the ApplicationSet and background deletion.
  • spec.ignoreApplicationDifferences lets humans toggle settings like auto-sync on a generated Application without the ApplicationSet controller snapping them back.
  • Progressive syncs (experimental, opt-in): configure strategy.type: RollingSync with steps[].matchExpressions over Application labels and maxUpdate. Each cohort must reach Healthy before the next begins, and it forces auto-sync off on the generated Applications.

Notifications and sync windows

  • Notifications live in argocd-notifications-cm (service.slack, service.webhook.<name>, trigger.on-sync-failed, template.app-sync-failed) with credentials in argocd-notifications-secret. Subscribe by annotating an Application or AppProject, e.g. notifications.argoproj.io/subscribe.on-sync-succeeded.slack: my-channel. Installing the built-in catalog gives you standard triggers like on-deployed, on-health-degraded, on-sync-failed, and on-sync-status-unknown.
  • Sync windows on an AppProject take kind: allow|deny, a cron schedule, a duration, and selectors for applications, namespaces, or clusters. Setting manualSync: true lets a human bypass a deny window, and an active deny always beats an active allow.
How this gets tested

"Team A may deploy only from repo R into namespace N and must be able to sync but not delete" translates to an AppProject with sourceRepos: [R], destinations: [{server, namespace: N}], and a project role granting applications, get and applications, sync (without delete), bound to the team's group. Prove the guardrail works by pointing a test Application at a disallowed repo or namespace and checking its conditions for InvalidSpecError.

Self-check

answer before opening
An app is Synced/Degraded. What are you allowed to conclude, and what is the fix?

Live matches git, so Argo CD did its job - the desired state itself is broken (bad image, impossible resource request, missing config key). Fix it with a git commit. Re-syncing won't change anything because there's no diff left to apply.

A sync fails with "field is immutable". Two ways forward?

Add Replace=true (app-wide or per resource) so Argo uses kubectl replace instead of apply, or delete the live resource and let Argo recreate it (Force=true automates delete-and-recreate). Pick carefully, though: replace isn't magic - a Service manifest omitting clusterIP will still be rejected as immutable, and neither flag can shrink a PVC.

What is an AppProject for, in one sentence, and name two things it constrains?

It's the policy guardrail around a group of Applications, constraining permitted source repos and destination cluster/namespace pairs - plus allowed/denied resource kinds, per-project RBAC roles, and sync windows. It's how you give a team self-serve deployments without letting them deploy anything anywhere.

You are handed an ApplicationSet with a git directory generator over apps/*/overlays/*. How many Applications will exist?

One per matching directory in the repo at the current revision. Count the directories, then inspect the template's name expression for collisions (two identical names silently overwrite each other). Reading a generator block and predicting the exact output is the exam skill; kubectl -n argocd get applications confirms it.

An app shows OutOfSync forever on a field no human edits. What is happening and what fixes it?

Something inside the cluster is mutating the object after apply - a mutating webhook, an HPA updating replicas, or a defaulting controller. Fix it with ignoreDifferences for that path (plus RespectIgnoreDifferences=true if needed), or stop managing that field in git. That's a configuration choice, not a controller bug.

You changed the repo but Argo insists nothing changed. Sequence of moves?

Start with argocd app get --refresh (recompare), then --hard-refresh (drop the manifest cache). Next, verify the app's targetRevision actually points at the branch you pushed to, and finally check repo-server logs for auth or render errors. Always try the cheapest check first.

A sync ends with operation phase Error rather than Failed. What is the difference and where do you look?

Failed means the apply reached the API server and was rejected (immutable field, admission denial), with the exact rejection in syncResult.resources[]. Error means Argo CD itself couldn't complete the operation (render failure, unreachable repo, hook creation failure). For Error, check repo-server and application-controller logs; for Failed, read the per-resource message.

You must stop managing an Application but keep its workloads running. Exact move?

Run argocd app delete X --cascade=false, or with kubectl patch metadata.finalizers to strip resources-finalizer.argocd.argoproj.io before deleting the Application. Leaving the finalizer in place triggers a foreground cascade delete that wipes every managed resource. For protecting a single resource rather than the whole app, annotate it with Delete=false.

An ApplicationSet with a matrix of a git directories generator and a clusters generator: how many Applications, and what breaks if you nest another matrix inside?

directories × clusters - one Application per pair, named by your template (watch out for collisions, which silently merge). A matrix takes exactly two child generators and combination generators only nest one level deep, so nesting a matrix inside a matrix inside a matrix gets rejected at generation time rather than by the API server's schema validation.

A user can see Applications and sync them but the Logs tab is empty. Which policy line is missing since 3.0?

p, role:<their-role>, logs, get, <project>/*, allow. Starting in Argo CD 3.0, logs RBAC is enforced by default and is no longer implied by applications, get. That same 3.0 release split child-resource permissions into update/* and delete/*.
