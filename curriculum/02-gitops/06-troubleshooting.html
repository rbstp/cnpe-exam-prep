Broken delivery is the single most likely domain 2 exam task. Failures sort cleanly into four buckets (plus admission), and your first diagnostic move is figuring out which bucket you're in. Everything on this page trains that reflex.

needsmake core

Orientation

the diagnostic half of every domain 2 competency

Under exam time pressure, the costly mistake isn't picking the wrong fix; it's fixing the wrong layer. Bucket the problem first, then descend. Name the bucket out loud before touching anything: it takes three seconds and keeps you from patching live state when the real bug lives in git.

The four buckets

symptom → evidence → who fixes it

1 · Git is wrong, the cluster is faithful

Synced and Degraded. Someone pushed a bad image tag, an impossible resource request, a missing ConfigMap key, or a readiness probe that can never pass. The controller did its job faithfully, so the fix is a git commit. Evidence: health reads Degraded (or sits in Progressing headed there) while sync is green, and pod events spell out the real fault: ImagePullBackOff, CreateContainerConfigError, or CrashLoopBackOff.

2 · The cluster refuses what git says

The sync fails outright. An admission policy blocks the manifest, the API version doesn't exist on this cluster, a field is immutable (Service clusterIP, Deployment selectors, shrinking a PVC), or the CRD isn't installed yet. Evidence: the sync operation's error quotes the API server's rejection verbatim. For immutable-field errors, you need delete-and-recreate or Replace=true.

3 · The controller lacks permission or access

The repo is unreachable, credentials rotated, an Application targets a namespace the controller's RBAC can't touch, or an ApplicationSet token is missing a scope. Evidence: the error points at the controller's own identity, lives in controller logs (kubectl -n argocd logs deploy/argocd-repo-server or flux logs), and says nothing about your workload. No pod is ever involved, and that absence is the giveaway.

4 · Nobody is wrong, the state is stale

A dropped webhook, a long poll interval, a forgotten suspend, or a branch that moved while the app is pinned to a tag. Evidence: everything looks green, just old. flux get kustomizations shows Suspended: True, or argocd app get shows a last-sync timestamp from an hour ago. Run argocd app get --refresh or flux reconcile … --with-source, and always check for suspension first.

Drift deserves one more sentence

With self-heal turned on, live drift vanishes automatically, flipping the mystery to "what keeps recreating this object I keep deleting?". A controller is doing it, and kubectl get <res> -o jsonpath='{.metadata.ownerReferences}' (or Argo CD's argocd.argoproj.io/tracking-id annotation) proves which one. With self-heal off, argocd app diff shows you line by line what drifted.

Two habits pay off every single time. First, compare rendered manifests against live objects instead of squinting at raw source YAML: argocd app manifests <app> prints the exact manifests being applied, catching overlay bugs that source review misses. Second, don't skip the middle layer: when a Deployment exists with zero pods, the error is sitting on its ReplicaSet, and skipping straight from Deployment to pods makes people miss it completely.

Reflex

In Argo CD, run argocd app get X then kubectl -n argocd get app X -o jsonpath='{.status.conditions[*].type}'. In Flux, run flux get all -A --status-selector ready=false then kubectl get kustomization X -n flux-system -o jsonpath='{.status.conditions[?(@.type=="Ready")].reason}'. Let the reason string pick your bucket first; only then dig into the full message.

Bucket 5: admission refused it

webhooks and policy engines between the controller and etcd

The first four buckets assume the API server itself is the final gatekeeper. Once you add Kyverno, Gatekeeper, ValidatingAdmissionPolicy, or operator webhooks, there's a fifth place a manifest can die, and it speaks its own error dialect.

Message fragmentWhoFix lives in
admission webhook "validate.kyverno.svc-fail" denied the request: ... policy X rule YKyverno validate in Enforce modeThe manifest (satisfy the rule) or the policy (exclude or switch to Audit), never the GitOps controller
admission webhook "validation.gatekeeper.sh" denied the request: [constraint-name] ...Gatekeeper constraintSame choice; enforcementAction: dryrun is the audit equivalent
ValidatingAdmissionPolicy 'x' with binding 'y' denied request: ...VAP (GA 1.30), or MutatingAdmissionPolicy (GA 1.36) for mutationsThe policy's CEL expression or binding match (no webhook pod exists here)
failed calling webhook "x": ... connection refused / context deadline exceeded / no endpoints availableA webhook whose backing pod is down with failurePolicy: FailThe webhook's Deployment or Service; every matching write is frozen until it's back, including the GitOps controller's own
dry-run failed ... admission webhook "x" does not support dry runFlux's server-side dry-run hitting a webhook without sideEffects: None or NoneOnDryRunThe webhook configuration
the server could not find the requested resourceA CR whose CRD isn't installed yet (Argo CD dry-run)SkipDryRunOnMissingResource=true or a sync wave; in Flux, dependsOn the CRD Kustomization

The tell separating bucket 5 from bucket 2 is simple: the error names a webhook or policy rather than a schema field. On the controller side the symptom looks identical (Argo SyncFailed, Flux ReconciliationFailed), and for Deployments a pod-level policy violation can again show up one level down on the ReplicaSet. Meanwhile, a mutating policy that alters manifests after apply (injecting sidecars, labels, or resource requests) shows up as endless OutOfSync in Argo CD and noisy "configured" events every interval in Flux. Fix that with ignoreDifferences or kustomize.toolkit.fluxcd.io/ssa: Merge instead of fighting the policy.

The webhook that blocks its own fix

A dead webhook with failurePolicy: Fail and a broad scope (all pods, all namespaces) can block the GitOps controller from applying the exact manifest that would fix it. Inspect kubectl get validatingwebhookconfiguration,mutatingwebhookconfiguration and the webhook Service's endpoints. The clean fix is getting the webhook pod healthy; the break-glass move is flipping that webhook to Ignore or tightening its namespaceSelector, then capturing that change in git.

Self-check

bucket each of these in one sentence
"The app is Synced and Healthy but the feature we merged an hour ago is missing."

Bucket 4 (stale). Check for suspension first, then compare the last-sync timestamp and resolved revision against your commit SHA, and confirm the app is tracking the branch you actually pushed to. Trigger a refresh/reconcile before digging deeper.

"Sync fails: Service "demo" is invalid: spec.clusterIP: Invalid value: field is immutable."

Bucket 2 (cluster refuses). The API server rejected the patch and the sync operation relayed it verbatim. Either fix the manifest in git or use replace/force semantics if the field genuinely needs to change (accepting the recreation churn).

"argocd-repo-server logs show authentication required; the workload is untouched and running fine."

Bucket 3 (access). None of your workload pods are involved: the controller's own repo credentials, token scope, or rotated Secret broke. Existing pods keep humming because reconciliation broke, not the running deployment.

"Deployment exists, no pods, no error on the Deployment."

Step one level down to the ReplicaSet: a ResourceQuota, Pod Security Standards, or an admission webhook blocked pod creation (just like sections 1.4 and 5.3). Delivery succeeded; admission stopped the pods.

"I keep deleting this ConfigMap and it keeps coming back."

A controller is actively reconciling it: Argo CD self-heal, a Flux Kustomization on its interval, or an operator. Identify the owner via ownerReferences, Argo's argocd.argoproj.io/tracking-id annotation, or flux trace, then fix the source of truth (or suspend reconciliation first if you need a temporary live edit).

"Sync failed: admission webhook "validate.kyverno.svc-fail" denied the request". Which bucket, and where does the fix go?

Bucket 5 (admission). The manifest reached the API server and Kyverno blocked it. Fix the manifest so it satisfies the rule (usually what the grader expects), or update the policy if the task says the policy itself is wrong. Clicking sync again won't help: Argo CD reports SyncFailed and Flux reports ReconciliationFailed with the same denial text.

A Flux Kustomization reports ArtifactFailed. What is broken and where do you look first?

Its upstream source has no valid artifact: the GitRepository or OCIRepository isn't Ready (AuthenticationFailed, GitOperationFailed, bad ref) or hasn't fetched yet. That's bucket 3 upstream of the Kustomization: run flux get sources all -A and kubectl describe gitrepository first. Once the source publishes, the Kustomization heals on its own.

Argo CD shows sync status Unknown with a ComparisonError condition. Bucket?

Bucket 3 (access/tooling). Comparison itself failed, so Argo CD can't even tell whether live matches git. Common causes are bad repo credentials or URL/revision, a Kustomize/Helm render error in repo-server, or an unreachable target cluster. The condition message names the cause, and the workload stays untouched, the signature of bucket 3.
