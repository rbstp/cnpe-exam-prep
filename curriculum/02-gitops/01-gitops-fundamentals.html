GitOps is one idea applied ruthlessly: git holds your desired state, an in-cluster controller pulls it and reconciles continuously, and nobody deploys by pushing manifests from a laptop or a CI job. Everything else in this domain (Argo CD, Flux, promotion, drift handling) is just machinery built around that one idea.

needsmake core

Orientation

competency 2.1 · domain 2 is 25% of the exam

Domain 2 is the biggest slice of the exam and the most mechanical. You'll get tasks like "make this change reach the cluster through git", "this app is OutOfSync, fix it", or "pause reconciliation while I operate". Every one of them assumes the mental model on this page is already second nature.

The four OpenGitOps principles, quotable
  1. Declarative: the system's desired state is expressed declaratively.
  2. Versioned and immutable: desired state is stored in a way that enforces immutability and versioning, and retains a complete version history.
  3. Pulled automatically: software agents pull the desired state declarations from the source.
  4. Continuously reconciled: agents continuously observe actual state and attempt to apply the desired state.

Graders love these exact phrases. Memorize the four anchors (declarative, versioned/immutable, pulled, reconciled) and you can reconstruct the full definitions on the spot.

The concepts questions hang off

reconciliation · drift · push vs pull

Reconciliation is a loop, not an event

The controller compares live cluster state against git on a timer and whenever a webhook fires. That means a manual kubectl edit doesn't fail - it either gets reverted on the next loop (if self-heal is on) or gets flagged as drift (if it's off). "Why did my manual fix disappear?" is the symptom you'll run into most, and OutOfSync is how the controller tells you about it. The upside of a continuous loop is that recovery comes almost for free: wipe an entire namespace and the next reconcile rebuilds it. That's the disaster-recovery case for GitOps.

   ┌──────────── git (desired) ────────────┐
   │  demo-app/overlays/staging/…          │
   └────────────────┬──────────────────────┘
                    │ poll (~3 min) or webhook
                    ▼
        controller in the cluster  ── compares ──▶     diff
                    │                                   │
       automated?   │ yes → apply            selfHeal?  │ live drift → revert
                    │ no  → report OutOfSync    prune?  │ removed from git → delete live
                    ▼
   ┌──────────── cluster (live) ───────────┐
   └───────────────────────────────────────┘

Push vs pull

A CI job pushing manifests needs cluster credentials sitting outside the cluster, and it only knows the cluster's state at the moment it deploys. A pull-based agent keeps credentials inside the cluster, never exposes them outward, and never stops comparing. That second part - continuous comparison - is why GitOps isn't just "CI that runs kubectl".

Where the boundary actually sits

CI builds and tests artifacts and, at most, opens a pull request to bump an image tag. CD is the in-cluster agent reconciling git. If a scenario describes a Jenkins job running kubectl apply against production, hit all four expected critiques: cluster credentials live outside the cluster, there's no drift detection, there's no continuous reconciliation, and there's no single source of truth.

Repo design

directories, not branches

This lab seeds two Gitea repos that model the standard split: platform (cluster-level config like policies, tenants, and the app-of-apps) and demo-app (a single workload). Separating them matters because they have different reviewers, different blast radii, and different release cadences.

You'll still see branch-per-environment setups in the wild, and the exam expects you to know why they're an anti-pattern.

Templating, both flavors

Kustomize layers patches onto a base without a templating language, using resources, patches (strategic-merge or JSON 6902), images, namePrefix, labels (the v5 replacement for the deprecated commonLabels), and configMapGenerator. It's YAML all the way down, and kustomize build shows you the exact manifests that will land in the cluster. Helm renders Go templates from values files, trading away that plain-YAML clarity ("the manifest doesn't exist until something renders it") in exchange for conditionals and loops. Both Argo CD and Flux consume both, and both let you post-render one with the other.

Helm is also a release manager, not just a template renderer, and an exam task can test that side directly. Keep these commands handy: helm list -A (releases and revisions), helm upgrade --install --atomic --wait (roll back automatically if it never becomes ready), helm history and helm rollback <rel> <rev>, helm get values --revision, and helm diff if the plugin is installed. Release state lives in Secrets of type helm.sh/release.v1 in the release namespace. That's how you see what a previous operator deployed - and why a Flux HelmRelease can end up adopting or fighting an existing release.

Command reflex

Never push an overlay you haven't rendered locally first. kustomize build <dir> (or kubectl kustomize) and helm template turn "I think this renders right" into "I know". Better yet, both work completely offline in the exam terminal.

Secrets

Plain Secrets don't belong in git - base64 is encoding, not encryption. The three sanctioned patterns are Sealed Secrets (encrypt for git so only the in-cluster controller can decrypt), External Secrets Operator (git holds references while an external store holds the truth), and SOPS (encrypted values in git, decrypted by the agent, with native support in Flux). Section 5.1 covers the mechanics. Here, remember that "how do secrets work in GitOps?" has real architectural answers, and "commit it base64-encoded" isn't one of them.

Failure modes to recognize on sight

a preview of section 2.6
  • Two controllers, one resource. Pointing both Argo CD and Flux at the same manifest kicks off an infinite reconcile war. In this lab they deliberately own different paths, and keeping that boundary sharp is half the lesson.
  • Manual fix disappears. Self-heal just did its job. The fix belongs in git; if you genuinely need an emergency live change, suspend reconciliation first (Flux) or disable auto-sync (Argo CD), do the surgery, then land the fix in git and turn reconciliation back on.
  • Prune surprises. Rename a resource in git with pruning off and the old copy lingers forever. Turn pruning on and deleting a file deletes production. Know which setting is active before you push.
  • Immutable fields. Changing a Service's clusterIP, selector labels, or shrinking a PVC causes apply to fail with an API server rejection naming the field. The GitOps fix is delete-and-recreate or a replace-style sync option, not editing the live object.
  • Stale but green. A suspended reconciler, a dropped webhook, or a long poll interval leaves everything green while nothing is current. Always check when an app last synced before you trust a green dashboard.

Repos, promotion and rendered manifests

layouts by team structure · promotion as a diff · hydration · OCI as a source · Kustomize vs Helm

The OpenGitOps principles are versioned (v1.0.0), and their accompanying glossary defines desired state, state store, reconciliation, and continuous (specifically "continues to happen", not instantaneous). Everything in this panel turns those principles into concrete repository layouts and promotion flows.

Promotion patterns

  • Tag bump by PR: CI (or Flux image automation) writes the new image tag into the staging overlay, and a human or bot promotes that same change into production. The PR doubles as the change record, with approvals right on the diff.
  • Pin to a SHA or tag: Production Applications and Kustomizations track an immutable ref, so promotion means advancing the pin. Nothing hits production just because a branch moved.
  • Environment gates: Use Argo CD sync windows, Flux suspend, or a promotion controller like Kargo in front of those pins. The exam won't ask for Kargo by name, but it does expect you to know that promotion is a git operation, not a button click in a UI.
  • Anti-pattern: One branch per environment. Merges pile up conflicts, cherry-picks obscure history, and environments gradually drift apart structurally.

Rendered manifests

Templating hides the exact YAML that hits the cluster. The rendered manifests pattern solves that by rendering templates in a pipeline and committing the plain YAML to a branch or directory the agent watches. Reviewers inspect final manifests, and the diff between staging and production becomes a real diff. Argo CD builds this in as the Source Hydrator (beta since 3.5): spec.sourceHydrator.drySource points at the templated input, syncSource.targetBranch and path specify where hydrated output gets pushed and synced from, and write credentials live in a repo Secret labeled argocd.argoproj.io/secret-type: repository-write. Flux achieves the same thing by having CI run flux push artifact and pointing an OCIRepository at the result.

OCI artifacts as a source

  • Argo CD (3.1+): Set repoURL: oci://registry/org/config, targetRevision to a tag or digest, and path: .. Helm charts in OCI registries work the same way, using standard chart fields.
  • Flux: Run flux push artifact oci://registry/org/config:tag --path ./deploy --source ... --revision ... to publish an artifact with Flux media types. An OCIRepository consumes it via ref.tag, ref.semver, or ref.digest, with optional verify.provider: cosign or notation verification, and a Kustomization uses it just like a GitRepository.
  • Why bother? Your registries already hold container images, so config and images can share signing, retention, and promotion (retagging) - and air-gapped clusters without git access can still pull.

Both engines let you combine the two by post-rendering: Flux uses HelmRelease.spec.postRenderers[].kustomize, while Argo CD combines spec.source.kustomize with a Helm chart through multiple sources or a config management plugin. One surprise that catches people often: Argo CD doesn't create Helm release Secrets, so helm list comes up empty for an Argo-managed chart.

How this gets tested

"Promote the staging image to production" means finding where production pins the image (overlay images:, HelmRelease values, or Application targetRevision), updating it in git, and verifying the rendered output with kubectl kustomize overlays/production before the controller syncs. Editing the live Deployment scores zero even if the pods end up identical.

Bootstrapping, both ways

  • Flux: Run flux bootstrap github --owner ORG --repository fleet --branch main --path clusters/prod --personal --token-auth (also supports gitlab, gitea, bitbucket-server, and generic git). Bootstrap installs the controllers, commits gotk-components.yaml and gotk-sync.yaml under that path, and creates the flux-system GitRepository and Kustomization so Flux manages itself from then on. Pass --components-extra image-reflector-controller,image-automation-controller for image automation, verify with flux check, and run flux migrate before upgrades to move objects to current API versions (Flux 2.9 removed the v1beta2 image and notification APIs).
  • Argo CD: Apply the install manifest, then create a root Application pointing at your platform repo's argocd/ or clusters/ directory containing Argo CD's own config plus every child Application (the app-of-apps pattern). From there, Argo CD manages its own argocd-cm, argocd-rbac-cm, and Applications. Don't forget to rotate and delete the initial admin password in argocd-initial-admin-secret.
Two controllers, same path

If both engines run on the same cluster, make ownership crystal clear in the repo layout: let Flux reconcile clusters/ and infrastructure/ while Argo CD owns apps/ (or vice versa), and never point both at the same directory. If the split isn't spotless, Argo CD's FailOnSharedResource=true and Flux's kustomize.toolkit.fluxcd.io/ssa: Ignore annotation are your safety rails.

Self-check

answer before opening
State the four OpenGitOps principles without looking.

Declarative, versioned and immutable, pulled automatically by agents, and continuously reconciled. If you blank on one under pressure, it's usually "versioned and immutable" - which also happens to be the one carrying the audit and rollback story.

Why are environment branches discouraged?

Long-lived branches accumulate divergent changes. Promotion turns into messy merges with conflicts and cherry-picks instead of a clean, reviewable diff, and environments drift apart structurally instead of differing only in the values you intended. Directories keep those differences explicit and diffable.

A colleague fixes production with kubectl edit during an incident. What happens next, and what should they have done?

Self-heal reverts it on the next reconcile (or flags it as drift if self-heal is off). The right move is to suspend or disable reconciliation for that app, apply the emergency change, then land the same fix in git and resume so it sticks and stays in the audit trail.

What does prune actually change, and what is the failure mode in each setting?

Prune deletes live resources whose manifests disappear from git. With prune off, renamed or removed resources linger forever as invisible cruft. With prune on, deleting a file deletes the running workload, so a careless refactor can cause a production outage. Neither mode is magically safe - safety comes from knowing which one is on.

Where do secrets live in a GitOps repo?

Encrypted (Sealed Secrets or SOPS) or by reference (External Secrets Operator pointing at an external store) - never plaintext and never bare base64. The key distinction to state: Sealed Secrets and SOPS keep ciphertext in git, while ESO keeps only a reference and leaves the secret material in the external store.

What is the rendered manifests pattern and how does Argo CD 3.5 implement it?

You render Helm or Kustomize in a pipeline and commit the resulting plain YAML to a branch or directory that the agent syncs from, so reviewers diff final manifests instead of templates. Argo CD's Source Hydrator (beta since 3.5) builds this right into the controller: sourceHydrator.drySource is the templated input, and syncSource.targetBranch/path is where hydrated output gets pushed and synced from using a repository-write Secret.

Which secret approach keeps no secret material in git at all, and what is its dependency?

External Secrets Operator. Git holds an ExternalSecret referencing keys in a SecretStore or ClusterSecretStore, and the operator fetches and writes the Kubernetes Secret on a refreshInterval. The trade-off is your dependency on that external store and its credentials: if it goes down, rotation pauses (though existing Secrets keep working). Sealed Secrets and SOPS store ciphertext in git instead.

What does flux bootstrap actually create, and what is the name of the object that then manages Flux itself?

It installs the controllers, commits gotk-components.yaml and gotk-sync.yaml under --path in your repo, and creates a GitRepository and a Kustomization both named flux-system in the flux-system namespace. From then on, that Kustomization reconciles the whole cluster directory - Flux included - so upgrading Flux is just another commit.

Why does helm list show nothing for a chart Argo CD deployed?

Argo CD renders charts using helm template semantics and applies the plain manifests itself, so it never creates Helm release Secrets. Flux's helm-controller runs real Helm install and upgrade actions and keeps full release history, which is why helm list -n <storageNamespace> sees them. Make sure you call out that difference when comparing engines.
