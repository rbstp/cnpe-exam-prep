The exam names both Argo CD and Flux, and this lab wires both to the same Gitea for a reason: you should be able to express the same delivery in either. Flux has no Application monolith; it breaks GitOps into small CRDs that reference each other, and tracing those references is the core skill.

needsmake core

Orientation

competency 2.1 · the other engine

Argo CD gives you one central controller and one big CRD. Flux gives you a toolkit of small controllers and small CRDs wired together by reference. Neither is universally better; they just fail in different ways, and the exam can drop you in front of either. What really carries over is mental translation, which is why the translation table and exercise sit right below.

ControllerOwnsDoes
source-controllerGitRepository, OCIRepository, HelmRepository, HelmChart, BucketFetches sources and publishes an immutable artifact (tarball + revision)
kustomize-controllerKustomizationTakes an artifact and a path, builds manifests, and applies them
helm-controllerHelmReleaseTakes a chart source and manages real Helm installs and upgrades
notification-controllerAlert, Provider, ReceiverSends events out (Slack, webhooks) and takes webhooks in (git push → instant reconcile)
image-*-controllerImageRepository, ImagePolicy, ImageUpdateAutomationScans registry tags and commits new image versions back to git

Keep that last row in your pocket: Flux can close the CI→CD loop by committing the new image tag to git itself. That's the pure pull-based answer to "how does a new build get deployed without CI ever touching the cluster?".

Working model: sources and appliers

one artifact, many consumers
GitRepository/platform  (interval 1m, ref: main)
        │ produces artifact @ revision main/9f2c1ab
        ├────────────▶ Kustomization/apps     path ./apps      prune ✓  interval 5m
        ├────────────▶ Kustomization/infra    path ./infra     prune ✓  dependsOn: []
        └────────────▶ Kustomization/tenants  path ./tenants   dependsOn: [infra]

HelmRepository/podinfo ──▶ HelmRelease/podinfo ──▶ release in target namespace

That two-step split is the heart of Flux's design. One GitRepository can feed as many Kustomization objects as you like, each watching its own path with its own interval, health checks, and prune setting. dependsOn orders them, acting as Flux's counterpart to Argo CD sync waves and operating between top-level objects rather than inside a single sync.

Two things called Kustomization

Flux's Kustomization (kustomize.toolkit.fluxcd.io) isn't the same thing as Kustomize's Kustomization file (kustomize.config.k8s.io). The Flux CR lives in the cluster and points at a directory; that directory may contain a kustomization.yaml file. Exam prompts love leaning on this overlap, and knowing the difference between kubectl get kustomizations.kustomize.toolkit.fluxcd.io and reading a file in git cuts right through it.

Kustomization fields that decide behavior

FieldEffect
intervalHow often Flux re-applies. Drift correction is a built-in side effect of re-applying; there's no separate selfHeal toggle.
pruneDeletes resources removed from git, with the exact same blast radius as Argo CD's prune.
wait / healthChecks / timeoutHolds Ready back until the managed objects are actually healthy, which is what gives dependsOn real teeth.
targetNamespaceOverrides the namespace on every namespaced manifest the path applies.
postBuild.substitute / substituteFromSubstitutes variables from inline maps, ConfigMaps, or Secrets after kustomize build: Flux's clean answer to "one manifest, per-cluster values".
serviceAccountNameImpersonates that ServiceAccount when applying, enforcing multi-tenancy so a tenant's Kustomization can't exceed its own RBAC.
decryptionNative SOPS decryption at apply time for encrypted secrets in git.

HelmRelease

A HelmRelease points at a chart (from a HelmRepository, GitRepository, or OCIRepository), merges inline values with valuesFrom ConfigMaps and Secrets, and controls failure recovery via install.remediation and upgrade.remediation (retry counts and rollback strategy). Modern Flux also detects and corrects drift on the release's rendered manifests. When a HelmRelease breaks, the whole diagnostic trick is spotting which layer failed: source resolution (couldn't fetch the chart), install/upgrade (Helm itself errored), or health checks (the release installed, but the workload never came up). Each layer writes a distinct condition, so reading the right one points straight to the fix.

Suspend is a real answer

"Stop the controller from overwriting my hotfix while I debug" has a named, auditable answer in both engines: flux suspend, or turning off auto-sync in Argo CD. Scaling kustomize-controller down to zero technically pauses reconciliation too, but it'll cost you the mark because it freezes the entire cluster and leaves no trace on the object.

More Kustomization fields and the per-resource annotations

  • retryInterval controls how quickly Flux retries after a failure (defaults to interval), while timeout caps build, apply, and health checks combined.
  • deletionPolicy takes MirrorPrune (default: delete managed objects when the Kustomization is deleted only if prune: true), Delete, WaitForTermination, or Orphan. Reach for Orphan when a namespace teardown would otherwise race the controller.
  • healthCheckExprs lets you write CEL current, failed, and inProgress rules per apiVersion/kind for CRDs that kstatus doesn't understand natively. dependsOn[].readyExpr does the same for dependencies.
  • patches, images, components, namePrefix/nameSuffix, and commonMetadata let the controller apply Kustomize overlays on the fly without modifying the repo.
  • kubeConfig.secretRef targets a remote cluster using a kubeconfig Secret; Flux's multi-cluster model is simply one Kustomization per remote cluster.

You can also place control annotations directly on manifests in git (not on the Kustomization itself). kustomize.toolkit.fluxcd.io/prune: disabled shields PVCs or namespaces from garbage collection. kustomize.toolkit.fluxcd.io/ssa takes Merge (preserve fields other tools add), IfNotPresent (create once and never overwrite, useful for cert-manager Secrets or webhook configs), or Ignore (skip the object completely). kustomize.toolkit.fluxcd.io/force: enabled recreates resources when immutable fields change (handy for Jobs, risky on StatefulSets). Under server-side apply, manual kubectl edits only survive if you pass --field-manager=flux-client-side-apply. Finally, triggering an out-of-band reconcile sets the reconcile.fluxcd.io/requestedAt annotation, which is all flux reconcile does under the hood.

Condition vocabulary and failure remediation

Ready reasons · HelmRelease install/upgrade remediation · drift detection · force and reset

Flux resources follow the kstatus convention: Ready summarizes overall state, Reconciling (negative polarity, only present while true) tells you work is active with reason Progressing or ProgressingWithRetry, and Stalled means the controller gave up until the spec changes. These reason strings are stable API, so exam prompts can quote them verbatim.

ObjectReady=True reasonsReady=False reasonsOther condition types
GitRepository / OCIRepository / BucketSucceededAuthenticationFailed · GitOperationFailed · OCIArtifactPullFailed · OCIArtifactLayerOperationFailed · VerificationErrorFetchFailed · IncludeUnavailable · StorageOperationFailed · SourceVerified · ArtifactInStorage
KustomizationReconciliationSucceededArtifactFailed · BuildFailed · HealthCheckFailed · PruneFailed · DependencyNotReady · ReconciliationFailedHealthy
HelmReleaseInstallSucceeded · UpgradeSucceeded · TestSucceededInstallFailed · UpgradeFailed · TestFailed · RollbackSucceeded · RollbackFailed · UninstallSucceeded · UninstallFailed · RetriesExceededReleased · TestSuccess · Remediated · Drifted (DriftDetected / NoDriftDetected)

Read that table as a diagnostic ladder. ArtifactFailed means the source isn't Ready or hasn't produced an artifact yet, so fix the source first. BuildFailed points at kustomize build (wrong path, invalid YAML, or a missing substituteFrom ConfigMap without optional: true). DependencyNotReady points you at an upstream Kustomization. ReconciliationFailed quotes the API server's rejection ("field is immutable", "admission webhook denied"). HealthCheckFailed means manifests applied cleanly but never became healthy before timeout. And on a HelmRelease, Ready=False with reason RollbackSucceeded isn't a contradiction: the upgrade failed, remediation rolled back to the last good revision, and the HelmRelease stays not-ready until you fix the chart or values.

HelmRelease failure handling, field by field

  • install.remediation.retries defaults to 0 (no retries; -1 retries forever), uninstalling between attempts. upgrade.remediation.retries defaults to strategy: rollback (or uninstall), and remediateLastFailure defaults to true whenever retries > 0 so the cluster settles on the last good revision instead of a broken one.
  • install.strategy.name and upgrade.strategy.name select either RemediateOnFailure (above) or RetryOnFailure with retryInterval (Flux 2.7+), which retries in place without rolling back.
  • test.enable: true runs Helm tests after install or upgrade; a failing test triggers remediation unless you set test.ignoreFailures: true.
  • install.crds defaults to Create, whereas upgrade.crds defaults to Skip. Helm refuses to upgrade CRDs by default, so a chart upgrade adding new CRD fields needs upgrade.crds: CreateReplace (or better yet, CRDs managed in a separate Kustomization).
  • driftDetection.mode can be disabled (default), warn (emits an event and sets the Drifted condition), or enabled (corrects drift via server-side apply). driftDetection.ignore accepts JSON 6902 paths and a target, serving as Flux's equivalent of Argo's ignoreDifferences for HPA replicas and webhook mutations.
  • Since Flux 2.8, helm-controller uses server-side apply by default (install.serverSideApply, upgrade.serverSideApply: auto), tracks everything it owns in status.inventory, and waits via kstatus polling rather than Helm's built-in wait.
  • valuesFrom[] pulls values from a ConfigMap or Secret using name, valuesKey (default values.yaml), optional targetPath to graft a single key, and optional. Inline values always override valuesFrom.

The three annotations behind flux reconcile

flux reconcile helmrelease X sets reconcile.fluxcd.io/requestedAt. Adding --force sets reconcile.fluxcd.io/forceAt, forcing a fresh install or upgrade even when nothing changed. Adding --reset sets reconcile.fluxcd.io/resetAt, clearing failure counters after RetriesExceeded; without it, an exhausted HelmRelease stays halted until the chart, values, or generation changes. Kustomizations only recognize requestedAt; fixing a stuck one means fixing the underlying cause.

install.retries: 0 is the default

If a chart's first install fails, Flux leaves it failed and won't retry until the spec changes, and only the Ready reason (InstallFailed) tells you. Set install.remediation.retries: 3 and upgrade.remediation.retries: 3 on anything you don't want to babysit, and keep flux reconcile hr X --reset in mind as the manual restart lever.

Every source publishes an Artifact (a tarball plus a revision such as main@sha1:9f2c1ab), and downstream consumers only ever read that artifact. That's why one failing source starves every Kustomization behind it with ArtifactFailed.

Image automation, the loop that closes CI to CD

  • ImageRepository scans a container registry path on an interval, authenticating via secretRef or a cloud provider.
  • ImagePolicy selects one winning tag from the scan using policy.semver.range: 5.0.x, alphabetical, or numerical, optionally paired with filterTags.pattern and an extract group for build tags like main-abc123-1699999999. The winner lands in status.latestRef (image, tag, and digest).
  • ImageUpdateAutomation rewrites matching files under update.path in the sourceRef GitRepository (which needs push credentials) wherever it finds a marker comment like image: ghcr.io/org/app:1.0 # {"$imagepolicy": "flux-system:app"} (append :tag or :name to update just that piece). It commits as git.commit.author and pushes to git.push.branch, which can be a separate branch so a PR gates production.

Notification controller

  • Provider (notification.toolkit.fluxcd.io/v1beta3) configures an outbound target: type (slack, msteams, discord, github, gitlab, generic webhook, and more), address, channel, and secretRef. The github and gitlab providers post commit statuses, putting a red X right on the commit that broke reconciliation.
  • Alert (v1beta3) wires events to a provider via providerRef, eventSeverity: info|error, eventSources (kind, name or *, namespace), inclusionList/exclusionList regexes, and extra eventMetadata.
  • Receiver (v1) accepts inbound webhooks: set type (github, gitlab, bitbucket, harbor, dockerhub, quay, gcr, nexus, acr, generic, generic-hmac, generic-oidc, or cdevents; note there's no gitea type because Gitea sends GitHub-format webhooks, so use github), events, secretRef for the webhook token, and resources to reconcile (a GitRepository, or ImageRepository objects for registry pushes). Expose the webhook-receiver Service yourself and hand the git server status.webhookPath to turn a one-minute poll into an instant pull.

Bootstrap and lockdown recap

flux bootstrap <provider> commits gotk-components.yaml and gotk-sync.yaml under --path, installs the controllers, and wires up the flux-system GitRepository and Kustomization so Flux manages itself from then on. Pass --components-extra to include the image controllers, or --token-auth for HTTPS token auth instead of a deploy key. Multi-tenant lockdown adds three controller flags (--no-cross-namespace-refs=true, --no-remote-bases=true, --default-service-account=default) plus spec.serviceAccountName: kustomize-controller on the flux-system Kustomization, applied as Kustomize patches in your bootstrap directory. Once locked down, any tenant Kustomization that omits serviceAccountName impersonates the namespace's unprivileged default account and fails with a Forbidden inside ReconciliationFailed.

Reflex

flux get all -A --status-selector ready=false filters straight to what's broken, and kubectl get fluxcd -A (the CRD category) lists every Flux object at once. From there, drill down with flux events --for Kustomization/x, flux logs --level=error -A, flux trace, and flux tree. Before pushing a commit, run flux build kustomization x --path ./dir to render locally and flux diff kustomization x --path ./dir to preview the exact cluster diff.

Self-check

answer before opening
Flux has no selfHeal setting. Why is drift still corrected?

Because a Kustomization re-applies its rendered manifests on every interval; drift correction is built into re-applying, not bolted on as a separate toggle. The trade-off: your drift window equals the interval, and tightening it adds load on the API server.

A Kustomization is Ready False. Name the three layers where it could have failed.

Source (the GitRepository isn't Ready due to auth, ref, or network), build (kustomize build failed on a bad path or invalid YAML), or apply/health (the API server rejected a manifest or health checks timed out). The conditions and flux logs name the exact layer, so read those before diving into the YAML.

How do you order "install CRDs, then the operator, then the tenant CRs" in Flux?

Chain three Kustomizations with dependsOn, and set wait: true (or explicit healthChecks) on each so downstream dependencies wait until resources are actually healthy. Without wait/healthChecks, dependsOn only orders the apply, not readiness.

What is postBuild.substitute for, and what is its Argo CD analog?

It injects per-cluster or per-environment variables into manifests right after kustomize build, pulling values inline or from ConfigMaps and Secrets. In Argo CD, you'd reach for Kustomize overlays, per-Application Helm values, or ApplicationSet template parameters; Flux just saves you from creating another overlay directory.

How does Flux stop one tenant's Kustomization from deploying cluster-admin-level resources?

Set spec.serviceAccountName so the controller impersonates that ServiceAccount during apply, capping the tenant's manifests at their own RBAC. Paired with blocking cross-namespace source references, that's Flux's multi-tenancy boundary and the structural counterpart to Argo CD's AppProject.

A HelmRelease shows Ready False with reason RollbackSucceeded. Is the release broken or healthy right now?

The running workload is healthy on the last good revision; the upgrade failed and remediation rolled it back. The HelmRelease stays not-ready because the cluster isn't running the desired new chart or values. Fix the chart or values in git, or if you resolved an out-of-band issue after hitting RetriesExceeded, run flux reconcile hr X --reset to clear the retry counters.

A chart upgrade adds a CRD field but the CR that uses it is rejected as unknown. Why, and which field fixes it?

spec.upgrade.crds defaults to Skip because Helm doesn't upgrade CRDs automatically, leaving the old schema live to prune or reject the new field. Set upgrade.crds: CreateReplace (alongside install.crds: CreateReplace), or ship CRDs in a separate Kustomization that the HelmRelease depends on.

Make a git push reconcile Flux immediately instead of at the next interval. Objects and the field you hand to the git server?

Create a Receiver with the right type (github, gitlab, or generic; use github for Gitea), events: [push], a secretRef holding a shared token, and resources listing your GitRepository. Expose the notification-controller's webhook-receiver Service, then configure your git webhook with that host plus status.webhookPath and the same secret token.

After multi-tenant lockdown, a tenant's Kustomization fails with Forbidden. What did they leave out?

spec.serviceAccountName. Once --default-service-account=default is enabled, any Kustomization or HelmRelease that omits an explicit account impersonates the namespace's unprivileged default ServiceAccount. The API server rejects the apply, and the Ready condition shows ReconciliationFailed with the Forbidden error. The platform team needs to provision a tenant ServiceAccount and RoleBinding for them to reference.
