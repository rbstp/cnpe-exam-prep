Progressive delivery is a Deployment with a feedback loop: send the new version a slice of traffic, measure whether it behaves worse than stable, and promote or roll back based on real evidence.

Replica weight vs route weight

Without a traffic provider, Argo Rollouts fakes a 20% canary by running 20% of the pods as canary replicas. That split is purely statistical, granularity is limited by replica count, and every client is still load-balanced across the Service. Add a traffic provider (Istio, Gateway API, NGINX, ALB), or use Flagger driving a mesh, and you get true route weights: exact percentages independent of replica count, plus header and cookie routing.

Argo Rollouts

a Deployment with spec.strategy swapped

A Rollout is a drop-in stand-in for a Deployment (same pod template, same selector rules) with a much richer spec.strategy. Under the hood it manages ReplicaSets the exact same way a Deployment does (one stable, one canary), which is why kubectl get rs during a rollout is so easy to read.

strategy:
  canary:
    steps:
      - setWeight: 20
      - pause: { duration: 60s }      # omit duration → wait for a human promote
      - analysis:                     # run an AnalysisTemplate, act on the result
          templates: [{ templateName: success-rate }]
      - setWeight: 50
      - pause: {}
    # optional: canaryService / stableService / trafficRouting for real weights

That step list is almost the entire grammar: setWeight, pause, and analysis, plus setCanaryScale and experiment steps. Blue-green swaps the step list for two Services and a cutover:

strategy:
  blueGreen:
    activeService: demo-active
    previewService: demo-preview
    autoPromotionEnabled: false       # wait for `promote`
    scaleDownDelaySeconds: 30         # keep the old RS warm for instant rollback

AnalysisTemplate is the measurement half: a list of metrics, each pairing a provider (Prometheus, Datadog, a Kubernetes Job, or a web request) with an interval, a successCondition or failureCondition, and budgets like failureLimit, count, and inconclusiveLimit. An AnalysisRun is a single execution of that template, and its status logs every measurement, making it the first place to check when a rollout aborts and you want to see which number killed it. You can run analyses inline as a canary step, continuously in the background for the entire rollout, or as pre-promotion and post-promotion gates in blue-green.

An erroring analysis isn't a passing analysis

When a metric provider returns an error (bad PromQL, missing series, unreachable Prometheus), the measurement records Error, and errors have their own budget: exceed consecutiveErrorLimit (4 in a row by default) and the analysis aborts the rollout just as hard as blowing failureLimit. That means a broken query can kill a perfectly healthy release. Always inspect the AnalysisRun's measurements before blaming the app. In production, treating a blind metrics pipeline as a blocker is a feature, not a bug.

abort ≠ undo

abort halts the rollout and sends 100% of traffic back to the stable ReplicaSet, but spec still asks for the bad image, so status stays Degraded and it'll retry if you poke it. undo reverts the spec itself. When an exam asks you to "safely roll back", do both: abort to stop the bleeding, undo to make desired state honest. And under GitOps, the real form of undo is a git revert commit, or Argo CD will just re-apply the broken image on the next sync.

Flagger, for contrast

the mesh-native inversion

Flagger flips the authoring model upside down. You keep writing an ordinary Kubernetes Deployment, and Flagger's Canary CR generates everything else around it: a <name>-primary Deployment that actually serves production traffic, the <name>, <name>-primary, and <name>-canary Services, and the mesh or gateway routing objects. When you change the Deployment's image, Flagger shifts real route weights while running its analysis, with no Rollout CRD required.

Read kubectl get deploy carefully during a Flagger task

Between rollouts, Flagger scales your original Deployment down to zero and serves everything from <name>-primary. Your original Deployment is just the template, not the live workload. Seeing podinfo 0/0 sitting next to podinfo-primary 2/2 means Flagger is working normally; mistaking it for a broken deployment is the classic first-timer panic.

AspectArgo RolloutsFlagger
What you authorA Rollout (replaces your Deployment)A Canary alongside an untouched Deployment
Traffic controlReplica ratio, or a traffic router plugin/providerMesh or gateway route weights (except L4 blue/green)
AnalysisAnalysisTemplate + AnalysisRunanalysis.metrics + webhooks (load test, acceptance, confirm-rollout)

Flagger's webhooks fill the gaps that metrics alone can't cover: confirm-rollout (gate before starting), pre-rollout (acceptance checks against the canary), rollout (runs every step, typically a load generator), confirm-promotion, and post-rollout. A canary receiving zero requests generates zero metrics, so a load-test webhook is what makes analysis meaningful in a lab.

Lab caveat

The kind-mesh cluster doesn't run Prometheus, and make mesh points Flagger at a nonexistent metrics URL, so the built-in request-success-rate check can't pass there. Drive your analysis with webhooks only (a load-test webhook hitting flagger-loadtester.test, plus an optional pre-rollout acceptance gate). Every Flagger mechanic you're practicing (the Canary spec, generated objects, weight shifting, and events) is the real deal.

How to think about it on exam day

and what makes an analysis trustworthy
  • Pick the strategy from the constraint. Can't afford double capacity → canary. Need instant rollback and an atomic cutover → blue-green. Need to test behavior on a specific user segment → A/B with header routing (which requires L7).
  • Stateful and schema changes break both. Two versions run side by side, so your database schema has to tolerate both simultaneously. Expand-and-contract migrations are the standard answer.
  • Measure what users actually feel. Track error rate and latency percentiles over the canary's own series, not CPU usage or pod restarts. And double-check that your query isolates the canary: an analysis accidentally querying the stable pods will happily promote a broken release.
  • Watch sample size. At three requests a minute, a 20% canary is measuring noise. Either generate synthetic load (Flagger's loadtester or your own) or stretch the interval.
  • Remember how GitOps interacts with rollbacks. The Rollout or Canary lives in git like any other manifest, while promotion state stays in the cluster. If you abort a bad Rollout without reverting the git commit, Argo CD's next sync will re-apply the bad image.

Fields that decide the outcome

Rollouts analysis limits · blue-green extras · traffic routers · Flagger analysis, phases and strategy selection

Argo Rollouts: the analysis budget

  • failureLimit defaults to 0, meaning a single failed sample fails the analysis and aborts the rollout, so set it intentionally. consecutiveSuccessLimit (1.8+) requires N passes in a row; paired with failureLimit: -1, it turns analysis into "wait until the metric settles green".
  • inconclusiveLimit tracks samples that matched neither successCondition nor failureCondition. An Inconclusive run pauses the rollout for human review instead of aborting.
  • count and interval control total sample count; omitting count runs continuously until the rollout finishes (background analysis). Use initialDelay per metric or analysis.startingStep on the Rollout so the canary gets warm traffic before being judged.
  • Analysis hooks into four places: canary.steps[].analysis (inline, blocks that step), canary.analysis (background across the rollout), blueGreen.prePromotionAnalysis (gates the selector flip), and blueGreen.postPromotionAnalysis (aborts and flips back if it fails). Pass parameters via args, or use ClusterAnalysisTemplate to share templates across namespaces.
  • The Prometheus provider takes address, query, and optional rangeQuery. Results come back as a vector, so conditions check result[0] (or all(result, # < 1000) for range queries). Other providers include web (JSONPath over HTTP), job (Kubernetes Job exit status), datadog, newrelic, wavefront, graphite, influxdb, skywalking, and custom metric plugins.
  • dryRun records measurements without influencing the rollout, and measurementRetention keeps more than the default 10 samples in status.

Traffic routers and header routing

canary.trafficRouting accepts one provider block: istio (a VirtualService and route names, or DestinationRule subsets), nginx (stableIngress), alb, smi, traefik, apisix, or plugins like argoproj-labs/gatewayAPI (with httpRoute and namespace, driving HTTPRoute backendRefs weights on any conformant gateway such as Cilium, Envoy Gateway, kgateway, or Traefik). Whenever a router is configured, both canaryService and stableService are mandatory. A router also unlocks extra steps: setHeaderRoute (matching headerName by exact, prefix, or regex so testers hit the canary at 0% public weight), setMirrorRoute (Istio traffic shadowing), and setCanaryScale (decoupling canary replicas from traffic weight). Any route Rollouts creates must be declared in trafficRouting.managedRoutes so it gets cleaned up on completion or abort. Note that Rollouts 1.9 and 1.10 add new integrations exclusively via traffic-router and canary-step plugins; core no longer accepts new built-in providers.

Flagger: analysis fields, phases, strategy selection

Flagger uses a single Canary CR and infers the delivery strategy from whichever spec.analysis fields you populate:

You setYou getTiming
stepWeight + maxWeight (or stepWeights list)Progressive canary traffic shift (stepWeightPromotion makes final promotion gradual too)Minimum interval × (maxWeight / stepWeight); rolls back after interval × threshold
match (headers or cookie regex) + iterationsA/B testing: matched users go straight to the canary for the whole run (maxWeight and stepWeight are ignored)interval × iterations
iterations onlyBlue-green: validates the canary with conformance/load webhooks, then flips traffic all at once (works with provider: kubernetes at L4, no mesh needed)interval × iterations
mirror: true (+ mirrorWeight)Blue-green paired with traffic shadowing (Istio or Gateway API)Same as above
skipAnalysis: truePromotes as soon as the canary pods are ready (your emergency bypass lever)Immediate
  • threshold sets how many failed checks (metrics or webhooks) trigger rollback (default 1), interval defaults to 60s, and progressDeadlineSeconds (default 600) rolls back a canary whose pods never become ready.
  • Built-in metrics are request-success-rate (thresholdRange.min in percent) and request-duration (thresholdRange.max in milliseconds, P99). For custom queries, create a MetricTemplate (supporting prometheus, datadog, cloudwatch, newrelic, graphite, influxdb, dynatrace, keptn, splunk, or external metrics, with {{ namespace }}, {{ target }}, and {{ interval }} variables) and reference it via templateRef with a thresholdRange.
  • Configure service.port, targetPort, and portDiscovery (plus service.gatewayRefs and hosts for Gateway API). Your target Deployment must use a single-label selector (app, name, or app.kubernetes.io/name). Flagger automatically tracks and clones mounted ConfigMaps and Secrets to -primary unless you opt them out with flagger.app/config-tracking: disabled.
  • status.phase walks through Initializing → Initialized → (Waiting if gated by a confirm-rollout webhook) → Progressing → (WaitingPromotion) → Promoting → Finalising → Succeeded or Failed. Use kubectl wait canary/x --for=condition=promoted as a scriptable gate, suspend: true to freeze the Canary, and revertOnDeletion: true to restore your original Deployment and Service if the Canary is deleted.
  • Extra webhook types include confirm-traffic-increase (gate every weight step), rollback (returning 2xx aborts the canary on demand), and event (receives every Flagger event as JSON). Any non-2xx response from a rollout webhook counts against threshold, and total rollout webhook timeouts must fit inside interval.
Defaults that bite

In Argo Rollouts, failureLimit: 0 means a single bad measurement aborts the release. In Flagger, threshold: 1 rolls back on one failed check, and leaving maxWeight unset steps traffic all the way to 100%. Also remember that both tools promote a brand-new first deployment straight through without analysis, since there's no stable baseline to compare against; don't mistake that for broken analysis.

A stock rolling update has zero traffic shaping and zero metric analysis: readiness probes are the only gate, and the Service routes traffic to new pods the instant they turn Ready. Every progressive strategy improves on that baseline. Remember, under GitOps, "undo" means a git revert commit because kubectl rollout undo is live drift.

Choosing

Constraint in the scenarioStrategyWhat it needsHow rollback works
"can't afford double capacity", "measure before exposing everyone"CanaryUser-facing metrics (success rate, latency), a router for exact weights, and enough traffic for signalShift weight back; only the canary slice was exposed
"instant cutover", "instant rollback", "test the new version privately first"Blue-green2× capacity during cutover, a preview Service or hostname, and backwards-compatible schemaFlip the selector back while the old stack stays warm for scaleDownDelaySeconds

Two practical questions separate Argo Rollouts from Flagger. First, what does the app team want to author: a Rollout (Argo Rollouts replaces the Deployment and works even without a mesh via replica counts) or a plain Deployment with a Canary beside it (Flagger needs a mesh or gateway except for L4 blue-green)? Second, how do you want promotion driven: a step list with manual promote pauses, or an automated threshold loop with optional confirmation webhooks? Both plug into Argo CD and Flux identically: the Rollout or Canary lives in git, while promotion decisions stay out of band.

How this gets tested

"Route requests carrying header X-Beta: true to the new version and nobody else" is A/B, not a weighted canary: use setHeaderRoute with a traffic router in Rollouts, or analysis.match + iterations in Flagger. "Send 10% of traffic, then 50%, then 100%, only if error rate stays under 1%" is a canary with analysis, and the grader checks the weight steps and metric threshold in the CR, not a pretty dashboard.

When a measurement satisfies neither its success condition nor its failure condition, Argo Rollouts doesn't guess: it marks the run Inconclusive (neither Successful nor Failed) and pauses the rollout for a human decision. Remember this third outcome, because it's the one people forget to alert on.

kubectl apply -f - <<'EOF'
apiVersion: argoproj.io/v1alpha1
kind: AnalysisTemplate
metadata: { name: undecided, namespace: team-a }
spec:
  metrics:
    - name: undecided
      interval: 15s
      count: 1
      # vector(1) meets neither condition, so nothing can decide and the
      # measurement is Inconclusive. Leave both conditions out and Argo
      # Rollouts 1.10 counts the measurement Successful instead.
      successCondition: result[0] > 1
      failureCondition: result[0] < 1
      provider:
        prometheus:
          address: http://prometheus-kube-prometheus-prometheus.monitoring.svc:9090
          query: vector(1)
EOF

Route weights send a percentage of everyone's traffic to the new version. A header route sends 100% of one tester's traffic to it while leaving real users at 0%. Since header routing needs a mesh, we run this on kind-mesh and install Argo Rollouts there first. Notice the --server-side flag: a plain client-side apply rejects these CRDs because their last-applied-configuration annotation blows past Kubernetes's 256 KB annotation limit.

Self-check

answer before opening
You set setWeight: 10 with 3 replicas and no traffic provider. What actually happens?

Argo Rollouts can only work in whole pods, so it spins up 1 canary pod alongside the stable pods, giving you roughly a 25–33% split instead of 10%. Exact percentages require a traffic router (Istio, Gateway API, NGINX) or a lot more replicas.

A canary aborted and the AnalysisRun shows measurements in phase Error. What do you check?

Check the metric query and provider first: wrong metric name, no traffic/data yet, unreachable Prometheus, or a label selector matching nothing. Errors burn through consecutiveErrorLimit (default 4), so a broken query aborts rollouts just like a broken release; always inspect the measurement error before blaming the app.

Blue-green with autoPromotionEnabled: false: which Service points where, before and after promote?

Before promotion, the active Service selects the old ReplicaSet's rollouts-pod-template-hash while the preview Service selects the new one. After promotion, both select the new hash, and the old ReplicaSet stays warm for scaleDownDelaySeconds so rolling back is a single selector flip.

Argo CD manages your Rollout. You abort a bad canary. What happens next, and what should you do?

Because git still names the bad image, Argo CD's next sync re-applies it and kicks off the broken rollout all over again. Revert the commit (or pin the previous tag back): abort stops the bleeding live, while git controls desired state.

Name two things that make progressive delivery unsafe regardless of tooling.

Breaking database or API changes that both versions can't handle at the same time (solve with expand-and-contract migrations and backwards-compatible contracts), and metrics too sparse or coarse to catch regressions inside the canary window. Bonus third: an analysis query that accidentally measures the stable pods instead of the canary.

An AnalysisRun ended Inconclusive and the rollout stopped. Did it abort?

No. An Inconclusive run pauses the rollout at its current step and waits for a human to run promote or abort. It triggers when more than inconclusiveLimit samples match neither successCondition nor failureCondition (note that in Rollouts 1.10, omitting both conditions counts as Successful). Failed aborts, repeated Errors abort, and Inconclusive asks a human.

Flagger: you set match on a header and also stepWeight/maxWeight. What runs?

A/B testing. Whenever Flagger sees an HTTP match rule, it ignores maxWeight and stepWeight and runs iterations rounds sending matched traffic to the canary. Drop match if you want a weighted canary, or keep only iterations for blue-green.

What does progressDeadlineSeconds do on a plain Deployment, and what does it not do?

After 600 s (default) with no progress, Kubernetes sets Progressing=False with reason ProgressDeadlineExceeded, the exact condition Argo CD maps to Degraded. It does not roll back or pause anything, though the old ReplicaSet keeps serving with whatever pods maxUnavailable left running. Argo Rollouts' progressDeadlineAbort: true is what adds automatic rollback.

Why must canaryService and stableService exist when you add trafficRouting to a Rollout?

Because the traffic router splits requests between two distinct Services, so Rollouts needs one Service whose selector it pins to the canary ReplicaSet and one for stable (by injecting rollouts-pod-template-hash into each). Without a router, traffic splits by replica count behind one Service, so neither field is required.
