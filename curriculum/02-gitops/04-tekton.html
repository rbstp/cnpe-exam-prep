Tekton's core idea is simple: a pipeline isn't config for a separate CI server, it's Kubernetes resources executed as pods. Everything else is vocabulary, and debugging CI becomes debugging pods, which you already know how to do.

Orientation

competency 2.2 · CI/CD pipelines integrated with Kubernetes

A Task is a sequence of steps (containers sharing one pod). A Pipeline wires Tasks together. Running either means creating a TaskRun or a PipelineRun. That's the entire object model, and almost every failure you'll ever debug comes down to a container in a pod that exited non-zero.

Pipeline ──instantiated by──▶ PipelineRun
   └─ tasks[]                    └─ creates one TaskRun per task
        └─ Task                       └─ creates one pod
             └─ steps[]                    └─ one container per step, run in order
                                              sharing /workspace volumes
Why "steps share a pod" matters

Steps run sequentially inside the same pod, so they share volumes and land on the same node; that's how the clone step's checkout reaches the build step. The catch is that Kubernetes sums container resource requests across all steps even though they run one at a time (task-level computeResources on the TaskRun exists to claw that overhead back). It also means steps can't be scheduled onto different nodes, and everything in a Task lives or dies together. Tasks, by contrast, run in separate pods and can execute in parallel.

Params support types (string, array, object) and defaults. Results are written by a step to $(results.<name>.path) and are deliberately tiny: because they travel through the TaskRun's status, use them for a digest or a count, never a build log. Workspaces get bound at run time by the PipelineRun to an emptyDir (per-pod, lost between tasks), an existing persistentVolumeClaim (shared, you manage its lifecycle), or a volumeClaimTemplate (shared, created and cleaned up per run; usually the right default). You can also back a workspace with a ConfigMap or Secret, which is a clean way to hand credentials to a step.

Ordering surprises people exactly once

Tasks with no runAfter and no shared results run in parallel. Consuming another task's result creates an implicit dependency, which means removing a result reference can accidentally parallelize a pipeline that used to run sequentially. Whenever order matters, state it explicitly with runAfter instead of leaning on a data dependency someone might refactor away.

Identity, credentials, and registries

Each pipeline pod runs under a ServiceAccount (taskRunTemplate.serviceAccountName on the PipelineRun). In real clusters, that SA carries registry credentials via an imagePullSecret or a kubernetes.io/dockerconfigjson Secret linked for Tekton's credential init. Our lab registry skips auth, so kaniko pushes straight to it with --insecure.

One registry, two names

The pipeline pushes to kind-registry:5000/demo:v1 because it runs inside the cluster, where localhost points back at the pod itself. From your host terminal, that exact same registry answers at localhost:5001. Keep those two names straight: they come right back in section 5.6 when Kyverno verifies a signature from inside the cluster.

Where Tasks come from

make cicd pre-installs the git-clone and kaniko catalog tasks, and the trivy-scan task lands when you apply the lab example. Run tkn task list to see what's available. Modern Tekton also fetches task definitions on the fly using resolvers (git, hub, or bundles for OCI images holding task YAML) via taskRef.resolver. That's how a platform team distributes a shared, versioned task library without copy-pasting YAML into every repo, so be ready to describe it even if you don't configure one by hand.

Triggers: from a git push to a run

Three CRDs connect a Gitea push event to a live pipeline run:

  • EventListener: an HTTP-serving pod that receives the incoming webhook.
  • TriggerBinding: pulls fields out of the JSON payload (like $(body.repository.clone_url) and $(body.after)).
  • TriggerTemplate: stamps out a fresh PipelineRun populated with those extracted values.
  • Plus interceptors: filter by event type, validate the webhook secret, or evaluate a CEL expression before anything triggers. Skip the interceptor and your EventListener will happily build anything anyone POSTs to it.

A StepAction is the reusable building block one level below a Task, encapsulating image, command or script, args, env, params, results, workingDir, securityContext, and volumeMounts. A step pulls it in with ref: { name: x } (or ref.resolver for a remote one) and can't set any of those fields itself; doing so triggers a validation error at admission. StepActions are stable (check kubectl api-resources | grep stepaction for the served version on your cluster). For the exam, know why they exist: a platform team ships one vetted kaniko-build StepAction, and app teams compose Tasks from it without copying container boilerplate.

Tekton Chains handles the supply-chain side. It watches completed TaskRuns and PipelineRuns, signs them along with any type-hinted image results (IMAGE_URL and IMAGE_DIGEST results, or artifacts.outputs) using a key from the signing-secrets Secret in tekton-chains (cosign, x509, or KMS), and generates an in-toto attestation in slsa/v1 or slsa/v2alpha4 format. It stores the signature and attestation in the OCI registry beside the image, in Tekton annotations, or in a bucket, then marks the run chains.tekton.dev/signed: "true". Formats, storage backends, and signers live in the chains-config ConfigMap (artifacts.taskrun.format, artifacts.oci.storage, transparency.enabled). Section 5.6 verifies those signatures at admission; the key security property to remember here is that the build pod itself never holds the signing key.

Tekton vs Argo Workflows

Both execute DAGs of containers, and both sit on the exam's tool list. Keep the distinction crisp: Tekton is purpose-built for CI (building, testing, and publishing artifacts from git events with a CI-focused task catalog), whereas Argo Workflows (section 3.4) is general-purpose orchestration (provisioning sequences, scheduled batch jobs, data pipelines). Their capabilities overlap, but their sweet spots differ, and section 3.6 will ask you to defend the choice.

TaskRun reasons add the pod-level failure modes: TaskRunTimeout, TaskRunImagePullFailed, PodEvicted, StepOOM (an OOMKilled step fails the run even if it exited 0), InitContainerOOM, StepFailed, and ToBeRetried (a retry is queued; earlier attempts stay in status.retriesStatus). Individual step exit codes and terminationReason values live under status.steps[].

Timeouts

  • spec.timeouts.pipeline caps the whole run (defaulting to global default-timeout-minutes, 60m), timeouts.tasks caps all non-finally tasks together, and timeouts.finally caps finally tasks. Tekton validates that pipeline >= tasks + finally. Setting "0" disables a clock (which requires pipeline: "0" too).
  • Per-task clocks live at pipeline.spec.tasks[].timeout or at run time under taskRunSpecs[].timeout. If timeouts.tasks fires, finally tasks still get to run as long as timeouts.finally leaves room.

Canceling and pausing, by setting spec.status

  • Cancelled: kills running TaskRuns, deletes pods, drops retries, and skips pending finally tasks.
  • CancelledRunFinally: kills running TaskRuns, but lets finally tasks run so cleanup and notifications still execute.
  • StoppedRunFinally: lets already-running TaskRuns finish (including retries), schedules no new tasks, and then runs finally.
  • PipelineRunPending: creates the run in a paused state without starting it (handy for manual gates or quota queues); clearing the field kicks it off.

Control flow fields

  • retries: N on a pipeline task re-runs failed TaskRuns automatically, exposing $(context.pipelineTask.retries) and retry-count inside the task.
  • onError: continue on a pipeline task lets the pipeline keep going after a failure instead of the default stopAndFail. On an individual step, onError: continue lets subsequent steps run and exposes $(steps.<name>.exitCode.path).
  • when evaluates input, operator: in|notin, and values (plus a CEL form like cel: "'$(params.env)' == 'prod'" behind a feature flag). Watch out: guarding a task doesn't automatically guard its downstream dependents. Cascade the when expression or wrap them in a sub-pipeline.
  • Inside finally, $(tasks.<name>.status) evaluates to Succeeded, Failed, or None (skipped), and $(tasks.status) rolls up to Succeeded, Completed, Failed, or None. Note that finally tasks run in parallel and can't be ordered with runAfter.
  • matrix.params fans a single pipeline task out across every parameter combination (capped at 256 by default via default-max-matrix-combinations-count). Child TaskRuns are named <run>-<task>-<n>, and array results from a matrix task are consumed with $(tasks.x.results.y[*]).
  • Results travel inside the container termination message, which Kubernetes caps at 4096 bytes per step (including Tekton's metadata). If you hit "Termination message is above max allowed size", either shrink the result or enable the results-from: sidecar-logs feature flag.
How this gets tested

"The pipeline must always publish a report even when the build fails, and a failed scan must not stop the report" maps cleanly to two fields: put the report task in finally, and either give the scan task onError: continue or let the report inspect $(tasks.scan.status). And "stop the running pipeline while letting cleanup finish" means patching spec.status: CancelledRunFinally, not deleting the PipelineRun.

Self-check

answer before opening
Two tasks in a pipeline run at the same time and you did not expect it. Why?

There's no runAfter and no result dependency linking them, so Tekton runs them concurrently by default. Ordering only comes from an explicit runAfter or consuming another task's result; list order in the YAML means nothing.

How do files get from the clone task to the build task, and what happens if you bind the workspace to an emptyDir?

Through a shared workspace backed by a PVC or volumeClaimTemplate mounted into both tasks. Because an emptyDir lives inside a single pod, each task gets its own brand-new empty directory and the build step sees nothing, a classic "why is my workspace empty?" trap.

Where do you put a step that must run whether the pipeline passed or failed?

In spec.finally. Those tasks run after every main task finishes regardless of outcome, and they can inspect $(tasks.status) to branch. Cleanup, notifications, and teardown belong there rather than as a trailing runAfter task that gets skipped on failure.

Why does the pipeline push to kind-registry:5000 and not localhost:5001?

Because the build runs inside a pod where localhost is the pod's own network namespace. In-cluster pods reach the registry via its CoreDNS name (kind-registry:5000), while your host reaches the same store over its published port (localhost:5001). Different hostnames, identical registry and digests.

Your EventListener is Ready and a push produces nothing. Diagnostic ladder?

Walk the chain in order: did Gitea actually deliver the webhook (check its delivery log)? Did the EventListener receive it (check its pod logs)? Did an interceptor drop it (event type, secret mismatch, or CEL rule)? Did the TriggerBinding extract every field the TriggerTemplate expects (a missing param fails PipelineRun creation)? Each rung leaves its own error.

A PipelineRun shows status True with reason Completed rather than Succeeded. What happened?

The run passed, but one or more tasks were skipped by a when expression; check status.skippedTasks to see which ones and why. Scripts or graders checking reason == Succeeded will trip on this, so check status == "True" on the Succeeded condition instead.

Which spec.status value stops new tasks, lets running ones finish and still runs finally?

StoppedRunFinally. By comparison, CancelledRunFinally kills in-flight TaskRuns before running finally, and plain Cancelled kills everything and skips finally. PipelineRunPending goes the other way: it creates a run parked until you clear the field.

A step referencing a StepAction also sets image. What happens, and why is the design that way?

Admission rejects it with a validation error: a step using ref can't set image, command, args, script, env, or volumeMounts, because the StepAction owns the execution details while the step just wires params and results. That boundary lets a platform team ship one vetted StepAction and let tenants compose Tasks without touching container config.
