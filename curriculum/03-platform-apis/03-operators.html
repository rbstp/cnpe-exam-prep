Orientation

competency 3.3 · operators for automation and integration

Almost every layer of this lab is an operator reconciling CRDs: Crossplane, Kyverno, Prometheus Operator, Trivy Operator, CloudNativePG, Argo CD, and Flux. Whenever an unfamiliar operator lands in front of you on exam day, ask the exact same four questions: what kind does it watch, what does it create, what does its status say, and where do its logs live?

Level-based, not edge-based

A controller watches a kind and runs the same loop for each object: read actual state, compare it with desired spec, take one step toward convergence, write status, and requeue if needed. Because it acts on the current state it sees rather than the specific event that woke it, missed events don't matter, duplicate events are harmless, and the loop is safe to re-run anytime. That's why deleting an operator-owned pod doesn't "reset" anything; the next reconcile simply recreates it without knowing or caring who deleted it.

The conventions that make operators readable

status · generation · owners · finalizers

1 · Status conditions

Standard conditions carry type, status (True/False/Unknown), reason (machine-readable CamelCase), message (human-readable), lastTransitionTime, and observedGeneration. Ready is the roll-up summary; the other conditions pinpoint which phase is stuck. Good operators pair those with Kubernetes Events so you also get timestamps and retry counts.

2 · observedGeneration versus metadata.generation

If those two numbers don't match, the controller hasn't processed your latest edit yet; whatever status says is describing an older spec. Checking this first saves you from chasing stale errors, and almost nobody remembers to do it. Just keep in mind that metadata.generation only tracks spec changes when the CRD enables the status subresource; without it, every status write bumps generation too and observedGeneration stops meaning anything (section 3.2).

3 · Owner references

Resources created by an operator carry ownerReferences pointing back to their parent CR. That single field answers "what keeps recreating this?", drives cascade deletion (foreground, background, or orphan), and lets you map an entire operator's object tree without reading a line of docs. Two hard Kubernetes rules: an owner must live in the same namespace (or be cluster-scoped), and a namespaced object can never own a cluster-scoped one, the exact constraint behind Crossplane's architecture in section 3.5.

4 · Finalizers

A deleted object hangs in Terminating while a finalizer sits on it, either because the controller is actively running teardown logic or because the controller is dead and can't clear it. A stuck namespace or CR almost always comes down to finding whose finalizer is attached and checking why that controller isn't running. Stripping a finalizer by hand is your last resort: it unblocks deletion, but leaks whatever external cleanup (cloud volumes, databases, DNS records) the controller was supposed to perform. Make that trade deliberately.

Vocabulary around operators

worth knowing as words
  • Operator capability levels (the OperatorHub model): 1 Basic Install → 2 Seamless Upgrades → 3 Full Lifecycle (backup, failover) → 4 Deep Insights (metrics, alerts) → 5 Auto Pilot (auto-scaling, auto-tuning). Great yardstick whenever a scenario asks whether an operator is worth adopting.
  • OLM (Operator Lifecycle Manager): installs and upgrades operators from curated catalogs. Not installed in this lab, but know how it works (details below).
  • Kubebuilder / Operator SDK / controller-runtime: the Go scaffolding behind most Kubernetes operators. make tools puts kubebuilder on your PATH if you want to scaffold a toy controller (kubebuilder init, kubebuilder create api) to see the machinery, though writing Go is outside CNPE scope.
  • Reconcile loop hazards worth naming: hot loops (a controller whose status write re-triggers itself endlessly), requeue backoff, leader election (why multi-replica operator Deployments use a Lease), and informer cache staleness right after a write.
  • Operator vs controller vs webhook: a controller reconciles; an operator is a controller packed with domain-specific operational knowledge and CRDs; a webhook intercepts API writes synchronously. Their failure modes are night and day: a dead controller just pauses convergence, whereas a dead webhook with failurePolicy: Fail blocks every matching write outright.
Integration is a competency word

"Operators for platform automation and integration" means plugging an operator cleanly into the rest of your platform: its CRs are managed via GitOps, its metrics are scraped (ServiceMonitor/PodMonitor), its connection Secrets flow to workloads, its CRs pass through admission policy like any built-in object, and its API sits behind a thinner developer-facing abstraction (Crossplane, kro, or a Backstage template). Naming all five gives you a complete exam answer.

Inside a controller: controller-runtime in one page

manager · reconciler · For, Owns, Watches · predicates · requeue · leader election · the RBAC it needs

You won't write a line of Go on the exam, yet almost every operator you troubleshoot is built on the same dozen controller-runtime primitives, and their names pop up constantly in logs, flags, and Deployment specs. Recognizing them turns "the operator is acting weird" into "the informer cache is stale" or "it lost its leader Lease".

The pieces

  • Manager: the process hosting shared informer caches, a Kubernetes client, metrics (:8080), health probes (:8081, /healthz and /readyz), an optional webhook server (:9443), and the controllers themselves. Deployment flags like --leader-elect, --metrics-bind-address, --health-probe-bind-address, and --watch-namespace all configure the manager.
  • Controller: a deduplicating work queue of namespace/name keys feeding a Reconciler with a single method, Reconcile(ctx, req) (Result, error). Because it only receives a key (never the triggering event), reconciliation is level-based by construction. MaxConcurrentReconciles defaults to 1, which explains why an operator managing hundreds of CRs can look sluggish.
  • Builder: For(&MyKind{}) watches the primary CR and enqueues its key. Owns(&appsv1.Deployment{}) watches owned child kinds and enqueues the owner found via ownerReferences (with controller: true). Watches(...) maps any other object (like a referenced Secret) onto the CR keys to reconcile. Owns is why deleting an operator's Deployment or Secret sparks an instant rebuild, and why ownerReferences maps everything the operator manages.
  • Predicates filter watch events before they hit the work queue: GenerationChangedPredicate drops status-only updates where metadata.generation didn't move, alongside LabelChangedPredicate, AnnotationChangedPredicate, and custom filters. When an operator either ignores a label change or spins in a hot loop, a predicate is usually the culprit.
  • Result: returning Result{} means done; Result{RequeueAfter: 5*time.Minute} schedules a periodic poll (common for external APIs); returning an error triggers exponential backoff from the workqueue rate limiter (starting at 5 ms, doubling up to ~16 minutes, within a 10/s global cap). Log lines like "Retrying in 1m4s" are that exact backoff.
  • Cache: reads hit local informers rather than etcd directly, so reading right after a write can briefly return a stale copy. Good reconcilers handle that gracefully on the next pass instead of crashing.
  • Leader election: uses a Lease in the operator's namespace named by LeaderElectionID (defaults: 15 s LeaseDuration, 10 s RenewDeadline, 2 s RetryPeriod). Standby replicas stay warm and idle until they win the lease. Run kubectl get lease -n <operator-ns> and read holderIdentity to see which pod is actually reconciling.

Admission webhooks inside operators

Many operators install their own ValidatingWebhookConfiguration and MutatingWebhookConfiguration for defaulting, cross-field validation beyond CEL, or version conversion. Those webhooks need TLS certs, usually via cert-manager's cert-manager.io/inject-ca-from annotation or a self-signed key pair patched into caBundle. When the operator pod dies while its webhook carries failurePolicy: Fail, every write to its CRDs fails with "failed calling webhook" (including your GitOps controller's syncs). Check webhooks first whenever an entire API group turns read-only during an operator upgrade.

Reflex

Check who leads (kubectl -n <op-ns> get lease), grep logs for RBAC and backoff (kubectl -n <op-ns> logs deploy/<op> | grep -i -E 'forbidden|error'), and check for blocking webhooks (kubectl get validatingwebhookconfiguration -o wide) alongside the four-command diagnosis above. Restarting the operator pod comes after those checks, never before.

The three Operator SDK flavors map cleanly to that ladder: a Helm operator turns a CR spec into Helm values (zero custom Go logic, Levels 1–2); an Ansible operator runs a playbook or role per reconcile (reaches Level 3, slower loops); and a Go operator uses controller-runtime directly (no ceiling). When an exam scenario asks "should we adopt this operator or manage the database ourselves?", match the operator's capability level to the workload: a Level 1 operator for a stateful database buys you almost nothing on day 2.

Status conditions, the convention in full

  • metav1.Condition standardizes six fields: type (CamelCase, or domain/CamelCase for third parties), status (True/False/Unknown), reason (required CamelCase machine code), message (human-readable), lastTransitionTime (only moves when status flips), and observedGeneration. The slice uses listType: map keyed by type.
  • Condition names describe an observed state using an adjective or past participle (Ready, Available, Succeeded, Degraded), not an action verb like Deploying. Long-running transitions still model as state flags (Resizing, Reconciling) toggled True or False.
  • Polarity matters: Ready=True is normal-true, while Stalled=True or Degraded=True is normal-false. Generic tools can't summarize arbitrary condition lists without knowing each condition's polarity, which is why the convention calls for a single roll-up summary condition (Ready for long-running resources, Succeeded for run-to-completion jobs).
  • A missing condition means Unknown, so good controllers populate their conditions on the first pass (even as Unknown) to prove they're alive. kstatus (used by Flux, Argo CD guidance, and kubectl wait) reads Ready, Reconciling, Stalled, and observedGeneration to compute Current, InProgress, or Failed.

Reading a stuck operator, in order

  1. Compare metadata.generation vs status.observedGeneration: if they stay unequal, the controller hasn't processed your edit: it's down, not holding the leader lease, or filtering your event with a predicate.
  2. Read conditions: grab the reason on the False or Stalled condition. A kstatus Stalled=True means the controller stopped retrying until you change the spec.
  3. Check Events on the CR: Warning events usually quote the exact failed API call.
  4. Follow ownerReferences to owned objects: spot which child is missing or unhealthy and read its events (quota, PSS, admission, image pull).
  5. Inspect the operator pod: verify it's running, check who holds the Lease (kubectl get lease), and scan logs for Forbidden (RBAC), connection refused (dependency), or backoff retries, then inspect any webhooks it registered.
  6. Check finalizers: a CR stuck in Terminating with a finalizer from a dead or uninstalled operator needs either that controller brought back online, or a deliberate manual finalizer strip knowing you'll leak whatever external resource it was guarding.
How this gets tested

"The database CR has been Progressing for twenty minutes" is graded on finding the actual root cause: an RBAC Forbidden in the operator log, a NetworkPolicy blocking the init Job, a quota blocking pods on the StatefulSet, or a webhook with no endpoints. Each leaves its own distinct fingerprint (log line, Hubble drop, ReplicaSet event, webhook error). Find the artifact and fix the broken object; deleting and recreating the CR is a level-based no-op that just reproduces the exact same stall.

Self-check

answer before opening
You patch a CR and its status still reports the old problem. What do you check before believing it?

Compare status.observedGeneration against metadata.generation. If they don't match, the controller hasn't reconciled your edit yet and status is still reporting on the previous spec. Once they match and the error persists, you're looking at a real current failure.

A namespace has been Terminating for twenty minutes. Method?

List whatever objects remain (kubectl api-resources --verbs=list --namespaced -o name | xargs -n1 kubectl get -n <ns>), check the finalizer holding them, and verify whether the owning controller is alive. Reviving the controller is the clean fix; stripping the finalizer by hand is a last resort that leaks whatever teardown it was guarding.

Why is deleting an operator-managed pod not a way to "reset" anything?

Because reconciliation is level-based: the controller simply sees a missing pod and spins up a replacement, with zero memory of why you deleted it. To change behavior, fix the spec or underlying cause; otherwise the reconcile loop will faithfully restore the same state forever.

An operator's CRs apply fine and nothing happens at all. Two checks?

First, verify the controller pod is running and actually holds its leader Lease. Second, check its logs for RBAC Forbidden errors covering your namespace or kind, the classic silent failure. Only after clearing both should you check whether the CR is missing a selector, class field, or has a pause annotation.

Name the five ways an operator integrates with the rest of a platform.

Its CRs are delivered through GitOps, its metrics are scraped and alerted on, its connection Secrets are consumed by apps (or bridged via ESO), its CRs are validated by admission policy, and its API is wrapped behind a thinner developer-facing abstraction (Crossplane, kro, or a portal template). That's the full "integration" half of the competency.

An operator Deployment has three replicas and only one does work. How does it decide, and how do you see which?

Leader election via a Lease in the operator's namespace (named by LeaderElectionID, defaulting to a 15 s lease and 10 s renew deadline). Run kubectl -n <ns> get lease <id> -o jsonpath='{.spec.holderIdentity}' to identify the active pod. Standby replicas warm their caches without reconciling, so checking the wrong pod's logs gives you nothing.

What does Owns() in a controller builder do, and what does it explain about operator behavior you see in the cluster?

Owns() watches a child resource kind and, whenever a child changes, enqueues its parent CR using the controller ownerReference. That's why deleting an operator-owned Deployment or Secret triggers an immediate recreate, why ownerReferences map an operator's entire object tree, and why operators require full RBAC on every child kind they create.

Install an operator with OLM v1 pinned to versions below 2.0 from channel stable. Which object, and what does upgradeConstraintPolicy: SelfCertified change?

Create a ClusterExtension naming spec.namespace, spec.serviceAccount.name (an SA you pre-configured with the bundle's RBAC), and spec.source.catalog: { packageName, channels: [stable], version: "<2.0" }. The default CatalogProvided policy only permits upgrades on the catalog's upgrade graph; SelfCertified lets you jump to any version (including downgrades), while CRD upgrade safety checks still run unless disabled.

Why should a condition be named Ready or Degraded rather than Deploying, and what is polarity?

Condition types describe an observed state (adjective or past participle), while ongoing transitions are represented by toggling status (like Reconciling=True rather than Deploying). Polarity tells you whether True is healthy (Ready) or unhealthy (Degraded, Stalled), and because generic tooling can't guess polarity for every custom condition, the convention provides a roll-up Ready summary condition.
