A CRD teaches the Kubernetes API server a new noun, and that's all it does: persistence, validation, RBAC, kubectl integration, and watch semantics all come for free. Behavior requires a controller (section 3.3). Keeping schema and behavior cleanly separated in your head unlocks the rest of domain 3.

Orientation

competency 3.1 · designing and creating CRDs

Nothing on this page needs a running controller - the whole point is seeing how much a CRD gives you all by itself. Apply one and you immediately get a typed, validated, RBAC-aware, watchable, kubectl explain-documented API with zero behavior behind it. That clean seam is where platform engineering lives.

What a task looks like

"Create a CRD for X with required field Y, an enum, and a printer column; create one valid instance; show that an invalid one is rejected." Every clause is graded by an object or an error message. Writing a CRD from scratch under time pressure takes muscle memory, so type one out by hand at least three times before exam day.

Anatomy: the fields that matter

group · names · scope · versions

Every CRD comes down to four structural pieces: group, names (plural, singular, kind, shortNames, categories), scope (Namespaced or Cluster), and versions[]. Watch out for metadata.name: it isn't free-form - it must be exactly <plural>.<group>, and mistyping it is the most common first error.

FieldWhy it matters
scopeNamespaced unlocks per-namespace RBAC and ResourceQuota via count/<plural>.<group>. Cluster-scoped objects can't be owned by namespaced ones - a real design constraint you'll see again in Crossplane (3.5).
names.shortNamesCluster-global and first-come. If two CRDs both claim tb, kubectl prints a collision warning - as a platform API author, you own avoiding those clashes.
names.categoriesDrops your kind into groupings like kubectl get all (or a custom kubectl get platform). Cheap usability win.
versions[].servedControls whether the API server serves requests for this version at all.
versions[].storageMarks the single version persisted in etcd; all other served versions convert on the fly.
versions[].deprecatedSends a deprecation warning header to clients using this version - the polite way to sunset an API.

Versioning at exam depth: deprecating an old version means keeping served: true while moving storage: true to the new version; retiring it means flipping served: false. That's the entire story whenever schemas match (strategy: None). When schemas actually diverge, you need a Webhook converter to transform objects on the fly. Know both options and what each one costs.

Schema: where design happens

CRD schemas use OpenAPI v3: types, required, enum, pattern, minimum/maximum, default, and format. Keep these Kubernetes extensions on your radar:

  • x-kubernetes-validations: CEL rules with custom error messages evaluated right inside the API server. This gives you cross-field checks (self.max >= self.min) and immutability (self == oldSelf) with zero webhooks to run. Users see your message directly in their terminal, so write it clearly.
  • x-kubernetes-preserve-unknown-fields: opts a subtree out of schema pruning. By default, any field missing from the schema is silently stripped on write - which looks like data loss until you realize the schema is doing its job.
  • Also handy: x-kubernetes-list-type: map paired with x-kubernetes-list-map-keys (so server-side apply merges lists cleanly instead of replacing them wholesale), and x-kubernetes-int-or-string.
Pruning isn't an error

The API server drops any field your schema didn't declare. kubectl's default strict field validation catches that and throws an error (strict decoding error: unknown field), but any client skipping validation (--validate=false, many controllers, raw API calls) loses the field silently with no warning and no event. Users swear "my setting is being ignored", when in fact etcd never stored it. That's why slapping preserve-unknown-fields on a platform API is usually a trap - you're trading a loud, helpful rejection for silent misconfiguration.

Subresources and presentation

  • subresources.status splits /status into its own API endpoint, and that boundary cuts both ways: writes to the main resource ignore .status, while writes to /status ignore .spec. That's why the classic "my controller's status updates keep vanishing" bug is actually the subresource working - the caller used Update() instead of UpdateStatus() (or forgot --subresource=status on kubectl patch). Without it, anyone editing spec can clobber controller status, which is why every operator convention in section 3.3 relies on it.
  • subresources.scale wires kubectl scale and HPAs straight into your custom kind with three JSONPaths.
  • additionalPrinterColumns controls what kubectl get displays. As section 3.1 noted, a platform API without a clear READY column makes users miserable.

Once you apply a CRD, wait for its Established condition - until then, requests for the new kind can 404. Right after that, your custom noun acts like a native Kubernetes type: RBAC rules can grant it, ResourceQuota can count/ it, admission webhooks and policy engines see it, and kubectl explain renders the descriptions you wrote. Those descriptions aren't busywork - they're the live docs your developers actually read.

Where CRDs stop

and what you reach for instead
  • Aggregated API servers: for custom storage backends, massive object counts, or non-etcd persistence. Good to recognize in docs, almost never the right exam pick.
  • Admission webhooks: for validation that CEL can't do (like cross-object lookups) or complex mutation. Remember the cost: every webhook becomes an availability dependency on the API server, and failurePolicy is where you pick your failure mode (section 5.2).
  • Operators: for actual behavior. A CRD without a controller is just a typed ConfigMap - which is occasionally fine on its own (Crossplane XRs, Argo Applications, and Tekton Tasks are all declarative data driven by controllers running elsewhere).
  • Generators: Crossplane's XRD and kro's ResourceGraphDefinition both generate CRDs behind the scenes. Sections 3.5 and 3.6 build directly on what you're hand-writing right here.
Command reflex on an unfamiliar cluster

Run kubectl api-resources | grep <tool> to discover the nouns, kubectl explain <kind> --recursive to inspect the schema, and kubectl get crd <name> -o yaml to check printer columns, versions, and validation rules. Those three commands let you operate an operator you've never seen before - a classic exam move.

Schema mechanics the API server enforces

structural rules · CEL in detail · ratcheting · defaulting and nullable · list types

Structural schema: the four rules

apiextensions.k8s.io/v1 mandates a structural schema. If your CRD violates it, create fails with a Required value error pointing at the node missing a type (legacy CRDs migrated from v1beta1 surface a NonStructuralSchema condition instead and forfeit pruning, defaulting, and CEL). The four rules are straightforward: every node (root, every property, every array item) must declare a non-empty type unless it sets x-kubernetes-int-or-string: true or x-kubernetes-preserve-unknown-fields: true; anything referenced inside allOf, anyOf, oneOf, or not must also be declared outside it; description, type, default, additionalProperties, and nullable can't live inside those junctors; and metadata can only constrain name and generateName. Nine times out of ten, a hand-written CRD fails because a nested property two levels down forgot its type.

Pruning and its exceptions

Unknown fields get pruned on every write across every version. Setting x-kubernetes-preserve-unknown-fields: true keeps arbitrary fields under that node, though pruning turns right back on for any child properties you explicitly declare inside it. x-kubernetes-embedded-resource: true marks a field that embeds a full Kubernetes object (so apiVersion, kind, and metadata are validated). Because kubectl apply runs strict field validation by default, it rejects unknown fields before pruning ever happens - explaining why the same YAML fails from your laptop yet silently succeeds when applied by a controller without strict validation.

CEL rules, all the fields

  • rule is scoped to whichever schema node holds x-kubernetes-validations, and self refers to that node. Putting a rule at the root lets you inspect both self.spec and self.status; lower down you only see that subtree. From metadata, CEL can only read apiVersion, kind, metadata.name, and metadata.generateName.
  • message gives a static error string, while messageExpression evaluates a CEL string dynamically (wrap numbers in string(x) to concatenate; falls back to message if evaluation errors). Skip both and Kubernetes prints a raw failed rule: <expression>.
  • reason picks the API status reason (FieldValueInvalid by default, or FieldValueForbidden, FieldValueRequired, FieldValueDuplicate), and fieldPath sets a relative JSON path so the error highlights the exact offending field rather than the parent block.
  • Transition rules (any rule referencing oldSelf) only fire on updates where both old and new values exist, and only along correlatable paths (object parents or x-kubernetes-list-type: map lists, never set or atomic). Core idioms: immutability self == oldSelf, append-only self.all(e, e in oldSelf), monotonic growth self >= oldSelf. Add optionalOldSelf: true to turn oldSelf into a CEL optional so the rule also runs on create and on newly populated fields.
  • Property names that clash with CEL keywords or contain -, ., or / get escaped: self.__namespace__, self.x__dash__prop.
  • Cost budget: Kubernetes statically estimates CEL cost when you apply the CRD. Looping over an unbounded list or string assumes worst-case sizes and fails with "CEL rule exceeded budget by more than 100x (try simplifying the rule, or adding maxItems, maxProperties, and maxLength where arrays, maps, and strings are used)". Add those bounds and the exact same rule passes (there's also a per-CRD total and runtime cap).
  • Compile-time errors that reject the CRD itself: no_matching_overload (like comparing an int to a bool), no_such_field (misspelled property), and invalid argument to has() macro.
  • Type gotchas: OpenAPI integer maps to 64-bit int while number maps to double (so self.replicas > 1.5 against an integer fails to compile). format: date-time becomes a timestamp, format: duration a duration, maps come from additionalProperties, and listType: set or map compares unordered.

Validation ratcheting (GA since 1.33)

When you tighten a CRD schema, an update to an existing object still succeeds as long as it doesn't touch the already-invalid field - letting you roll out stricter validation without migrating every stored object up front. Know the exceptions where ratcheting doesn't apply: transition rules using oldSelf, changes to x-kubernetes-list-type, additions to required, renamed properties, metadata rules, and any create request. Pair it with optionalOldSelf when you want explicit grandfathering rules.

Defaulting and nullable

  • Defaults are applied on incoming requests (in the request version), when reading stored objects back from etcd (storage version), and right after a mutating webhook patches an object. Read-time defaults aren't persisted back to etcd until the next write.
  • A default on a composite/object field has to pass the schema itself and is pruned of any unknown keys.
  • With nullable: false (default), an explicit null gets stripped and replaced by default if one is defined. With nullable: true, null is preserved as null and never defaulted. So foo: null with default: "x" only turns into "x" when the field isn't nullable.
  • Defaulting is another reason the status subresource matters: defaulting fields inside status can confuse controllers tracking generation changes.

List semantics

x-kubernetes-list-type: atomic (the default for primitive and struct lists) means server-side apply replaces the entire array under a single field manager. set merges unique scalar items. map paired with x-kubernetes-list-map-keys: [name] keys entries by field so multiple field managers can each own their own list items - and lets CEL correlate elements across updates (conditions lists use map keyed on type). Both Argo CD and Flux server-side apply treat atomic lists as all-or-nothing, which is why forgetting list-type: map causes "my injected sidecar keeps disappearing" bugs.

The error you'll read most

Learn to recognize all four rejection styles on sight: spec.tier: Unsupported value: "platinum": supported values: "bronze", "silver", "gold" is an enum; spec.sizeGB: Invalid value: 900: spec.sizeGB in body should be less than or equal to 500 is a numeric bound; spec: Invalid value: ...: bronze tier is capped at 50GB is your CEL rule; and strict decoding error: unknown field "spec.color" is kubectl's strict validation before the schema even ran. Spotting which validator spoke tells you the exact line of the CRD to edit.

Versions, subresources and the CRD-level errors

conversion · storedVersions · selectableFields · printer columns · scale · what kubectl says when the CRD itself is wrong

Versions in practice

  • Exactly one version carries storage: true, while any number can be served: true. When you don't specify a version, kubectl picks the highest-priority served version: GA (v2, v1) beats beta beats alpha, higher numbers first - so v1 beats v1beta1 beats v2alpha1.
  • Setting deprecated: true with a deprecationWarning attaches a warning header to every request on that version (which kubectl prints). Flipping served: false shuts down the endpoint, though existing objects stored at that version remain untouched in etcd.
  • spec.conversion.strategy: None simply rewrites apiVersion and assumes compatible schemas. Webhook sends a ConversionReview batch to your conversion service, which can transform anything except metadata (beyond labels and annotations).
  • Etcd only rewrites stored objects to the new storage version when those objects are next updated. status.storedVersions tracks every version that might still have bytes on disk, and Kubernetes blocks you from dropping a version from spec.versions while it's still listed there. Migrate cleanly using a StorageVersionMigration (storagemigration.k8s.io) or a no-op update loop over every object, then patch status.storedVersions.

Subresources, precisely

  • subresources.status: {} separates .status onto its own endpoint (main writes ignore status; /status writes ignore spec and validate only status) and ensures metadata.generation only increments when spec changes. Without it, every status update bumps generation and observedGeneration becomes useless.
  • subresources.scale takes specReplicasPath (under .spec, required), statusReplicasPath (under .status, required), and labelSelectorPath (string holding a serialized selector, required for HPA). Once wired, kubectl scale, HPA, and VPA all work natively on your CRD.
  • selectableFields (GA since 1.32) declares up to 8 scalar jsonPath fields per version under spec.versions[].selectableFields[], unlocking server-side filtering like kubectl get shirts --field-selector spec.color=blue so controllers and humans don't have to mirror spec fields into labels.

Printer columns and names

Each entry in additionalPrinterColumns[] sets name, type (integer, number, string, boolean, or date), optional format, jsonPath, description, and priority (0 appears in default output; > 0 appears only with -o wide). Using type: date formats timestamps as human-friendly ages. Because NAME is automatic while AGE isn't, most CRDs add {name: Age, type: date, jsonPath: .metadata.creationTimestamp}. Columns are per version, so v1alpha1 and v1 can render differently. names.shortNames are cluster-global and first-come; names.categories: [all] adds your kind to kubectl get all, and defining your own category (like fluxcd or platform) lets kubectl get platform -A show every kind you ship at once.

Lifecycle of the CRD object itself

  • Wait for Established: True and NamesAccepted: True right after applying - requests before then 404. If NamesAccepted is False citing "is already in use", your plural, kind, or shortName collided with an existing CRD.
  • Deleting a CRD deletes every custom resource of that kind across the cluster. The customresourcecleanup.apiextensions.k8s.io finalizer holds the CRD in Terminating until all CRs are gone, so a single stuck CR (say, a finalizer owned by a dead controller) pins the CRD too. Both Argo CD and Flux will happily prune a CRD if you remove its file unless you shield it (Prune=false or kustomize.toolkit.fluxcd.io/prune: disabled) - easily the most destructive prune mistake you can make.
  • ResourceQuotas count CRs via count/<plural>.<group>, and RBAC targets them with apiGroups: [group] and resources: [plural, plural/status].

Self-check

answer before opening
A user says their field "does not work". kubectl get -o yaml shows it missing entirely, and no error was printed. What happened?

Schema pruning. The field isn't declared in the CRD's OpenAPI schema, so the API server stripped it on write - and whatever applied it bypassed strict field validation (a controller, a GitOps sync, or --validate=false), which is why nothing errored. Fix it by adding the field to the schema (or, in rare cases, adding x-kubernetes-preserve-unknown-fields on that subtree). Declaring it properly gives users real validation and docs.

Your controller's status writes vanish. One likely cause?

The status subresource is enabled, and the writer is hitting the main resource endpoint - which silently ignores the status stanza. Switch to UpdateStatus() (or kubectl patch --subresource=status). And watch out for the flip side: with no status subresource at all, any spec write from a user overwrites the status your controller just wrote.

You must forbid changing spec.tier after creation. How, without a webhook?

Add a CEL transition rule right on the field using x-kubernetes-validations: rule: "self == oldSelf" with a clear message like "tier is immutable". Because the API server evaluates CEL against the stored object on updates, you get immutability with zero webhooks to operate.

You want to serve v1alpha1 and v1beta1 with different fields. What do you need?

Mark both versions served: true, mark exactly one storage: true, and set up a conversion strategy: None only works when fields are compatible, so diverging fields need a conversion Webhook. Everything stays persisted in the storage version in etcd and gets converted on the fly when served.

What does a CRD give you for free, and what does it definitively not give you?

For free: etcd persistence, OpenAPI and CEL validation, defaulting, RBAC integration, watches and informers, kubectl support and explain docs, ResourceQuota counting, and admission/policy visibility. Definitely not free: behavior. Nothing actually happens until a controller reconciles the object.

Your CEL rule over a list of strings is rejected with "exceeded budget by more than 100x". What do you change?

Bound the inputs your rule loops over: add maxItems on the array and maxLength on its string items (or maxProperties on a map). The static cost estimator assumes worst-case sizes for unbounded collections, so adding bounds lets the exact same CEL expression pass - and gives your API cleaner input limits too.

You tightened a pattern on spec.name. Existing objects with old-style names must still be updatable. What makes that work, and what does it not cover?

Validation ratcheting (GA since 1.33): updates succeed as long as every part failing the new schema stays unchanged. It doesn't cover transition rules (oldSelf), list-type changes, new required fields, renamed properties, metadata rules, or create requests. For custom grandfathering rules, use optionalOldSelf: true inside a CEL rule.

You want to drop v1alpha1 from a CRD but the update is refused. Why, and what is the sequence?

status.storedVersions still includes v1alpha1, so etcd might still hold objects serialized in that version and Kubernetes refuses to strand them. Set v1 as the storage version (optionally setting served: false on v1alpha1 first), rewrite every object via a StorageVersionMigration or a no-op update loop so etcd re-persists them as v1, patch status.storedVersions to ["v1"], and then remove v1alpha1 from spec.versions.

Enable kubectl get widgets --field-selector spec.tier=gold. Field, version status, and limits?

Add spec.versions[].selectableFields: [{jsonPath: .spec.tier}] (GA since Kubernetes 1.32). You're limited to scalar fields, at most 8 per version, and clients have to query a version that declares them. It eliminates the old workaround of duplicating spec fields into labels just to filter efficiently.
