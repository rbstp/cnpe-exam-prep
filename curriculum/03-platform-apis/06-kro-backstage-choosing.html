kro in one sitting

Crossplane's niche with less machinery

kro (Kube Resource Orchestrator) sits in Crossplane's niche with a fraction of the moving parts. One ResourceGraphDefinition declares both the schema and the resources it expands into, and kro generates the CRD and runs the reconciliation loop itself. No providers, no functions, no package manager. CEL expressions wire fields together, and cross-resource references (like ${ns.metadata.name}) automatically build the dependency graph and creation order.

apiVersion: kro.run/v1alpha1
kind: ResourceGraphDefinition
metadata: { name: tenantspace }
spec:
  schema:
    apiVersion: v1alpha1
    kind: TenantSpace
    spec:
      team: string
      cpu: string | default="1"
  resources:
    - id: ns
      template:
        apiVersion: v1
        kind: Namespace
        metadata:
          name: ${schema.spec.team}
          labels:
            tenant: ${schema.spec.team}
    - id: quota
      template:
        apiVersion: v1
        kind: ResourceQuota
        metadata:
          name: tenant-quota
          namespace: ${ns.metadata.name}
        spec:
          hard:
            requests.cpu: ${schema.spec.cpu}
YAML flow-style trap

Always write kro's ${...} substitutions in block style. Inside flow-style braces (labels: { tenant: ${schema.spec.team} }), the expression's own closing } ends the YAML map prematurely and the whole manifest blows up with a useless parse error.

kro is still young and its API evolves quickly. If this manifest disagrees with your installed version, kubectl explain resourcegraphdefinition.spec settles it on the spot, and that recovery habit is worth more than memorizing the YAML.

The RGD fields beyond the first manifest

  • Schema markers. Simple Schema types (string, integer, boolean, objects, arrays) accept validation markers after a pipe: required=true, default=..., enum="a,b", pattern="regex", minimum=1 maximum=100. kro compiles these into OpenAPI validation on the generated CRD, so bad instances get rejected by the API server before kro even sees them.
  • Status. schema.status fields hold CEL expressions over child resources (like url: ${service.status.loadBalancer.ingress[0].hostname}). kro infers their types and populates them onto the instance, giving you the equivalent of Crossplane's ToCompositeFieldPath.
  • readyWhen. A list of CEL conditions on a resource that dependents must wait for. Without it, kro treats a resource as ready the moment it exists and its expressions resolve, so a broken Deployment can still make the instance look healthy unless you explicitly add readyWhen: [${deployment.status.availableReplicas > 0}].
  • includeWhen. Conditions controlling whether a resource is created at all (like ${schema.spec.ingress.enabled}). They're re-evaluated on every reconcile, so flipping the flag off later deletes the resource.
  • forEach expands one resource entry into a collection (one object per list item), while externalRef reads an existing object without taking ownership of it.
  • Ordering. kro infers the dependency graph from your CEL references. Run kubectl get rgd <name> -o jsonpath='{.status.topologicalOrder}' to inspect the computed order: creation walks it forward and deletion walks it in reverse. A cycle (A reads B, B reads A) blocks the RGD from going Active; break it by reading from schema.spec instead.
  • Scope. schema.scope: Namespaced (default) or Cluster. Unlike Crossplane, namespaced instances in kro can still create cluster-scoped objects (just like the lab's Namespace example) because kro tracks ownership using ApplySet-style labels rather than ownerReferences, which can't cross scopes.

Conditions to read

An RGD tracks ResourceGraphAccepted, KindReady (the CRD exists), ControllerReady (the dynamic controller is running), and an overall Ready condition. Its status.state only turns Active when all three succeed; otherwise it stays Inactive with the failing condition's message (often a CEL type mismatch or unknown field caught by static analysis before anything is created). Instances report InstanceSynced and status.state: ACTIVE, and RGD authors can expose custom conditions via schema.status.conditions. To pause reconciliation on one instance while debugging, annotate it with kro.run/reconcile: suspended.

Trap

kro's controller needs RBAC for every kind an RGD templates. The Helm chart's rbac.mode: unrestricted allows everything, while aggregation mode only grants what ClusterRoles labeled rbac.kro.run/aggregate-to-controller: "true" permit. In aggregation mode, an RGD referencing an ungranted kind still goes Active, and then every instance fails with forbidden from the kro ServiceAccount. Same RBAC lesson as Crossplane and Argo Workflows, one namespace over.

The golden path, hop by hop

Backstage → Gitea → ApplicationSet → workload

Backstage implements the "web portals" capability from the CNCF white paper. It combines a software catalog (components, systems, APIs, and owners declared in each repo's catalog-info.yaml), software templates (the scaffolder: a parameter form wired to actions like fetch:template, publish:gitea, and catalog:register), TechDocs, and plugins that surface Kubernetes, CI, and other systems in one place.

Backstage template  (parameters form)
      │ scaffolder actions: fetch skeleton → publish → register
      ▼
new repo in Gitea org services   (contains k8s/ manifests + catalog-info.yaml)
      │ noticed by the SCM-provider generator
      ▼
ApplicationSet golden-path  ──generates──▶ Argo CD Application
      │
      ▼
running workload  ── and the component appears in the catalog with its owner

Each hop is a place where things can break and a link the exam can ask you to trace: template action failures (git host credentials), the generator's filter (which repos match), the generated Application's destination, and the workload itself. Being able to narrate this chain end to end is the "golden path" competency, and the commands below verify every hop.

Why a portal is not a platform

Watch out for this classic scenario trap: a portal is an interface over capabilities, not a capability in itself. If fulfillment behind the scenes is still a manual ticket queue, bolting Backstage onto it just gives you a nicer-looking ticket queue. Call that out directly whenever a question pitches a portal rollout with no real automation underneath.

Software templates, the parts that break

  • parameters is JSON Schema rendered as multi-step forms. Use ui:field to pick specialized widgets: OwnerPicker, EntityPicker, RepoUrlPicker (make sure ui:options.allowedHosts lists your git host or the form rejects it on sight), and Secret (referenced as ${{ secrets.x }}, never parameters.x).
  • steps run sequentially in the scaffolder backend, each defining id, action, input, and an optional if. Know the core built-ins: fetch:template (copies a skeleton and renders ${{ values.x }}), fetch:plain, publish:github / publish:gitlab / publish:gitea / publish:bitbucket (creates and pushes the repo), catalog:register (registers the new catalog-info.yaml via repoContentsUrl + catalogInfoPath), catalog:write, debug:log, fs:rename, and fs:delete. You can inspect every installed action live at /create/actions in the UI.
  • Templating syntax. Read inputs via ${{ parameters.name }}, prior step outputs via ${{ steps['publish'].output.repoContentsUrl }}, and final user links via output.links. Backstage's ${{ }} is Nunjucks, not kro's ${} or Helm's {{ }}; mixing up the braces is a classic reason templates fail to render.
  • Where templates fail. Publish steps fail if app-config.yaml (integrations.github/gitlab/gitea) lacks a token with repo-creation rights. catalog:register fails if the repo exists but the catalog can't read the URL. And if the template finishes green but no Argo CD Application appears, check the ApplicationSet generator's filter rather than Backstage.

Two plugins the exam vocabulary assumes

TechDocs builds MkDocs sites directly from a repo's docs/ folder and mkdocs.yml, pointed to by the backstage.io/techdocs-ref annotation (dir:. means "this repo"). The Kubernetes plugin surfaces pods, deployments, and errors for a component by matching workloads labeled backstage.io/kubernetes-id (or selected by backstage.io/kubernetes-label-selector), querying clusters configured under kubernetes.clusterLocatorMethods with a ServiceAccount token. Both are read-only windows over state your platform already manages, which ties straight into the maturity model below.

Mental model

The CNCF maturity model's Interfaces axis progresses from Custom processes → Standard tooling → Self-service solutions → Integrated services. A portal that opens tickets is just level 1 with nicer typography. A portal whose template commits to git and lets GitOps and controllers handle the rest is level 3. When the exam hands you a "portal is an interface, not the platform" scenario, it's asking you to place that proposal on this ladder.

Choosing the engine

the differentiators to reason from
EngineTriggerLifetimeBest at
CRD + operatorAn API objectForeverDomain behavior: failover, backup, upgrade
CrossplaneAn API objectForeverComposing many resources, including cloud APIs, behind one abstraction
kroAn API objectForeverThe same declarative composition, in-cluster only, in a single file
Argo WorkflowsSubmit, schedule, or eventRun to completionImperative sequences, batch jobs, scheduled maintenance
TektonGit eventRun to completionBuilding, testing, and publishing artifacts
Backstage templateA human filling a formOne-shot scaffoldingThe front door: create repo, register in catalog, hand off to GitOps

Three questions settle almost every architecture choice:

  1. Does the state need to reconcile forever, or be produced once? Forever → a controller (operator, Crossplane, kro). Once → a workflow or pipeline.
  2. What triggers it? An API object, a schedule, a git event, or a human.
  3. Who's the consumer? A developer writing YAML, a developer clicking through a form, or another automated system.

And when two engines both fit, say so explicitly and pick the thinner one. That reasoning scores well because it applies the TVP instinct from section 3.1 to your own platform stack.

Engines the table leaves out

EngineWhat it isPick it whenNot when
Helm chartInstall-time templating with no continuous controllerPackaging a single application's manifests with valuesState must keep converging or compose external APIs
tofu-controller (Flux)A Terraform CR reconciled by Flux (approvePlan gates applies, drift detection is built in)You have existing Terraform/OpenTofu modules and state that need to become GitOps-drivenYou'd rather model the API natively in Kubernetes types (pick Crossplane or kro)
KubeVela (OAM)An Application made of components, traits, and policies with a delivery workflowYou want an application-centric abstraction across clusters with CUE-defined delivery stepsYou're building infrastructure-first APIs (Crossplane fits better)
Cloud-vendor controllers (ACK, Config Connector, ASO)One CRD per cloud resource typeYou're on a single cloud and want native resource fidelity, optionally wrapped by kro or CrossplaneYou need one unified abstraction spanning multiple clouds

Keep two final pairings sharp. Crossplane vs a cloud controller: a cloud controller gives you the raw resource kinds, while Crossplane (or kro) gives you the developer-facing abstraction on top, so they compose rather than compete. Argo Workflows vs Tekton: both sit on the official tool list, so if a prompt names one, use it. Otherwise, git-driven CI pipelines go to Tekton, and parameterized orchestration on request or schedule goes to Argo Workflows.

The suspend annotation freezes kro's reconciliation on a single instance. Delete an owned resource while it's suspended and nothing brings it back, showing both the debugging escape hatch and the controller's role in keeping the graph intact.

apiVersion: kro.run/v1alpha1

Self-check

answer before opening
How does kro know to create the namespace before the quota?

From the CEL reference: the quota template reads ${ns.metadata.name}, so kro builds a dependency graph automatically and orders creation accordingly. You never write dependsOn, which also means a refactor that drops a reference can silently reorder your graph.

A team asks for "a portal so developers can self-serve". What do you ask before agreeing?

Ask what actually happens after the user clicks submit. If fulfillment behind the scenes is still manual, the portal is just a nicer ticket queue. The real platform work is the automated chain underneath (templates → git → GitOps → controllers), and the portal is the last 10%. That's the white paper's interface-versus-capability distinction.

Nightly image rebuild-and-rescan: which engine, and why not the others?

A CronWorkflow: it's scheduled, runs to completion, and gives you a DAG with retries and notifications. You wouldn't pick an operator (nothing to reconcile continuously), Tekton (no git event trigger, though it could execute the build), or Crossplane (no persistent resource graph to maintain).

Give the three questions that decide the engine.

Does the state need to reconcile forever or run once? What's the trigger: an API object, a schedule, a git event, or a human? And who's the audience: a YAML author, a form filler, or another system? Answer those three and the decision table practically fills itself in.

What does the SCM-provider generator actually watch, and how would you debug a repo that never appears?

It polls the git host's API for repos in an org matching your filters (name pattern, topic, or required path), then stamps out one Application per match. Debug by checking the generator block (org, filters, credentials Secret), then reading the ApplicationSet's status conditions and controller logs for API errors, which usually trace back to a token scope or a filter mismatch.

An RGD is Active, but every instance sits with ResourcesReady=False and the kro controller logs forbidden. Cause?

kro is running in RBAC aggregation mode and nobody granted its controller permissions on the kind your RGD templates. Because static analysis still passes, the RGD goes Active, and the error only shows up when the controller tries to create child objects. Add a ClusterRole for that kind labeled rbac.kro.run/aggregate-to-controller: "true". Same failure family as a Crossplane provider missing RBAC or an Argo Workflows SA missing workflowtaskresults.

A Backstage template's publish step fails with an authentication error although the form rendered fine. Where do you look, and what is the other common form-time failure?

Check the scaffolder backend's integration config (integrations.github|gitlab|gitea in app-config.yaml) and verify its token actually has repo-creation rights in the target org. The classic form-time failure is a RepoUrlPicker whose allowedHosts list doesn't include your git host, blocking submission before any step ever runs.

How do you make a kro resource wait for a Deployment to actually be available before creating the Service that points at it, and why is the default insufficient?

Add readyWhen: [${deployment.status.availableReplicas > 0}] (or check its Available condition) on the Deployment entry. By default, kro considers a resource ready the moment it exists and its CEL expressions resolve, so dependents get created even if the pods never start. Don't confuse it with includeWhen, which decides whether to create the resource at all.

Which Backstage kinds must a catalog contain before spec.owner: group:default/team-x resolves, and what happens if they are missing?

A Group named team-x (typically alongside User entities linked via memberOf). If it's missing, the Component still loads into the catalog, but its ownedBy relation dangles: the UI renders a broken owner link and ownership filters won't find it. In practice, Groups and Users are synced from an org provider like GitHub or LDAP rather than written by hand.
