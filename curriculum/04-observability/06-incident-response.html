Orientation

competency 4.3 · diagnosing and remediating incidents

Under a ticking clock, the gap between a 5-minute fix and a 20-minute spiral isn't raw Kubernetes trivia: it's following a calm, repeatable method instead of guessing. Internalize the four steps below, then drill them with make break until they run on autopilot.

The method

four steps, in order
  1. Scope the blast radius first. Find out what's broken and what's still healthy: kubectl get pods -A | grep -v Running, make status, top-level dashboards. One namespace or the whole cluster? Workloads or control plane? Bounding the problem early keeps you from debugging two layers away from the real cause.
  2. Check the timeline second. Ask what just changed: kubectl get events -A --sort-by=.lastTimestamp | tail -30, recent Argo CD syncs, helm list -A, and kubectl rollout history. Most real incidents trace straight back to a recent change.
  3. Descend one layer at a time. Walk cleanly through describe → events → logs → previous logs (--previous for crash loops) → exec / debug. Resist jumping straight to guesses; skipping steps is where rabbit holes start.
  4. Fix the cause, then prove recovery with the exact same check that failed. If you caught the bug via a failing curl, the incident isn't over until that curl returns 200; never stop at "the pod says Running."

Node-level moves

When a node itself is unhealthy: kubectl cordon <node> blocks new pods from landing there, kubectl drain <node> --ignore-daemonsets --delete-emptydir-data evicts running workloads (honoring PDBs; remember section 1.2 if it hangs!), and kubectl uncordon puts it back in rotation. Draining is also the cleanest way to verify whether your workloads genuinely tolerate losing a node.

Four-command triage opener

Whenever a task says "the cluster is broken," run four commands immediately: kubectl get nodes, kubectl get pods -A | grep -v Running, kubectl get events -A --sort-by=.lastTimestamp | tail -30, and kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations. Nine times out of ten, the root cause jumps straight off the screen.

The debugging toolbox and rollback commands

debug profiles, per-tool rollback, remediation vs resolution

kubectl debug flags to keep handy

  • kubectl debug -it pod/x --image=busybox --target=app attaches an ephemeral container sharing app's process namespace (note: ephemeral containers can't be removed individually; they live until the pod is deleted).
  • --copy-to=x-debug --share-processes --set-image=app=busybox clones a crashing pod with a swapped image or entrypoint (pair with --container app -- sh) when the original dies too fast to attach.
  • kubectl debug node/n -it --image=busybox drops you onto the node with its root filesystem mounted at /host. Profiles control privilege: general (default, unprivileged), baseline / restricted (PSS-friendly), netadmin (NET_ADMIN + NET_RAW for tcpdump and ip), and sysadmin (full root for chroot /host). Remember to delete the node-debugger-* pod afterward.
  • Check API server internals with kubectl get --raw /readyz?verbose and /livez?verbose (lists etcd, informers, and webhooks individually; kubectl get componentstatuses has been deprecated since 1.19).

Vocabulary and incident discipline

Keep the metrics straight: MTTD (detect: alert fired minus impact start), MTTA (acknowledge), and MTTR (restore), alongside DORA's "failed deployment recovery time" from section 4.5. A strong on-call setup pairs one clear severity taxonomy with linked runbooks (symptom, top causes, exact diagnostic commands, rollback, escalation path), a dedicated incident channel, and a quick blameless postmortem producing concrete action items with owners. Finally, separate remediation (restoring service fast: rollback, scale, fail over, pause a broken policy) from resolution (fixing the underlying bug so it doesn't come back).

How this gets tested

Exam incident prompts always hand you a symptom, never the cause: "payments returns 503 since the last deploy," "pods in namespace X won't start," or "nothing can be created cluster-wide." Run your four-command opener to land on the right row, restore service first, and finish by re-running the original failing check to prove it's green.

After the fix

"structured incident response process"

Fixing the outage is half the job; closing the loop is the other half. A crisp five-line postmortem takes five minutes to write:

  1. Symptom: what users or checks observed, with timestamps.
  2. Blast radius: what broke and what stayed healthy.
  3. Root cause: the exact mechanism that failed, never a person to blame.
  4. Fix: what resolved it (including dead ends worth documenting).
  5. Proof & prevention: the verification command that confirmed recovery, plus one concrete follow-up (an alert, policy, or default) so it can't recur.

Keep the SRE vocabulary handy too: MTTD (detect), MTTA (acknowledge), MTTR (restore), error budget (allowable unreliability under an SLO), and toil (manual, repetitive operational work that scales with load, which is exactly what platforms exist to eliminate).

Remediation ≠ resolution

Both on exam day and on call: stabilize users first (rollback, scale, fail over, bypass a broken guardrail), then fix the underlying root cause properly. Two different actions, two different urgencies: always be explicit about which one you've completed.

Self-check

say the first command out loud
Every pod in a namespace is Running and the app returns nothing. First three moves?

Force a real request (run curl or nslookup from inside the namespace) so you have live evidence; inspect the Service's EndpointSlice and pod readiness; then check Hubble for DROPPED NetworkPolicy verdicts and DNS resolution. "Running" only proves kubelet started the container.

A pod is CrashLoopBackOff and kubectl logs shows nothing useful.

Run kubectl logs --previous so you read the container that actually crashed rather than the fresh one still starting. Follow up with kubectl describe pod and lastState.terminated for the exit code and reason (137 + OOMKilled points to memory; 1 with stack trace points to app config).

Nothing can be created cluster-wide; every apply times out with a webhook error. What happened and what is the lever?

An admission webhook's backend is down while its failurePolicy is set to Fail, blocking every matching write. Fix the backend Deployment first, or in a genuine emergency, scope or remove the webhook configuration temporarily (section 5.2).

You have four minutes left and no theory that fits the evidence. What do you do?

Pull back to Step 1 and widen: re-check blast radius and recent events instead of digging deeper into the wrong object. Under exam pressure, flag the task and move on, because getting stuck on one hard task costs you two easy ones.

What proves an incident is over?

Re-running the exact check that failed and seeing it pass: the broken curl returns 200, the alert clears, or the validation probe succeeds. A pod saying Running never proves recovery on its own.

Every write to the cluster fails with etcdserver: mvcc: database space exceeded but reads work. What happened and what is the order of operations?

etcd filled its backend quota (2 GiB default) and tripped the NOSPACE alarm, flipping the store read-only. Run compact → defragment every member → etcdctl alarm disarm (in that exact order), raise --quota-backend-bytes if growth is legitimate, and track down whatever flooded etcd (event storms, giant ConfigMaps, or a looping controller).

A container exits with code 143 every 30 seconds and the app logs look healthy. Diagnosis?

Exit code 143 is SIGTERM: Kubernetes is gracefully killing it on a timer, which almost always means a failing liveness probe (wrong port/path, or timeout too short for startup). Check kubectl describe pod for Liveness probe failed events and fix the probe or add a startupProbe.

You roll a Deployment back with kubectl rollout undo and two minutes later it is broken again. Why, and what should you have done?

Your GitOps controller reconciled Git back onto the cluster. Either pause reconciliation first (argocd app set x --sync-policy none or flux suspend kustomization x) for an emergency undo, or go straight to reverting the Git commit so the controller rolls back cleanly for you.

Which kubectl debug invocation gives you tcpdump on a node without full root, and why does the default node debug pod fail at chroot /host?

Run kubectl debug node/<n> -it --image=<image with tcpdump> --profile=netadmin to grant NET_ADMIN and NET_RAW without full privilege. The default general profile mounts /host unprivileged, so host-root operations like chroot fail unless you pass --profile=sysadmin.
