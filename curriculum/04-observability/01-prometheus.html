Our obs layer installs kube-prometheus-stack, which bundles three distinct pieces people often blur together: Prometheus itself, the Prometheus Operator that wires it via CRDs, and a set of exporters and dashboards. On the exam you'll drive everything through those operator CRDs, so that's the layer to get fluent in.

Orientation

competency 4.1 · monitoring solutions

Two core skills drive this whole domain: getting a target scraped cleanly, and writing a PromQL query that answers a real question. Alerting, dashboards, DORA metrics, and incident debugging all sit right on top of those two.

The pull model in one paragraph

Prometheus scrapes HTTP endpoints on a schedule and writes samples into its local TSDB. Every unique combination of metric name plus label values creates a separate time series, which is why label cardinality is your primary scaling limit. Kubernetes service discovery feeds Prometheus the list of targets, relabeling filters and rewrites them, and each scrape records either success (up = 1) or failure (up = 0). Because nothing is pushed, short-lived batch jobs vanish unseen unless they report through a Pushgateway or emit an event elsewhere.

The operator model

ServiceMonitor · PodMonitor · selectors

Instead of hand-editing prometheus.yml, you declare what to scrape with CRDs. A ServiceMonitor targets endpoints behind Services matching specific labels (by port name, path, and interval). A PodMonitor scrapes pods directly without needing a Service. A ScrapeConfig reaches targets outside Kubernetes, and a Probe drives blackbox-exporter checks. The operator watches all of them and reloads Prometheus's config automatically.

ServiceMonitor (selector: app=example, port: web, path: /metrics)
      │  matched by Prometheus.spec.serviceMonitorSelector   ← the filter people forget
      ▼
Service app=example, ports: [{name: web, port: 8080}]
      │  its EndpointSlice supplies the actual pod IPs
      ▼
pod:8080/metrics  ──scraped every 30s──▶  series {job="example", namespace=…, pod=…}
The silent selector trap

Prometheus only watches ServiceMonitors matching its own serviceMonitorSelector. On a stock kube-prometheus-stack install, that requires the Helm release label (release: prometheus). Miss it, and your perfectly valid monitor gets silently ignored with zero errors and zero targets. Our lab turns that filter off (serviceMonitorSelectorNilUsesHelmValues=false) so {} picks up everything, but don't assume the exam cluster did. Always inspect the Prometheus selector first, then write the monitor.

kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.serviceMonitorSelector}'; echo
kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.serviceMonitorNamespaceSelector}'; echo
outputcaptured 2026-08-26
$ kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.serviceMonitorSelector}'; echo
{}
$ kubectl -n monitoring get prometheus -o jsonpath='{.items[0].spec.serviceMonitorNamespaceSelector}'; echo
{}

Here it prints {}; on a default chart install it prints the release-label matcher. Check the namespace selector right beside it too, because a monitor living in a namespace Prometheus doesn't watch is just as invisible.

The other three reasons a target goes missing

  1. Port name, not number. endpoints[].port expects the Service's port name. Leave the Service port unnamed and the monitor silently finds nothing to scrape.
  2. No ready endpoints. The Service selector doesn't match any Ready pods (section 1.1): same empty target list, different root cause.
  3. RBAC or NetworkPolicy. Prometheus's ServiceAccount needs permission to list endpoints in the target namespace, and default-deny tenant namespaces need an explicit ingress rule allowing traffic from monitoring.

Keep your debugging order simple: open Status → Targets in the Prometheus UI (it prints the exact failure reason), query up{job="…"}, then walk through those four checks.

Relabeling at exam depth

relabelings transform discovered targets before scraping (drop targets, rewrite job or namespace labels), while metricRelabelings filter samples after scraping. Keep one rescue move in your back pocket: dropping a noisy high-cardinality metric at ingestion using action: drop on a __name__ regex can save a struggling Prometheus instance on the spot.

  • Selectors: up{namespace="argocd"} using =, !=, =~, or !~. Prometheus regexes are automatically anchored end to end.
  • Ranges: adding [5m] turns an instant vector into a range vector for rate, increase, and *_over_time. Passing a range vector where an instant vector is expected throws "expected type instant vector."
  • Aggregation: sum by (label) (...) keeps only listed labels; sum without (pod) (...) keeps everything else. Never sum before taking a rate: always rate() first, then sum().
  • Vector math joins series with identical label sets; mismatched labels produce empty output unless you add on() / ignoring() and group_left (just like the cost gap query in section 1.5).
  • Handling missing series: absent(x) returns 1 when x disappears entirely (essential for dead-target alerts), and … or vector(0) turns empty results into a clean zero for stat panels.
  • rate vs. irate: rate averages across the full window (use for alerts and graphs), while irate only looks at the last two samples (great for sharp spikes, terrible for alerts). increase is rate × window, ideal for totals like "deployments in the last 24h."

The up metric

Every healthy target emits 1 and every failed scrape emits 0, making count(up == 0) the quickest health check on the cluster. make validate asserts it returns zero (which is why our lab patches kubeadm's localhost-bound control-plane metrics via make fix-cp-metrics). Any "is monitoring healthy?" question starts right here.

  • Namespace selector gotchas: on the Prometheus CR, a nil namespace selector watches only Prometheus's own namespace, {} watches all namespaces, and matchLabels filters by namespace label (such as kubernetes.io/metadata.name: team-a). On a ServiceMonitor itself, spec.namespaceSelector is the second gate: set matchNames: [argocd] or any: true, because omitting it restricts discovery to the monitor's own namespace.
  • Free label enrichment: jobLabel promotes a Service label into job, while targetLabels and podTargetLabels copy Service or pod labels onto every scraped series. Without them, series only carry namespace, pod, service, and endpoint, so "aggregate by team" requires copying that label here first.
  • Endpoints to EndpointSlice: since Kubernetes 1.33 deprecated v1 Endpoints, modern operators support spec.serviceDiscoveryRole: EndpointSlice (with discovery.k8s.io/endpointslices RBAC). Seeing an operator log warning about deprecated Endpoints just points to that migration.
  • Safety limits: sampleLimit, labelLimit, labelNameLengthLimit, and labelValueLengthLimit abort oversized scrapes outright (showing the reason under Status → Targets), handy as a circuit breaker against runaway exporters. Always keep scrapeTimeout shorter than scrapeInterval or config reload rejects it.
  • Relabel actions: replace (default), keep/drop via regex over sourceLabels, labelmap (copying __meta_kubernetes_pod_label_(.+) into real labels), labeldrop/labelkeep, and hashmod. Rewrite __address__, __scheme__, and __metrics_path__ whenever using raw kubernetesSDConfigs inside a ScrapeConfig.
Three-command reflex

Before authoring any monitor, run three quick reads: check the Prometheus selectors via kubectl -n monitoring get prometheus -o yaml, check the target Service's port names via kubectl get svc <name> -o jsonpath='{.spec.ports[*].name}', and confirm ready addresses via kubectl get endpointslices -l kubernetes.io/service-name=<name>. Zero guesswork.

Storage, cardinality, and scale

  • Retention: configured via --storage.tsdb.retention.time (15d default when neither is set) and --storage.tsdb.retention.size (exposed as spec.retention and spec.retentionSize). Keep size limits around 80–85% of your PVC because TSDB compaction briefly spikes disk usage.
  • Hunting cardinality: open Status → TSDB Status or run topk(10, count by (__name__) ({__name__=~".+"})). Fix the explosion at ingestion (metricRelabelings dropping the noisy metric or label) and upstream in the exporter; don't just throw RAM at it.
  • Scaling past one Prometheus: use remoteWrite (v2.0 in Prometheus 3.x) into Thanos Receive, Mimir, or Cortex, or pair a Thanos sidecar with object storage. PrometheusAgent runs scrape-only purely to remote-write. Federation (/federate with honor_labels: true) pulls aggregated rollups for small setups. Whenever a scenario asks for multi-cluster long-term retention, reach for remote write or Thanos, not federation.
  • Kubernetes native histograms: the NativeHistograms feature gate arrived alpha in 1.36 and became beta/default-on in 1.37; on older clusters control-plane metrics still emit classic _bucket series.

In the UI under Status → Targets, or via API: count the scrape pools, find which ServiceMonitor each corresponds to (kubectl -n monitoring get servicemonitors), and confirm zero targets down.

Self-check

answer before opening
Your ServiceMonitor is correct and no target appears. List the checks in order.

1) Prometheus's serviceMonitorSelector and serviceMonitorNamespaceSelector: is Prometheus even watching your monitor? 2) Does the monitor's selector match the Service's labels (and its namespaceSelector match the Service's namespace)? 3) Is endpoints[].port the Service's port name? 4) Does the Service have ready endpoints? 5) Check RBAC and NetworkPolicy between monitoring and the target namespace.

Why is sum(rate(x[5m])) right and rate(sum(x)[5m]) wrong?

Counter resets happen independently per series, and rate() only knows how to compensate for resets on an individual series. Summing first mixes resets across pods into garbage (and isn't even valid syntax without a subquery). Always rate() first, aggregate second.

How do you alert on "the metric disappeared entirely"?

Use absent(up{job="x"} == 1) or absent(metric). Standard comparisons return empty when there's no data to compare, so they can never fire; absent() explicitly turns "no series" into 1.

A p95 query returns NaN. Two plausible reasons?

Either no requests landed in the lookback window (empty buckets), or your aggregation accidentally dropped the le label that histogram_quantile needs. Keep it intact with histogram_quantile(0.95, sum by (le) (rate(x_bucket[5m]))).

An exporter added a label with one value per request. What happens, and what is the fix?

Instant cardinality explosion: every request creates a brand-new series, blowing up TSDB memory and slowing queries to a crawl. Drop the label or metric immediately via metricRelabelings, then strip it from the exporter. High-cardinality IDs belong in logs and traces, never Prometheus labels.

You need to scrape a database VM outside the cluster with the Prometheus Operator, without editing the Prometheus config by hand. Which CRD, and which selector must match?

Use a ScrapeConfig with staticConfigs[].targets: ["db.example.internal:9187"] (or httpSDConfigs / dnsSDConfigs), labeled to match Prometheus's scrapeConfigSelector and placed in a namespace matched by scrapeConfigNamespaceSelector (or Prometheus's own namespace if that selector is nil).

Predict that a volume fills within a day, and alert if any series that should exist has vanished. Two expressions?

For disk fill: predict_linear(node_filesystem_avail_bytes{mountpoint="/data"}[6h], 24*3600) < 0. For a vanished target: absent_over_time(up{job="payments"}[10m]), which evaluates to 1 only when zero samples showed up during the entire 10-minute window.

A ServiceMonitor in monitoring selects the right labels and port for Services in argocd, yet no target appears and Prometheus's own selectors are {}. What is missing?

spec.namespaceSelector on the ServiceMonitor itself (matchNames: [argocd] or any: true). Left unset, a ServiceMonitor only looks in its own namespace. Remember the two-hop rule: Prometheus's selector discovers monitors, and the monitor's namespaceSelector discovers Services.
