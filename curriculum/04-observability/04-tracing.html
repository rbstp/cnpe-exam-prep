Distributed tracing answers the one question metrics and logs can't touch: across a chain of microservices, where did the latency go or the failure actually begin? The vocabulary is compact, and the exam expects you to use it precisely.

Orientation

competency 4.1 · tracing solutions

Two habits make tracing tasks straightforward: knowing the exact OTLP address telemetry needs to hit, and remembering that a trace only hangs together if context propagates across every hop. Everything else is just reading the UI.

Lab topology

The OpenTelemetry Operator runs in opentelemetry-operator-system, with the Collector and Jaeger side by side in tracing. That gives you in-cluster OTLP endpoints at otel-collector.tracing.svc:4317 (gRPC) and :4318 (HTTP). Burn the pattern <svc>.<ns>.svc:4317 into memory - almost every tracing task starts right there.

Vocabulary and plumbing

spans · context · pipeline

A trace captures one request's end-to-end journey. A span represents a single timed operation along the way, stamped with a trace ID, its own span ID, its parent span ID, status, attributes, and events. Together they form a tree anchored at the root span.

Context propagation stitches spans across service boundaries: the caller injects trace context into outbound headers, and the callee extracts it to continue the same trace rather than starting a brand-new one. Modern stacks use W3C traceparent (alongside tracestate, plus baggage for custom key-values traveling with the request). Older services may still speak B3 headers, so mixed fleets configure propagators for both.

The classic broken-propagation tell

If Jaeger fills up with hundreds of single-span traces - one per service, none stitched together - context propagation is broken. Suspect a proxy stripping unknown headers, a mismatched propagator (W3C vs. B3), a hand-rolled HTTP client skipping header injection, or an uninstrumented async hop like a message queue.

The OpenTelemetry pipeline

app (SDK or auto-instrumentation agent)
   │ OTLP  gRPC :4317 / HTTP :4318
   ▼
Collector   receivers ──▶ processors ──▶ exporters
             otlp, jaeger,     batch, memory_limiter,   otlp_grpc/jaeger,
             prometheus,       attributes, k8s_attributes, debug,
             filelog           tail_sampling            prometheus
   ▼
backend  Jaeger (traces) · Prometheus (metrics) · Loki (logs)

The Collector is the platform team's control plane for telemetry: sampling, batching, PII redaction, and routing all belong here instead of inside app code. That's the platform-engineering answer to controlling observability spend - update one Collector deployment instead of chasing forty application teams.

SamplingDecidesTrade-off
Head-basedat trace start, typically a fixed percentagecheap and stateless, but can easily drop the one slow or broken request you actually needed
Tail-basedafter the trace completes, based on errors or latencykeeps every interesting trace, at the cost of buffering full traces in memory - and requiring every span of a trace to hit the exact same collector

Kubernetes-side: two CRDs

  • OpenTelemetryCollector: lets the operator manage collectors as Deployments, DaemonSets, StatefulSets, or Sidecars. Inspect its spec whenever you need to trace the receiver → processor → exporter chain.
  • Instrumentation: your zero-code auto-instrumentation path. Our lab ships one named auto in default; add instrumentation.opentelemetry.io/inject-java: "default/auto" (or -python, -nodejs, -dotnet) to a pod template and the admission webhook injects the language agent via an init container automatically.
Injection runs at pod creation only

Adding the annotation to a live Deployment won't touch existing pods - you have to trigger a rollout restart. Also make sure the annotation sits on spec.template.metadata (the pod template), not the Deployment's top-level metadata. Those two slip-ups cause 90% of "auto-instrumentation isn't working" headaches.

The Collector, field by field

pipelines, connectors, the processors that decide cost

A Collector configuration defines four data-path sections (receivers, processors, exporters, connectors), an extensions block for side capabilities (health_check, pprof, zpages), and a service.pipelines block that wires them together per signal. Declaring a component does nothing until a pipeline activates it. You can instantiate the same type multiple times with suffixes (otlp_grpc/2, otlp_http/loki), and a connector acts as both an exporter on one pipeline and a receiver on another (that's how span_metrics turns traces into RED metrics automatically). Note that Collector 0.16x renamed several components (otlp → otlp_grpc, otlphttp → otlp_http, k8sattributes → k8s_attributes, spanmetrics → span_metrics); older names still load with deprecation warnings, so stay fluent in both.

receivers:
  otlp: { protocols: { grpc: { endpoint: 0.0.0.0:4317 }, http: { endpoint: 0.0.0.0:4318 } } }
processors:
  memory_limiter: { check_interval: 1s, limit_mib: 800, spike_limit_mib: 160 }
  k8s_attributes: {}
  batch: {}
exporters:
  otlp_grpc/jaeger: { endpoint: jaeger-collector.tracing.svc:4317, tls: { insecure: true } }
  prometheus: { endpoint: 0.0.0.0:8889 }
connectors:
  span_metrics: {}
service:
  pipelines:
    traces:  { receivers: [otlp], processors: [memory_limiter, k8s_attributes, batch], exporters: [otlp_grpc/jaeger, span_metrics] }
    metrics: { receivers: [span_metrics], processors: [batch], exporters: [prometheus] }

Most production setups split into two tiers: an agent (DaemonSet or sidecar) sitting right next to workloads to enrich and batch, forwarding to a gateway (Deployment behind a Service) that handles tail sampling, redaction, and fan-out. When verifying whether spans arrive at all, add the debug exporter (verbosity: detailed) - the old logging exporter was removed in current builds and will crash startup.

Port/protocol mismatch trap

otlp_grpc expects host:port on 4317, while otlp_http expects a full URL on 4318. Crossing gRPC and HTTP ports causes cryptic connection resets or HTTP 415 / unimplemented errors. Note that Python auto-instrumentation speaks http/protobuf only, so always point its Instrumentation CR at port 4318.

Operator CRDs, Jaeger v2, and tracing failure modes

modes, annotations, backends, exemplars, failure modes

OpenTelemetryCollector and Instrumentation details

  • spec.mode: deployment (default), daemonset, statefulset (required for the target allocator or sharded tail sampling), and sidecar (injected via sidecar.opentelemetry.io/inject: "true" or a collector name - distinct from language injection annotations). The operator automatically renders spec.config into a ConfigMap and creates a Service matching your receiver ports (otlp-grpc, otlp-http). Enabling spec.targetAllocator lets a Collector StatefulSet shard Prometheus ServiceMonitor/PodMonitor scrapes.
  • Instrumentation fields: exporter.endpoint, propagators (tracecontext, baggage, b3), sampler.type (parentbased_traceidratio) and sampler.argument ("0.25"), plus per-language overrides (java.image, python.env, nodejs, dotnet, go).
  • Annotation values on instrumentation.opentelemetry.io/inject-<lang>: "true" (only works cleanly if there's one Instrumentation CR in the pod's namespace), "name", "namespace/name", or "false". Multi-container pods need instrumentation.opentelemetry.io/container-names: "app,worker" or only the first container gets instrumented. Use inject-sdk for env vars only, and note that Go auto-instrumentation uses eBPF with a privileged sidecar (pointing otel-go-auto-target-exe at the binary), which a restricted PSS namespace rejects.

Jaeger v2 and Tempo

Jaeger v2 is built straight on top of the OpenTelemetry Collector: one jaeger binary configured in Collector YAML, running as collector, query, ingester (from Kafka), or all-in-one. Its extensions include jaeger_storage (in-memory, Badger, Cassandra, Elasticsearch, OpenSearch, ClickHouse), jaeger_query (UI and API on port 16686), remote_sampling, and the adaptivesampling processor. Ingest is pure OTLP on 4317/4318 - legacy v1 jaeger-agent and Thrift ports are gone (use an OpenTelemetry Collector instead). The HTTP query API (/api/traces?service=) stays unchanged for scripted checks.

You'll also see Grafana Tempo named in scenarios: an object-storage trace backend indexed primarily by trace ID, queried with TraceQL, and sporting a metrics-generator that emits span metrics and service graphs to Prometheus just like the Collector's span_metrics connector.

Exemplars and semantic conventions

An exemplar attaches a real trace_id to a Prometheus histogram bucket sample (# {trace_id="abc..."} in OpenMetrics text), letting you jump straight from a latency spike on a dashboard into an exact slow trace. Prometheus stores them when --enable-feature=exemplar-storage (spec.enableFeatures) is on, and Grafana wires the jump via exemplarTraceIdDestinations. Consistent semantic conventions tie all three signals together: service.name (unset = unknown_service), service.namespace, k8s.namespace.name, k8s.pod.name, k8s.deployment.name, http.request.method, http.response.status_code, and url.path (dots become underscores when exported to Prometheus).

How this gets tested

"Deploy a Collector forwarding OTLP traces to Jaeger" → OpenTelemetryCollector with an otlp receiver, pipeline, and exporter pointed at Jaeger on 4317. "Auto-instrument this Deployment" → Instrumentation CR + pod-template annotation + rollout restart. "Keep only errors and requests over 1s" → tail_sampling with status_code and latency policies (plus trace-ID-aware routing if running multiple replicas).

Self-check

answer before opening
Jaeger shows hundreds of one-span traces. Diagnosis?

Context propagation is broken, so every service starts its own orphan trace. Check for a proxy stripping traceparent, a propagator mismatch (W3C vs. B3), a hand-rolled HTTP client skipping header injection, or an uninstrumented async queue hop.

Head-based versus tail-based sampling: when does the difference bite?

Whenever rare failures matter most. Head sampling at 1% usually discards the exact 5-second timeout or 500 error you needed to debug. Tail sampling inspects finished traces so you keep every error and slow request, trading extra collector memory and trace-ID-aware routing across replicas.

Where should sampling and redaction be configured, and why there?

In the OpenTelemetry Collector. It's the platform's central control plane: one config edit updates sampling and PII redaction across the entire fleet without begging forty app teams to redeploy their SDKs.

You annotated a Deployment for auto-instrumentation and nothing changed. Two most likely reasons?

Either the annotation went on the Deployment's metadata instead of spec.template.metadata, or you haven't restarted the pods yet (webhook injection only fires at pod creation). Third check: verify the <namespace>/<name> value matches a real Instrumentation CR.

How do traces, metrics and logs tie together in practice?

Exemplars link histogram latency spikes straight to sample trace IDs, structured logs include the trace ID so you can pivot directly from a slow span into its exact log lines, and the Collector stamps shared Kubernetes resource attributes across all three signals.

Your tail-sampling collector runs three replicas behind a Service, and the sampling decisions look random. Why, and what fixes it?

A normal Kubernetes Service spreads spans from the same trace across different replicas, so no collector ever sees the full trace before decision_wait fires. Put a front-tier collector with a loadbalancing exporter (routing_key: traceID) ahead of a StatefulSet sampling tier - or run a single sampling replica.

What is Jaeger v2 architecturally, and where does the old jaeger-agent go?

Jaeger v2 is a distribution of the OpenTelemetry Collector: one binary configured in Collector YAML, running as collector, query, ingester, or all-in-one with Jaeger extensions for storage, query UI (16686), and remote sampling, ingesting standard OTLP on 4317/4318. The legacy jaeger-agent is gone - run a standard OpenTelemetry Collector as a DaemonSet or sidecar instead.

A pod has the injected init container and the right annotation, yet no spans appear. Two collector-side reasons and one network reason?

Collector/config: the Instrumentation endpoint uses the wrong port for the language agent's protocol (Python only speaks HTTP on 4318, while Java defaults to gRPC on 4317), or the Collector has no traces pipeline wired to that receiver. Network: a default-deny NetworkPolicy blocks egress to the collector namespace. Inspect OTEL_EXPORTER_OTLP_ENDPOINT inside the pod and test the port directly.

How does a metric panel jump to a trace, and what has to be enabled at each layer?

Through exemplars: the app or span_metrics connector attaches trace_id to histogram buckets, Prometheus retains them when --enable-feature=exemplar-storage is enabled, and Grafana maps trace_id to Jaeger or Tempo via exemplarTraceIdDestinations. Logs join the same loop through Loki's derivedFields.

Docs to know your way around

study time, not exam time
  • opentelemetry.io: the Concepts pages (signals, context propagation), the collector's receivers/processors/exporters reference, and the Kubernetes operator's Instrumentation injection docs.
  • jaegertracing.io: the UI is mostly self-explanatory; know that the HTTP API exists for scripted verification.
  • w3.org/TR/trace-context: one page, and it is the header everything agrees on.
  • opentelemetry.io/docs/collector/configuration: sections, connectors and pipelines; the processor READMEs in github.com/open-telemetry/opentelemetry-collector-contrib (tailsamplingprocessor, k8sattributesprocessor) hold the field defaults.
  • opentelemetry.io/docs/platforms/kubernetes/operator/automatic: annotation values, container-names, the Go and Python caveats; the troubleshooting page beside it is the injection diagnostic ladder.
  • jaegertracing.io/docs/latest/architecture: roles, storage backends and the "we recommend the OpenTelemetry Collector instead of the agent" statement.
