# 4.2 Alerting: rules, Alertmanager, routing

Competency: implementing alerting solutions and notification routing (domain 4, 20%). Needs: `make up obs`.

Two systems, one handoff, and keeping their jobs separate answers half the questions about them. Prometheus evaluates alerting rules and decides what is *true*. Alertmanager receives those firing alerts and decides who *hears* about it: grouping, routing, silencing, inhibition. "Where do I configure X" questions are really "which side of the handoff is X" questions.

## Rules

A PrometheusRule CRD holds groups of rules. An alerting rule is a PromQL expression plus `for` (how long it must hold before Pending becomes Firing), `labels` (routing material, e.g. severity), and `annotations` (human material, summary and description, which can template in `{{ $labels.x }}` and `{{ $value }}`). The same selector story as ServiceMonitors applies: rules are only evaluated if they match the Prometheus object's `ruleSelector`. This lab's is `{}` (everything), a stock install's is the release label, and an unmatched rule produces no evaluation and no error, so read the selector before blaming the rule.

Alert states: Inactive → Pending (expression true, `for` not yet satisfied) → Firing. Pending alerts are visible in Prometheus's Alerts page and nowhere else, which matters when someone asks why nothing reached the receiver yet.

## Routing

Alertmanager's config is a tree of routes. Each alert enters at the root and descends to the most specific matching route; `continue: true` lets it match siblings too. A route names a receiver (webhook, email, Slack, PagerDuty...) and grouping keys: `group_by` collapses alerts sharing those labels into one notification, `group_wait` batches the first send, `group_interval` and `repeat_interval` pace the rest. Silences mute matching alerts for a time window without touching config; inhibition suppresses alerts when a related more-severe alert is already firing (node down inhibits everything on that node).

In this stack the live config is generated by the operator into a secret, and the UI's Status page shows the rendered result. The operator also supports namespaced AlertmanagerConfig CRDs that merge into the tree; whether an Alertmanager picks them up depends on its `alertmanagerConfigSelector`, so *verify pickup in the rendered config* rather than trusting the apply. That verify-the-rendered-truth habit transfers to every operator-managed config on the exam.

## Exercises

Alertmanager has no LoadBalancer here: `kubectl -n monitoring port-forward svc/prometheus-kube-prometheus-alertmanager 9093:9093` and browse localhost:9093.

**Fire an alert you control.**

```bash
kubectl apply -f - <<'EOF'
apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: curriculum-drill
  namespace: monitoring
  labels: { release: prometheus }
spec:
  groups:
    - name: drill
      rules:
        - alert: TooManyExamplePods
          expr: count(kube_pod_info{namespace="default"}) > 0
          for: 1m
          labels: { severity: warning, team: platform }
          annotations:
            summary: "{{ $value }} pods in default"
            description: "Drill alert; fires whenever default has any pods."
EOF
```

Watch it walk the states: Prometheus UI → Alerts shows Pending, then Firing after the minute. Verify: it appears in the Alertmanager UI with your labels, grouped. Then check the annotation rendered the live value, not the template text.

**Silence it like an operator would.** In the Alertmanager UI, create a silence matching `alertname=TooManyExamplePods` for 2 hours with a comment. Verify: the alert leaves the active view and lands under Silences, while Prometheus still shows it Firing. That split is the lesson: silencing changes notification, never truth.

**Read the routing tree.** Open Status in the Alertmanager UI and answer from the rendered config: what is the root receiver, what does `group_by` collapse on, which special route exists for the Watchdog alert (the stack ships one that fires always, as a dead-man's switch; know why that is a feature). Verify: you can trace where your drill alert's `severity: warning` lands in the tree and say which single config line you would change to route `team: platform` alerts to a new webhook receiver.

**Route to a receiver you can see (stretch).** Deploy a trivial webhook sink (`kubectl create deploy sink --image=mendhak/http-https-echo:31` plus a Service), add an AlertmanagerConfig in `default` routing `team: platform` to it, and then verify pickup honestly: does the rendered config in the UI now contain the route? If yes, `kubectl logs deploy/sink` shows the JSON payload when the drill alert fires, and read that payload once; its structure (groupLabels, commonAnnotations, alerts[]) is what every receiver integration parses. If the config never picks it up, find the selector on the Alertmanager object and state what would have to change; diagnosing that honestly is worth as much as the happy path.

Clean up: delete the PrometheusRule, the silence expires on its own.
